## 执行摘要

1. **Agent 的竞争正从「模型能力」转向「执行环境」。** 云端常驻 Agent（xAI Grok Bot、OpenAI dot）单用户每月成本约 $70–300（估算），只开放给 $100 以上的订阅档；Apple、Google、华为、荣耀已把应用能力函数化（App Intents、AppFunctions、HMAF、MCP / A2A），并以 12GB 内存划定端侧准入线。手机厂商能守住的位置是端侧执行环境，即本机应用、个人上下文和系统资源调度，它的硬约束是内存。
2. **加内存的路走不通。** 2025 年末全球手机平均 DRAM 只有 8.4GB，2026Q2 手机内存价格环比 +80%，TrendForce 判断 2027 年不会明显回落；而端侧常驻权重年增约 40%–60%（估算）。两条曲线已经在 12GB 机型上交叉，系统只能自己挖出更多可用内存。
3. **Agent 不会替换应用，而是叠加在应用之上。** 头部应用只开放部分接口，Agent 仍要拉起应用、等用户前台确认。以 12GB 机型、模型常驻 1–6GB 计，留给应用的内存只有约 2.5–7.5GB（估算）；GB 级应用 86.6% 的冷启动已超过 1 秒。叠加场景下，冷启动、切换卡顿和后台被杀会一起恶化。
4. **业界没有人把「模型内存」纳入系统统一治理。** 四家系统级平台都没有公开模型常驻占用、回收与共享机制；主流推理引擎中只有系统托管路线能跨应用共享权重，NPU 路径的缓冲脱离页缓存、被长期钉住。阶跃把「为端侧模型弹性供给资源」写进了 OS 叙事，但没有给出任何量化指标。这是我们可以占据的位置。
5. **Agent OS 的总体构想：模型内存成为系统的一等公民，做到统一记账、可回收、可共享。** 架构上是「一本账、一套冷热证据、一条 IO 队列」。三项关键技术：
   - **KT1 智慧化内存管理**：管应用和 Agent 中非模型部分的内存，包含 .so 文件页锁优化、基于 SPE 的匿名页预取、基于 SPE 的匿名页换出三个子技术；
   - **KT2 Agent 内存组件**：MoE 专家缓存（建议泛化为稀疏权重分层）与 KV Cache 回收和压缩；
   - **KT3 模型翻译组件**：零拷贝的模型加载与卸载。

   配套建设性能跟踪与仿真平台（S1 云转端评估、S2 单 Agent 并行化），用来建立基线、校准目标、评估收益。
6. **AI + 图形是体验线，系统层做 App 做不到的事。** 手机 GPU 已内置神经加速，3DGS 渲染可行，A2UI 已进入 Android 官方渠道；国内旗舰把「超帧」做成卖点，第三方插帧芯片厂 Pixelworks 已退出移动业务。差异化在「热稳态下的全链路能效」与「系统层才能做好的事」：常驻低功耗的萌宠、对游戏透明的神经后处理、流式且原生一致的生成式 UI。AI 陪伴的监管已落地，萌宠定位为「助手的表现层 + 轻陪伴」。
7. **收益可量化、可折算。** 建议目标：叠加场景冷启动 -15%～-30%，后台存活应用数 +30%～+80%，切回前台时延 -20%～-40%，12GB 机型释放 ≥2GB 等效可用内存（按 2026Q2 合约价约每台 $40）。全部为建议区间，以 S1 基线校准后承诺。
8. **最大的风险是前提不成立。** 三项单点前置风险在 2027-Q1 末收口：量产手机 SoC 是否开放 SPE（KT1-b/c）、NPU 驱动能否映射文件页（KT3）、有没有真机基线（全部目标）。立项第一阶段必须先建好标准负载集、体验指标和真机基线，再把建议区间定成承诺值。

# 第一部分 洞察：业界最新发展趋势

> 本部分回答三个问题：Agent 的商业形态正在往哪里走、哪条路线留给终端厂商的位置最大；支撑端侧 Agent 的基础能力（模型、引擎、内核、硬件、评估手段）演进到了哪一步、缺口在哪里；AI + 图形四个议题的产业成熟度与机会窗口。每节先给事实，再给「分析：这说明什么」。分析部分为立项组的判断。

## 1.1 Agent 商业形态：三条路线并行

### 1.1.1 全景

2026 年下半年，Agent 产品沿三条路线同时推进。三条路线的分歧不在模型能力，而在于 **Agent 的执行环境放在哪里**：放在云端虚拟机里、放在手机操作系统里，还是另起一台为 Agent 设计的整机。

| 维度 | ① 云端常驻 Agent | ② 系统级端云 Agent | ③ 整机重构 Agent 手机 |
|---|---|---|---|
| 代表产品 | xAI Grok Bot（2026-08 公测）；OpenAI dot（2026-09 DevDay）；Meta Muse（2026-09） | Apple iOS 27 新 Siri；Google Android 17 Gemini Intelligence；华为 HarmonyOS 7 小艺；荣耀 MagicOS 11 | 阶跃 STEPX Neo + Step AOS（2026-10 首销）；字节豆包 × 努比亚（二代 2026-09）；荣耀 Robot Phone |
| 执行环境 | 云端 Linux 虚拟机 + 浏览器 + 文件系统，7×24 常驻，关掉终端后任务继续 | 端侧模型处理高频短任务，复杂任务上云（Apple PCC、Gemini 云、盘古云） | 自研或深改的 OS；端侧小模型执行简单指令，多应用任务交云端大模型 |
| 应用接入 | 云电脑登录用户账号；连接器与插件（dot 称 4000+ 应用）；浏览器直接操作网页 | 应用能力声明成函数：App Intents、AppFunctions、HMAF Skill、MCP / A2A；GUI 只作兜底 | 阶跃以 MCP / A2A 接入（支付宝 300+ 服务）；豆包一代 GUI 自动化，7 月起转向 MCP（LatePost 报道） |
| 商业模式 | 高价订阅：dot 只随 ChatGPT Pro（$100–500/月）提供；Grok Bot 单买 $200/月 | 系统免费，换入口与生态流量；Apple 早期不向开发者收取佣金（报道） | 卖硬件并打包云 token：STEPX Neo 3999 元含 12 个月 Token Plan（每月 1000 亿 token） |
| 规模与门槛 | 不受端侧资源约束；单用户成本约 $70–300/月（估算，见 1.1.3） | 用内存划线：Apple、Google 最强端侧能力都要求 12GB；Gemini Nano 已在 1.4 亿台以上设备运行 | 规模小：阶跃不设出货目标；豆包二代预约 36 万+，销量未公开 |
| 核心约束 | 成本与可靠性：dot 10 步任务链越权率 19.7%（OpenAI 系统卡，二手转述） | 内存：端侧模型常驻挤压应用；四家都没有公开模型常驻占用与回收机制 | 生态开放度：150 余款应用拒绝 GUI 自动化（2026-10）；接入方「只开一扇窗」 |

来源：M1 §1.0–1.1、D1 §1–5。

**分析：这说明什么。** 三条路线不是替代关系。云端路线拥有模型和算力，但没有本机上下文，也拿不到本机应用；系统级路线拥有入口、本机应用和个人数据；整机路线在叙事上领先，但规模有限。对手机厂商而言，能守住的位置是 **端侧执行环境**，即本机应用、个人上下文和系统资源调度。这个位置的硬约束是内存，这正是本立项要补的能力。

### 1.1.2 点名产品拆解（一）：阶跃 Step AOS / STEPX Neo

**架构拆解**（据公开报道整理，均为厂商口径）

| 层次 | 组成 | 说明 |
|---|---|---|
| 交互层 | 意图入口（语音为主，6 麦）；Amoo 个人智能体作首页；MiniLED 背屏显示后台任务进度 | 双入口：传统 App 宫格 + 独立 Agent 空间 |
| Agent 层 | 长期记忆（用户事实与偏好 + 任务执行经验，称检索最快 15ms）；任务调度与端云分工；安全（TEE 内执行、每步可审计） | 记忆存放在端还是云：未披露 |
| 能力层 | 手机功能（短信、应用、文件、设置）拆成可调用的「块」；第三方经 MCP / A2A 接入 | 支付宝开放 300+ 服务；美团只开放跑腿；微信本体缺席 |
| 模型层 | 端侧 Step Edge 家族四款（基础 / 音频 / GUI / 生成）+ 自研 Step Inference NPU 引擎；云端 Step 5 Preview（600B 总参、27B 激活、1M 上下文） | 端侧参数量与常驻内存：未公开 |
| 资源层 | 统一调度 CPU / GPU / NPU 异构算力，为端侧模型和系统服务「弹性供给」；统一语义数据层 + 高速混合数据库 | **与本立项直接相关**；没有任何量化指标 |
| 硬件 | 骁龙 8 系；16GB + 256GB（单一来源）；闻泰 ODM | 与 AOSP 的确切关系：未找到官方说明 |

**商业模式与现状**：3999 元是「软硬模全栈价」，包含手机、Step AOS、Step Studio 开发工具和 12 个月 Token Plan，第 13 个月起的价格未公布。10-16 首销，厂商称不设出货目标，至今没有独立评测；分析师评价为「一次合格的开发者版发布」。（D1 §1.1）

**分析：这说明什么。**
1. **OS 资源调度被视为 Agent 手机的核心能力。** 阶跃把「统一调度异构算力、为端侧模型弹性供给」放在 OS 底层，说明内存与算力供给已经进入 Agent 手机的产品定义。但参数量、常驻内存、回收机制全部空白，这个空位正是大厂可以用量化指标占领的。
2. **端侧承接比例直接决定毛利。** 端侧只做简单指令，复杂任务上云，厂商把每月 1000 亿 token 的云成本打包进售价，说明云 token 是长期成本项。端侧每多承接一类任务，就少一份持续支出。
3. **应用开放度由应用方利益决定。** 接入面靠逐家谈判，开放接口不足时，Agent 仍要拉起应用、等用户在前台确认，叠加场景会长期存在。
4. **对我们的启示。** 不必另起一个 OS。可落地的差异化在现有内核上的内存与 IO 供给，而且要给出阶跃没有给出的数字：常驻占用、冷启动劣化、后台存活数。

### 1.1.3 点名产品拆解（二）：Grok Bot 与 OpenAI dot（云端常驻 Agent）

**共同架构**：Agent = 模型 + 云端执行环境 + 连接器。入口是 ChatGPT、Slack、Teams 或桌面客户端，手机只作遥控；执行环境是持久化的云端 Linux 虚拟机，带 Chrome、文件系统和终端；应用经插件、连接器、自定义 MCP 或浏览器登录态接入。安全依靠环境外的独立自动审核检查每个计划动作，密码与付款永远交还用户。OpenAI 承认提示注入防护「不能消除风险」。

| 对比项 | xAI Grok Bot | OpenAI dot |
|---|---|---|
| 发布 | 2026-08-11 公测 | 2026-09-29 DevDay |
| 执行环境 | 账号级共享云 VM，多个 bot 共用一台，规格未披露（Vellum，竞品所写，待核实；**更正 M1「每个 bot 一台云电脑」的说法**） | 每个 dot 一台云端 Linux 电脑 + Chrome |
| 开放档位 | 单买 $200/月；SuperGrok Heavy、Cursor Ultra 等订阅附带 | 仅随 ChatGPT Pro（$100 / $200 / $500）与 Business Premium 附赠，Plus 及以下不含（二手，来源有冲突） |
| 可靠性 | 无独立测试 | 10 项商务任务均分 8.8，五个 Agent 中第三；5 步 / 10 步任务链越权率 8.6% / 19.7%（OpenAI 系统卡，二手转述） |
| 对终端的要求 | 无 | 无（安装与设置仅限桌面） |

**单位经济性（估算）**：一个常驻云 Agent 每用户每月要花多少？

| 成本项 | 口径 | 每用户每月 |
|---|---|---|
| 云电脑常驻 | 2vCPU / 4GiB × 730 小时，E2B 零售价（0.0504 $/vCPU·h、0.0162 $/GiB·h）：(2×0.0504 + 4×0.0162)×730 | 约 $121（自建机房可低数倍） |
| 浏览器 | 每天 4 小时 × $0.10–0.12/小时 × 30 天 | $12–14 |
| 模型 token | 每任务 30 万输入 + 2 万输出，按 GPT-6 Astra API 价：全缓存 $1.3，不缓存 $4.0；每月 30–90 个任务 | $40–360 |
| 合计 | 常见区间 | **$70–300** |

交叉验证：Manus 单任务付给模型厂商约 $2（The Information，待核实）；Anthropic 公开 Agent 的 token 用量约为普通对话的 4 倍、多 Agent 约 15 倍。对照定价：$20 档只够约 5 个任务；OpenAI 不向 Plus 开放 dot，Plus 的 ChatGPT Agent 额度仅为 Pro 的 1/10，是同一结论的市场证据。（D1 §2）

**分析：这说明什么。**
1. **云端常驻 Agent 在 2026 年的价格体系下进不了大众价位**：成本约 $70–300/月，与 $100–500 的开放档位恰好重合。
2. **它们抬高了用户预期**（全天候、主动、跨应用），手机上的 Agent 会被拿来对比。
3. **长任务链可靠性仍是瓶颈**（越权率 8.6%–19.7%），说明端侧也不应承接长链自治任务。
4. **反向证据必须写清**：端侧也不免费。内存涨价使 12GB + 256GB 的采购成本上升约 1700 元（博主数据，待核实），按 3 年摊销约 $6.7/月。端侧在账面上仍更便宜，但端侧承接的是高频、短时、隐私、离线、与本机应用叠加的任务，复杂规划仍要上云。因此表述应为 **端云混合**，而不是「端侧替代云」；每类任务是否下沉，由 S1 量化。

### 1.1.4 系统级 Agent：四家平台对比

**接口化进程**：2025-12 豆包一代发布后 48 小时内被微信、淘宝、支付宝等限制 → 2026-05 Google AppFunctions 私有预览 → 2026-06 HMAF 2.0 发布，微信与五家手机厂商洽谈 A2A → 2026-07 豆包新版转向由应用方提供 MCP（LatePost，与 9 月仍用 GUI 的报道有冲突）→ 2026-10 SAEP 公示期结束，150 余款应用（含微信、支付宝、淘宝、美团）拒绝 GUI 自动化。（D1 §3、§5）

**分析：这说明什么。**
1. **应用函数化成为共识。** Agent 通过函数调用应用，但头部应用只开放部分能力。需要拉起应用界面、等用户前台确认的场景会长期存在，冷启动与切换体验因此成为 Agent 体验的一部分。
2. **内存是共同的准入线，模型内存是共同的黑箱。** 两大平台都用 12GB 划线，却没有一家公开模型常驻占用、回收与共享机制。这是我们用系统能力建立差异化的空位。
3. **商业模式上**，系统级 Agent 大多以免费换入口与生态，付费订阅仍集中在云端 Agent 的 $100+ 档。

| 配置走向 | IDC：一年前的 12GB + 256GB 可能退到 8GB + 128GB；高端 12GB 成主流、16GB 采用率下降 | IDC；TrendForce |
| ≥12GB 机型占比 | 全球与中国均未找到公开资料（付费数据库） | — |

**分析：这说明什么。**
1. **能用上最强端侧 Agent 的用户是少数，而且在变少。** 门槛 12GB，均值 8.4GB；内存涨价让中端回落到 8GB，12GB 以上用户群在 2026–2027 年反而收窄。
2. **加内存的路被价格堵死。** TrendForce 判断 2027 年合约价不会明显回落，厂商守住 12GB 已属不易，不会为 Agent 再加 4GB。
3. **系统能力可以直接折算为 BOM 与覆盖面。** 按 2026Q2 合约价，每多出 1GB 等效可用内存，约等于每台省下 $20（约 140 元）DRAM；能让 Agent 在 12GB 机型上与应用叠加不卡、并下探到更低配置，就扩大了 Agent 的可用人群。立项的价值主张因此可以量化为「不加 DRAM，撑起 Agent 与应用叠加」。

### 1.1.6 商业形态洞察结论：对终端 OS 的五个要求

| 对终端 OS 的要求 | 依据 | 如果做不到 | 本立项的对应内容 |
|---|---|---|---|
| 一、不加 DRAM，把有效内存做大 | 门槛 12GB，均值 8.4GB；内存价格环比 +80% | Agent 只能覆盖少数旗舰；在 12GB 机型上与应用争内存 | 总体构想；KT1-b / KT1-c |
| 二、模型内存被系统统一治理 | 端侧走向稀疏大模型 + 闪存驻留；四家平台均未公开治理机制 | 权重、KV、NPU 缓冲长期钉住，只能靠杀应用腾空间 | KT2；KT3 |
| 三、应用拉得起、切得回 | 头部应用只开放部分能力，Agent 仍要拉起应用 | 冷启动劣化、切回卡顿被归咎于 Agent | KT1-a；KT1-b |
| 四、端云分工算得清 | 云端常驻约 $70–300/用户/月；整机路线把云 token 打包进售价 | 要么云成本失控，要么端侧体验受损 | S1 |
| 五、单个 Agent 跑得快 | 云上并行化证据充分；端侧 decode 受带宽限制，工具多有副作用 | 多步任务时延是各步之和 | S2 |

**结论**：Agent 的竞争正在从「模型能力」转向「执行环境」。对手机厂商，执行环境的护城河是本机应用、个人上下文和系统资源调度，其中内存供给是 2027 年最紧的约束，也是业界公开资料里最大的空白。

## 1.2 基础能力洞察

### 1.2.1 端侧模型的内存需求曲线

| 模型（时间） | 参数 / 量化 | 端侧内存 | 形态变化 |
|---|---|---|---|
| Gemini Nano-2（2023-12） | 约 3.25B，4bit | 约 1.6GB（估算） | 稠密 |
| Apple 端侧模型（2024） | 约 3B，平均 3.7bit | 约 1.4GB（估算） | 稠密 + 低位宽 |
| Apple 端侧模型（2025） | 约 3B，权重 2bit QAT | 权重 <0.75GB（估算） | 层间共享 KV，KV -37.5% |
| Gemma 3n E2B（2025） | 原始 >5B，有效 1.91B | 约 2GB（官方） | PLE 逐层嵌入放快速存储 |
| Gemma 4 E2B / E4B（2026-04） | 有效 2B / 4B | 1.1 / 2.5GB（官方移动端） | 滑窗 + 层间共享 KV；KV 约 6–14KiB/token（估算） |
| Gemini Nano 4（2026-08） | 基于 Gemma 4 E2B / E4B | Fast 4.2 / Full 5.9GB（二手，口径不明） | 系统托管；据报至少 12GB 机型 |
| Apple AFM 3（2026-06） | 20B 总参，激活 1–4B（二手，矛盾） | 未公开 | 稀疏 MoE，闪存驻留 |
| Qwen3-4B → Qwen3.5-4B | 4B | Q4 约 2.4GB（估算） | KV 每 token 144 → 32KiB |

**增长率（估算）**：以 Gemini 路线计，常驻权重从 2023-12 的约 1.6GB 涨到 2026 年的 4.2–5.9GB，跨度约 2.7 年，折合年增约 43%–62%（4.2/1.6 = 2.6 倍，e^(ln2.6/2.7) ≈ 1.43；5.9/1.6 = 3.7 倍，e^(ln3.7/2.7) ≈ 1.62）。同期手机平均 DRAM 从 7.4GB 到 8.4GB，约 +13.5%。沿此外推，2027 年同口径为 5.9–9.4GB，逼近 12–16GB 机型的一半以上，物理上不可持续。Apple 走另一条路：2-bit QAT 后常驻权重反而下降，代价是需要 QAT 与低秩适配器恢复质量。（D2 §1）

**分析：这说明什么。**
1. **剪刀差已经出现**：常驻权重增速约为 DRAM 的 3–4 倍，且 DRAM 在 2026–2027 年受价格压制更难增长。两条曲线的交叉点已经出现在 12GB 机型上，这是「内存是第一瓶颈」的直接数据。
2. **模型侧三个方向一致**：稠密走向稀疏（PLE、MoE、激活稀疏）；全量 KV 走向滑窗与层间共享；位宽降到 2–4bit。这些由模型厂商决定，OS 无法事后加上；OS 能做的是为「稀疏权重分层」和「多会话 KV」提供系统支持。
3. **KV 的主矛盾在转移**：单 token KV 两年降了约一个数量级，2027 年的压力来自「多会话 × 长 Agent 上下文」，而不是单会话。KT2-B 的投入要与此对齐，避免押注稠密模型的 KV 压缩。

### 1.2.2 推理引擎：模型内存游离在 OS 之外

| 引擎 | 权重加载 | KV 管理 | 多应用 / 多会话共享权重 | OS 能否看到并回收 |
|---|---|---|---|---|
| llama.cpp | 默认 mmap，权重是文件页 | 按上下文预分配；支持 q8_0 / q4_0 | 多进程映射同一文件时共享页缓存（推断） | 权重可回收；KV 是匿名页，计入进程 RSS |
| ExecuTorch | mmap / mlock 多模式；.pte 数据段页对齐 | 编译期写入最大上下文 | 两个 .pte 不共享权重，RFC 推进中 | 选 mlock 则被钉住、不可回收 |
| LiteRT-LM（应用内） | 首次加载优化并缓存；Gemma 4 E2B 峰值内存 1733MB（CPU） | 未公开 KV 上限 | 每个应用各一份 | 按进程由 lmkd / Jetsam 治理 |
| Android AICore | 系统服务托管 Gemini Nano | 请求级隔离，多轮历史由应用管理 | 是：所有调用方共享一份模型与 LoRA | AICore 进程如何被 lmkd 评分：未公开 |
| MNN-LLM | 低利用率参数（如 Embedding，约 15%）放闪存 | KV 超阈值溢出到闪存并预取 | 未公开 | 未公开 |
| 高通 QNN / Genie | context binary 预编译、绑定单一 SoC | KV 在 NPU 可见缓冲 | 同一 binary 内共享；跨应用未公开 | 缓冲注册到 NPU 地址空间、通常钉住，不在 LRU |
| Apple Foundation Models / MLX | 系统共享端侧模型；MLX 由应用自带 | 上下文 8192（二手） | Foundation Models 共享；MLX 应用私有 | 受 Jetsam 约束：单应用上限约 6144MB，8GB 与 12GB 机型相同（论坛实测，非官方） |
| 华为 MindSpore Lite | 2.7.0 支持进程间共享模型权重 | 大模型 KV 管理未公开 | 框架级支持 | HiAI Foundation 加载机制未公开 |

**分析：这说明什么。**
1. 引擎层面的共识是「权重文件化 + 页对齐 + mmap」，但这只在 CPU 路径成立；一旦走 NPU，权重要被拷贝或注册到厂商私有缓冲，脱离页缓存，OS 既不能回收，也无法跨应用共享。
2. 真正做到多应用共享一份权重的只有系统托管路线（AICore、Foundation Models）；其他情形下，每多一个带模型的应用，就多一份权重和一份 KV。系统托管解决了共享，但没有解决「被谁回收、何时回收」。
3. 这直接支撑总体构想「模型内存成为一等公民」，以及 KT3「文件页直接映射给 NPU」。AICore 进程在前台叠加时如何被治理，是立项后需要自测的关键事实。

### 1.2.3 内核内存管理的上游演进

| 版本 | 关键变化 | 对应 GKI |
|---|---|---|
| 6.1 | MGLRU 多代 LRU | android14-6.1 |
| 6.4 | per-VMA lock 首次合入（仅匿名页） | — |
| 6.6 | 文件缺页、swap 缺页走 VMA 锁（6.5 与 6.6 的分工待核实） | android15-6.6 |
| 6.8 | 匿名 mTHP；DAMOS 自动调参 | — |
| 6.9 | arm64 连续 PTE（contpte） | — |
| 6.12 | mTHP 换出；zram 压缩后端 API | android16-6.12 |
| 6.18 | swap table 第一阶段 | android17-6.18 |
| 未合入 | DAMON 硬件采样访问报告 RFC（2026-09 v2）；AMD IBS pghot v8；virtual swap 提案 | — |

| 机制 | 解决了什么 | 对 Agent + 应用叠加没解决什么 |
|---|---|---|
| per-VMA lock | 多线程缺页不再抢 mmap_lock，缓解启动锁竞争 | 回收侧 rmap 锁（i_mmap_rwsem）争用仍在：Android 重负载下 kswapd 等锁 ≥300ms |
| mTHP / contpte | 一次缺页分配大页，减少缺页与 TLB 缺失 | 手机碎片严重，大页分配失败率高；可执行段大 folio 合入版本待核实 |
| mTHP 换出 / swap table | 大 folio 整块换入换出，降低 swap 元数据与锁开销 | 不提供冷热证据，也不做预取 |
| MGLRU | 更细的页龄；Pixel 6 Pro 启动 -6.60%（LPC 2022） | 多家 Android 厂商未启用；与前后台应用语义脱节，匿名页回收偏弱 |
| DAMON / DAMOS | 区域级访问监控，开销与内存大小无关；可作回收执行入口 | 区域粒度；硬件采样未合入；冷证据仍依赖页表 Accessed 位 |
| Arm SPE | arm_spe_pmu 驱动已在主线与 Android 通用内核 | 主线没有基于 SPE 的冷热识别；手机 SoC 是否开放 SPE 未公开 |
| Android 16KB 页 | 内存压力下应用启动 -3.16%，整机启动 -8% | 内存占用上升；2027-02 起 Play 强制，.so 优化须按 16KB 粒度设计 |

其他平台：iOS 以 Jetsam 杀进程 + 内存压缩器治理，无磁盘交换，单应用上限与 12GB 机型不匹配；OpenHarmony 标准系统有 ESwap（zram 压缩页加密换出到专用分区），华为 2026-04 发布的 HyperSpace Memory 宣称 12GB 达到 16GB 的保活效果（厂商口径，无技术细节）；HarmonyOS NEXT 为鸿蒙微内核，页回收与换出机制没有公开资料。（D2 §3）

**分析：这说明什么。**
1. 上游四年的主线是「降锁、大页、可编程回收」，而不是「按应用语义与硬件证据做冷热识别」。后者在主线仍是 RFC，说明 KT1-b / KT1-c 有空间；也意味着实现要对接 DAMON 的采样通道，不另起框架。
2. 所有机制都以 LRU 和进程为治理单位，KV 与 NPU 缓冲都不在其中。「模型内存一等公民」在上游路线图里没有对应项。
3. Android 16KB 页在 2027-02 前后成为强制生态要求，KT1-a 必须按 16KB 页粒度设计。

**分析：这说明什么。**
1. **带宽追不上模型**：端侧 decode 将长期受带宽限制，省内存就是省带宽。
2. **闪存第一次成为可用的一层**：UFS 5.0 使「热权重常驻 + 冷权重闪存流式」成立，前提是把 4KB 缺页聚合成大块 IO（KT3 的难点）。
3. **三项前提必须先摸底**：手机 SoC 是否开放 SPE（KT1-b / c）、NPU 能否映射文件页（KT3）、手机侧仿真器（S1）都没有公开证据，列为立项第 0 阶段的决策点。
4. **评估平台本身是立项理由**：没有手机侧仿真器与统一能耗口径，云转端与并行化的收益无法在立项前量化。

| 路线 | 输入 | 质量上限 | 覆盖 |
|---|---|---|---|
| SDK 级（游戏集成） | 深度、运动向量、UI 分层 | 高 | 取决于游戏接入 |

| 系统级 · GPU / NPU 软件 | 最终帧或部分元数据 | 待评估 | 对游戏透明；跨机型复用 |

**分析：这说明什么。** 国内头部厂商已把「超帧」做成芯片加内核的卖点，用户价值得到市场验证，但全部是厂商口径，没有可复核的功耗与延迟数据，自测一份对比数据本身就有汇报价值。Pixelworks 退出后，没有自研芯片的机型只能走 GPU / NPU 软件方案，这是系统级软件方案的窗口。桌面的教训是底帧率要够、倍率越高延迟与鬼影越明显（DLSS 4.5 高倍率插帧延迟 68ms，目标降到 120 FPS 后约 45ms；插帧至少增加一个底帧时间）。我们不与自研芯片拼峰值帧率，而是做跨 SoC 的统一算子抽象、UI 遮罩和热稳态预算调度。

## 1.4 洞察小结：三个判断

1. **Agent 的竞争正从「模型能力」转向「执行环境」。** 云端常驻 Agent 只能服务 $100 以上的订阅档；系统级平台已把应用能力函数化，并用 12GB 划定准入线。手机厂商能守住的是端侧执行环境，它的硬约束是内存。（对应：总体构想、KT1–KT3、S1）
2. **基础能力的零件齐了，但没有为「Agent + 应用叠加」整合。** 常驻权重年增 40%–60%，DRAM 年增约 13%；内核在降锁、大页、可编程回收上持续演进，但冷热识别缺少应用语义和硬件证据；推理引擎的模型内存普遍游离在 OS 治理之外。（对应：KT1-a/b/c、KT2、KT3）
3. **图形体验进入神经化窗口，系统层要做 App 做不到的事。** 手机 GPU 已内置神经加速，3DGS 渲染可行，A2UI 进入 Android；但手机系统层在高斯格式、常驻渲染、生成式 UI 上都是空白，业界数据几乎全是厂商口径。（对应：G1–G4）

## 2.2 当代系统与瓶颈

> 平台术语：Android 杀进程靠 lmkd，iOS 靠 Jetsam；Android 匿名页换出用 zram，iOS 用 compressed memory（不落盘）；OpenHarmony 标准系统是 Linux 内核，有 ESwap 机制，HarmonyOS NEXT 是鸿蒙微内核，回收和换出机制没有公开资料。

### 2.2.1 系统内存（对应 KT1）

| 瓶颈 | 当代系统的做法 | 卡在哪 | 量化数据 |
|---|---|---|---|
| **容量被冻结** | 历来靠「加 DRAM」解决 | 加内存的路被价格堵死，回收成了唯一杠杆 | 移动 DRAM 合约价 2026Q1 环比 +58–63%，Q2 接近翻倍（约 $20/GB），3Q26 再涨 8–13%；TrendForce 判断 2027 年不会明显回落 |
| **冷启动慢，瓶颈在内存** | 冷启动的瓶颈过去是 CPU 初始化 | 现在转向文件 I/O 和内存回收 | GB 级应用 86.6% 冷启动超过 1 秒（AppFlow，Pixel 7/8）；可回收文件页常超过 1GB，模型文件页会和应用的 .so 争同一块页缓存 |
| **回收路径的锁** | kswapd 回收共享库页时要做反向映射 | 共享库被几十个进程映射，i_mmap_rwsem 被多条路径争抢 | Android 重负载下 kswapd 等 rmap 锁达 300ms 以上；i_mmap_rwsem 争用使回收效率从 48% 降到 27% |
| **换入既不分冷热也不预取** | zram 按需换入 | 切回前台时大量缺页，解压落在关键路径上 | 对标方案的改进空间为 -22%～-50%（ASAP、Ariadne） |
| **冷热信号不准** | MGLRU 或经典 LRU 扫描页表 | 很多 Android 厂商没开 MGLRU；MGLRU 的冷热模型和前后台应用模型对不上 | 见 LWN 2026-03-05 |

# 第三部分 架构与关键技术

## 3.1 Agent OS

### 3.1.1 关键问题

1. **模型内存游离在系统治理之外**：权重、KV、NPU 缓冲分属不同的记账域，回收看不见、也收不走，只能靠提前杀应用腾空间。
2. **叠加场景下，非模型部分的内存供给不足**：容量被价格冻结，冷启动受 .so 页争用和锁的拖累，切回前台时匿名页换入慢，误杀后台应用。
3. **模型加载与驻留低效**：多份拷贝、长期钉住、IO 打不满；稀疏大模型的专家命中率不稳定。

另外，缺少手机侧的评估手段，以上收益无法在立项前量化，这由支撑能力 S1、S2 解决。

### 3.1.2 总体构想：模型内存成为系统的一等公民

| 属性 | 含义 | 落在哪 |
|---|---|---|
| **统一记账** | 权重映射页、专家缓存、KV 块、NPU 缓冲都计入同一本模型内存账，和应用内存一起参与压力判断 | 共享层：统一内存预算账本 |
| **可回收** | 权重保持为干净的文件页，压力大时零成本丢弃、再从 UFS 读回；专家缓存可收缩；KV 块可压缩、换出、丢弃重算 | KT2、KT3 |
| **可共享** | 同一基座权重按内容在多会话、多 LoRA、CPU 与 NPU 之间只留一份 | KT3 |

非模型部分由 KT1 负责「省内存、提速度」。KT1、KT2、KT3 共用一本预算账本和一个 IO 调度队列，避免预加载和回收互相打架（AppFlow 的消融实验是直接论据）。

### 3.1.5 叠加场景走查：三项技术如何协同

以「刷视频时让 Agent 订明天去上海的高铁并加到日历」为例，五个时刻的分工如下。

| 时刻 | 事件 | 今天的系统 | Agent OS 的做法 |
|---|---|---|---|
| t0 唤起 Agent | 用户在视频应用里说出指令，端侧模型需要载入或唤醒 | 权重拷进私有缓冲并钉住；缺页式读取打不满 UFS，首 token 慢 | **KT3**：页对齐权重经大块顺序预读载入，文件页直接映射给 NPU，不再复制；**KT2-B** 按配额分配 KV 块 |
| t1 Agent 拉起 12306 | Agent 经接口下单，需要拉起 12306 完成支付确认（冷启动） | 共享库 .so 页已被逐出；缺页等 I/O、等 folio 锁和 rmap 锁 | **KT1-a**：关键 .so 页受软保护，缺页走 VMA 锁，回收侧 trylock 不阻塞 |
| t2 内存吃紧 | 模型、视频应用、12306、日历同时在内存里，余量低于水线 | zram 不分冷热地压缩匿名页；仍不够就由 lmkd 杀掉视频应用 | **KT1-c**：只换出三项冷证据一致的后台匿名页；**KT2-A** 专家缓存按预算收缩；模型权重作为干净文件页可零成本丢弃 |
| t3 切回视频 | 订票完成，用户回到视频应用 | 视频应用若被杀则冷启动；若在 zram 中则逐页解压，画面卡顿 | **KT1-b**：切后台时记录的「恢复集」在切回的头几百毫秒批量换入，与模型加载共用 IO 队列 |
| t4 任务结束 | Agent 会话结束 | KV 与 NPU 缓冲继续钉住，直到进程退出 | **KT2-B**：KV 块压缩保留或丢弃，系统提示与工具 schema 前缀留作复用；**KT3** 权重页标为可回收 |

共享底座在其中的作用：**统一记账与预算账本**记录每个时刻各方占用，t2 的回收排序依据它，而不是只看进程 RSS；**冷热模型**在 t1 前后由 SPE 样本建立后台应用的热集合，它既是 t3 预取的恢复集，也是 t2 换出的排除名单；**IO 调度队列**在 t0 模型加载与 t3 换入同时发生时按截止时间排队，前台缺页优先，预读填满剩余带宽。

## KT1-a .so 文件页锁优化

**要解决的问题**：Agent 与应用叠加时，多个进程同时映射并缺页同一批共享库（libc、libart、libhwui、引擎库等）。内存压力下文件页被逐出，冷启动时反复经历缺页、等 I/O、等 rmap 和 LRU 锁。公开的间接证据：GB 级应用 86.6% 冷启动超过 1 秒；kswapd 等 rmap 锁达 300ms 以上。「.so 页被逐出导致冷启动变慢」这一点没有手机侧的专项公开数据，需要自测。

**业界做法与局限**：
- per-VMA lock（6.4 起覆盖匿名页，6.5 起覆盖页缓存命中的文件缺页）：需要 I/O 的文件缺页何时纳入，待核实。
- rmap trylock（Minchan Kim，2022）：有活锁风险，需要节流。
- RWH_RMAP_EXCLUDE（Hygon，未合入）：代价是这些页不可回收。
- arm64 可执行段大 folio（Ryan Roberts、Usama Arif）：服务器上冷缺页降 50%，手机实测缺失。
- Android 16KB 页：内存压力下启动时间均值降 3.16%，代价是内存占用略增。
- AppFlow 选择性预加载：预加载本身会加重内存压力。

**技术难点**

| 难题 | 难在哪 | 怎么破 | 关键突破 |
|---|---|---|---|
| **一、文件缺页与回收去全局锁** | 缺页要拿 folio lock、等 I/O，还可能回退到 mmap_lock；回收做反向映射要拿 i_mmap_rwsem，共享库被几十个进程映射。约束是不能让 .so 页变得不可回收 | 补全 per-VMA lock 对 I/O 型文件缺页的覆盖（确认版本并回移植）；回收侧对多进程映射的热 .so 页走 trylock + 批量跳过，不阻塞 kswapd；评估只读共享库的 i_mmap 遍历能否 RCU 化（需论证） | 共享库页脱离全局锁路径 |
| **二、.so 软保护与回收腾空间的平衡** | 保护多了，匿名页换出（KT1-c）就腾不出空间；AppFlow 显示单独预加载会让冷启动次数增加 30% | 按应用启动画像生成「冷启动关键 .so 页集合」，用软保护（降低回收优先级，不用 mlock）；预算受 memcg 和全局上限双重约束，和 KT1-c 共用一本账 | 有预算的关键页软保护 |
| **三、大 folio 与碎片的权衡** | 大 folio 减少缺页和 TLB 缺失，但要连续物理内存；手机内存碎片严重，读放大还会增加 I/O 和内存占用 | 只对冷启动关键 .so 的热段请求 contpte 对齐的 folio，其余保持小页；分配失败就退回小页 | 热段大页、冷段小页 |

**机制架构**
- 感知 / 建模：缺页 trace、各应用各版本的冷启动 .so 访问画像、rmap 锁等待时间、PSI。
- 决策：关键页集合与预算；回收时的跳过和旋转策略；大 folio 开关。
- 执行：补全 VMA 锁覆盖；rmap trylock 批处理；设置 readahead 阶数；打软保护标志。
- 反馈：冷启动时延、major fault 次数、rmap 锁等待、关键页 refault 率；出现异常自动撤销保护。

**目标与度量**：叠加场景下（Agent 常驻 + 应用冷启动，内存余量 <20%）冷启动 -15%～-30%（依据：AppFlow 组合方案 -40.8%、ASAP -22%，本技术只占其中一部分，故取保守区间）；rmap 锁 P99 等待 <50ms；关键 .so 的 major fault -40% 以上（依据服务器数据 -50% 折减）。

**风险**：没有手机侧基线；内核版本待核实；HarmonyOS NEXT 微内核的对应机制没有公开资料，需要单独做映射；软保护可能被滥用，必须有 memcg 预算。

**交付节奏（建议）**：2027-Q1 叠加场景冷启动与锁等待基线、原型；2027-Q2 锁路径优化和软保护合入内部版本；2027-Q3 随版本商用。

## KT1-b 基于 ARM SPE 的匿名页冷热识别与预取

**要解决的问题**：zram 换入是按需的，不分冷热、也不预取，应用切回前台时大量缺页，解压落在关键路径上。软件冷热信号来自页表 Accessed 位扫描，页级精度和扫描开销互相制约，而且很多 Android 厂商没有开 MGLRU。对标方案的改进空间是 -22%～-50%（ASAP、Ariadne），但它们用的都是软件信号。

**业界做法与局限**：
- SPE 本身：Armv8.2 起的可选特性，记录 PC、数据地址、延迟、data source。局限是可选、异构核上不一定每个核都实现，且固件可以关闭。
- openEuler 的 SPE + DAMON 系列：无性能数据，也未上游。
- DAMON 硬件采样 RFC：尚未合入。
- HeMem / Memtis（PEBS）：阈值方案对写密集负载效果差。
- SPE 过滤扩展（FEAT_SPEv1p4）：合入版本待核实。

**技术难点**

| 难题 | 难在哪 | 怎么破 | 关键突破 |
|---|---|---|---|
| **一、手机上稀疏采样能用且用得起** | SPE 是可选特性，大中小核不一定都实现，固件可能关闭；采样间隔小则中断和写缓冲区耗电，间隔大则漏判热页；没有公开的手机侧数据 | 第 0 阶段逐个 SoC 摸底（`arm_spe_0` 节点、固件开关、哪些核可采样）；只在大核和应用所在核上开采样，按 PSI 和前台状态动态调间隔；用延迟阈值、data source 过滤，只保留访问 DRAM 的样本 | 按压力和场景自适应的稀疏采样 |
| **二、采样证明不了冷** | 没采到不等于没访问；把「没采到」当冷会换出热页，造成 refault 和颠簸 | 三态证据：SPE 命中即标热；冷必须由 Accessed 位为 0 和代龄双重确认；两者都没有的页先算「未知态」，不换出。预取只用热证据，所以这个问题主要压在 KT1-c 上 | SPE 管热、页表管冷 |
| **三、预取什么、何时预取、取多少** | 预取多了反而挤掉别的页，预取晚了又没用；「按 Agent 语义调前后台」不在本立项范围内，只能用通用信号 | 应用切到后台时，把最近窗口的热页集合记为「恢复集」；切回前台的头几百毫秒批量解压换入；预取量受内存余量封顶，命中率低就自动减量 | 以换出前的热集合为目标，按余量封顶 |

**机制架构**
- 感知 / 建模：`arm_spe_pmu` 采样，经地址、延迟、data source 过滤后映射到物理页号，形成每个 memcg 的热页集合和时间戳；页表 Accessed 位和 DAMON 提供冷证据；PSI 和内存余量。
- 决策：预取触发（应用切换、唤起事件）；恢复集的选择；采样间隔和开关策略。
- 执行：批量解压换入 zram 页（可用大 folio 换入）；把恢复集里的页在 LRU 中提前，避免刚换入就被回收。
- 反馈：预取命中率、浪费率、重启时延、采样 CPU 占用和功耗。

**目标与度量**：切回前台时延（匿名页相关部分）-20%～-40%（依据 ASAP -22.2%、Ariadne -50%）；预取命中率 ≥70%；SPE 采样 CPU 占用 ≤1%（目标设定，属于风险项）。

**风险**：**量产手机 SoC 是否放开 SPE 是头号风险**，目前查不到公开资料。备选退路是改用软件信号（DAMON + Accessed 位 + 应用生命周期）驱动同一套预取，但这样和 ASAP、Ariadne 的差异会变小。此外，Android GKI 是否带 `CONFIG_ARM_SPE_PMU` 待核实；HarmonyOS NEXT 没有 Linux perf/SPE 子系统，需要单独适配。

**交付节奏（建议）**：2027-Q1 完成 SoC SPE 可用性摸底，得出采样开销实测（作为能否继续的决策点）；2027-Q2 冷热模型和恢复集预取原型；2027-Q3 合入内部版本。

## KT1-c 基于同一冷热识别的匿名页换出（zram）

**要解决的问题**：DRAM 价格涨了 4 倍，内存压力只能靠回收承担；Android 匿名页回收偏弱、文件页回收过猛。误换出热页会带来 refault 和解压开销；压力顶满时 lmkd 杀进程，冷启动次数和后台存活两头都受损。

**业界做法与局限**：
- zram 的 recompress 与 writeback：触发策略依赖用户态，写回受闪存寿命约束。
- MGLRU：很多厂商没有启用。
- DAMOS pageout：粒度是区域。
- 荣耀 memcg 强制回收：私有方案，无公开细节。
- Ariadne、Chou 等：都用软件热信号。
- 三星 RAM Plus、OpenHarmony ESwap：说明闪存 swap 已经商用，但磨损处理没有公开。

**技术难点**

| 难题 | 难在哪 | 怎么破 | 关键突破 |
|---|---|---|---|
| **一、换出准确率** | 换出一个热页要付出压缩、再解压的代价，还可能触发 lmkd；硬件采样没采到不代表冷 | 换出候选必须同时满足三条：没有 SPE 热证据、Accessed 位为 0、代龄超过阈值；按应用 memcg 设配额，先换出已进后台且冷的应用；每轮换出量由 PSI 反馈闭环控制 | 多证据一致才换出 |
| **二、压缩、CPU 与闪存的预算博弈** | 不可压缩的页占着 DRAM 又压不下去；写回带来闪存写放大和寿命问题 | 按可压缩性分流：可压缩的冷页进 zram（可二次压缩），不可压缩且长期空闲的页才限额写回；按日写入量设上限；和 KT1-a 共用一本账 | 按可压缩性和冷度分流到不同层 |
| **三、与内核既有回收协同** | 回收路径和厂商 hook 复杂，内核的 swap 子系统本身也在重构 | 用 `memory.reclaim` 或 DAMOS 作为执行入口，把冷页清单注入进去，不改核心回收路径；策略放在用户态，参数可调 | 注入冷页清单，不改内核主路径 |

**机制架构**
- 感知 / 建模：和 KT1-b 共用冷热模型；PSI、zram `mm_stat`、各 memcg 的前后台状态。
- 决策：冷候选清单；按应用、按压力的换出配额；zram 与写回的分流阈值。
- 执行：经 `memory.reclaim` / DAMOS 把页换出到 zram；对空闲且不可压缩的页限额写回；与大 folio 对齐。
- 反馈：refault 率、换出后 5 秒内被重新访问的比例、lmkd 杀进程次数、压缩率、CPU 占用、闪存写入量。

**目标与度量**：同等 DRAM 下后台存活应用数 +30%～+80%（依据 AppFlow 组合方案达 1.85 倍，取中低位）；误换出率（换出后 5 秒内 refault）≤10%；叠加场景下 lmkd 杀进程 -30% 以上。

**风险**：误换出导致颠簸，需要保守阈值和熔断机制；闪存寿命；功耗还没实测；swap table、mTHP 换入的版本待核实，基线内核需要锁定。

**交付节奏（建议）**：2027-Q1 与 KT1-b 共用冷热模型原型和换出准确率基线；2027-Q2 闭环配额与分流策略；2027-Q3 合入内部版本。

## KT2-A MoE 专家缓存（建议泛化为稀疏权重分层）

**要解决的问题**：35B 级 MoE 的 Q4 权重约 14–21GB，16GB 机型放不下，只能放在 UFS 上按需换入。iPhone 实测 512 MiB 的 LRU 缓存命中率为 0%，576 MiB 时才到 38.58%；命中率为 0% 时每 token 约 1.1GB IO，解码上限约 5 tokens/s（估算）。命中率直接决定模型能不能用。

**关于是否泛化**：已经出货的系统级端侧模型（Gemini Nano 4）走的是 PLE 稀疏，不是 MoE；MoE（Gemma 4 26B A4B、Qwen3.5-35B-A3B、Meta MobileMoE）正在研究前沿和旗舰档快速推进。判断（中等置信度）：2027 年「稀疏权重」会成为旗舰主流，「MoE 专家流式换入」是旗舰机型的一个选项。**建议把缓存对象抽象为「可分页的稀疏权重单元」**，统一覆盖专家、PLE 表、激活稀疏神经元簇和 Embedding 表。这样不管 2027 年哪条路线胜出，投入都不落空。

**业界做法与局限**：
- 流式与预取：LLM in a flash、EdgeMoE、PowerInfer-2（OnePlus 12 上 47B 模型 11.68 tokens/s）、Pre-gated MoE（ISCA 2024）。
- 替换与降级策略：MoE-Infinity、AdapMoE（ICCAD 2024）、HOBBIT、ProMoE、FlashMoE。
- 手机侧最新进展：EStream、Paging the Experts（均为 2026 年预印本）。
- 共同局限：多数在 GPU、桌面或嵌入式平台上验证，手机侧的绝对 tokens/s 数据很少。

**技术难点**

| 难题 | 难在哪 | 怎么破 | 关键突破 |
|---|---|---|---|
| **一、命中率对容量和负载极敏感** | 小缓存下 LRU 遇到循环式访问会完全失效（0%）；Agent 任务一切换，路由分布就漂移 | 对专家、PLE、神经元簇统一建热度模型；在 LRU、频率、学习型策略之间在线选择；缓存由系统记账 | 按负载在线选策略 |
| **二、预取要在 UFS 带宽内及时到位** | 专家只有 2–3MB，属于随机读；要等前一层门控算完才知道后一层用哪些专家 | 跨层预测（EdgeMoE / ProMoE / AdapMoE 路线）+ 按簇打包的存储布局（行列捆绑）；预取和 KT3 共用 IO 队列 | 预测与布局联合设计，让 IO 变大且可预知 |
| **三、精度与容量的折中** | 低精度替换、减少激活专家都会损失质量 | 未命中时换入低位宽副本作兜底，不阻塞解码；用评估集约束质量门限 | 未命中也不阻塞 |

**机制架构**
- 感知 / 建模：专家访问轨迹（层、专家、时间）；热度与转移概率模型；UFS 带宽和空闲内存。
- 决策：分层放置（DRAM / 压缩区 / UFS）；预取预测；淘汰策略选择；未命中时的降级决策。
- 执行：权重页池（与 KT3 共用映射）；异步预取线程；低位宽副本；NPU 可见的固定 arena。
- 反馈：命中率、预取准确率与提前量、tokens/s、热状态。

**目标与度量**：同等容量下命中率相对 LRU 提升 ≥30%（依据 FlashMoE 最高 +51%）；解码速度 ≥1.5 倍于 mmap 基线（依据 ProMoE 1.34–1.79 倍）。测试条件：旗舰机、UFS 4.x、Q4 量化的 30B 级 A3B 模型、多种 Agent 任务轨迹。

**风险**：MoE 主流度只是中等置信度；论文多为预印本；持续解码会热降频（iPhone 实测出现过停顿）；质量折损需要评估。

**交付节奏（建议）**：2027-Q1 建立手机侧专家访问轨迹和 LRU 基线；2027-Q2 自适应策略加预测预取原型；2027-Q4 稀疏权重分层统一接口落地。

## KT2-B KV Cache 回收与压缩

**要解决的问题**：KV 随上下文线性增长，而且没法从文件重建。Qwen3-4B 在 32K 上下文、fp16 下 KV 为 4.5 GiB，约是 Q4 权重的 1.9 倍（估算）；多个会话时还会线性放大。KV 常驻在被钉住的缓冲里，OS 回收不了。需要说明的是：模型正在走向混合注意力（Qwen3.5 每 token 只要 20 KiB），KV 问题会集中在稠密小模型和长会话上，投入要与模型路线对齐。

**业界做法与局限**：
- 量化：KIVI（ICML 2024，2-bit），在长 Agent 轨迹上的精度还没有充分验证。
- 淘汰：H2O（NeurIPS 2023）、StreamingLLM（ICLR 2024）、SnapKV（NeurIPS 2024），丢 token 可能破坏工具调用需要的精确引用。
- 架构层缩减：Apple 层间共享、混合注意力，由模型决定，OS 无法事后加上。
- 系统层：LLMS 分块压缩与换出、MNN-LLM 溢出到 Flash、KVSwap 磁盘加元数据预载，都受 Flash 带宽墙限制。
- 前缀 KV 复用与持久化：手机端没有找到公开系统。

**技术难点**

| 难题 | 难在哪 | 怎么破 | 关键突破 |
|---|---|---|---|
| **一、KV 不可回收、被钉住** | KV 在 dma-buf / NPU 可见缓冲里，不在 LRU 上 | 把 KV 切成块（参考 LLMS 的 16 token 一块），纳入统一记账；每个块可以压缩、换出，或丢弃后重算 | KV 块成为可回收对象 |
| **二、压缩质量与场景耦合** | 2-bit 量化和淘汰对工具调用、长推理的影响未知 | 按块评估压缩容忍度并分级：关键块保持高精度，系统提示、旧工具输出等低敏感块用低位宽 | 按块差异化压缩 |
| **三、换到闪存要掩盖延迟** | UFS 带宽比 DRAM 低一个数量级 | 只换出长期不被关注的块；用元数据预测提前预载；带宽不够时选择重算；跨会话复用固定前缀（系统提示、工具 schema） | IO 与重算择优，前缀复用 |

**机制架构**
- 感知 / 建模：每个块的注意力得分和访问时间；压缩容忍度；会话优先级；内存压力。
- 决策：对每个块在保留、压缩、换出、丢弃重算四者中选一；判断能否跨会话共享前缀。
- 执行：块池；量化与反量化 kernel；UFS 写出与预载；前缀块的共享映射。
- 反馈：TTFT、解码速度、质量回归（工具调用成功率）、重算比例。

**目标与度量**：32K 场景下 KV 常驻量压缩 ≥2.5 倍（依据 KIVI 2.6 倍、Apple -37.5%）；任务质量回归 ≤1 个百分点；会话切回的 TTFT 相对全量重算降 ≥50%（待实测）。

**风险**：有损压缩在 Agent 轨迹上的质量风险还没收口；模型走向混合注意力后收益会缩小；手机上没有前缀持久化和 KV 换出的实测数据。

**交付节奏（建议）**：2027-Q1 KV 块池与统一记账原型；2027-Q2 分级压缩与前缀复用；2027-Q3 闪存换出与重算择优。

## KT3 模型加载 / 卸载与零拷贝映射

**要解决的问题**：权重在文件、页缓存、框架私有缓冲和 NPU 缓冲之间存在多份拷贝；NPU 路径需要预编译、反量化重排和缓冲注册；大块连续内存分配很慢（8GB CMA 约 6.44 秒，mmap 约 0.56 秒，待核实）。叠加场景下模型会被频繁换入换出，冷加载直接决定首次响应。真实的冷 / 热加载时间没有公开数据。

**业界做法与局限**：
- llama.cpp mmap 与新的加载模式：压力下页被逐出后要重新缺页。
- ExecuTorch 的页对齐数据段与程序 / 数据分离：权重共享还处于 RFC 阶段。
- LiteRT-LM：首次加载需要优化并缓存，没有公开加载时间。
- QNN context binary 与权重共享：绑定单一 SoC，有会话数和权重上限。
- MNN-LLM：把 Embedding 放到 Flash，省约 15% DRAM。
- T-MAN：NPU 上只保留一份权重。
- 鸿蒙 MindSpore Lite / HiAI Foundation：加载机制没有公开资料。

**技术难点**

| 难题 | 难在哪 | 怎么破 | 关键突破 |
|---|---|---|---|
| **一、NPU 路径没法直接 mmap 文件页** | NPU 需要 IOMMU 映射、缓冲注册，往往还要求特定布局、物理连续或长期钉住，而钉住的页回收不了 | 离线把权重转成页对齐的 NPU 友好布局（「模型翻译」）；运行时由内核和驱动把文件页经 dma-buf 暴露给 NPU 的 IOMMU，页可以按需缺页、也可以被回收（与仓库 A16e 的 IOMMU / SVA 研究衔接） | 文件页即 NPU 内存 |
| **二、IO 利用率低** | 缺页是 4KB 级随机请求，打不满 UFS 带宽 | 按层或专家顺序打包，按调度顺序大块预读；和 KT2-A 的预取共用 IO 队列 | 大块顺序读，把 IO 打满 |
| **三、多框架多份权重** | 同一基座被多个 Agent、多个 LoRA、CPU 和 NPU 各存一份 | 以权重内容为键做共享映射，由内存系统统一记账 | 一份权重多方共用 |

**机制架构**
- 感知 / 建模：模型清单和布局元数据；各会话需要的层和专家；UFS 带宽和内存压力。
- 决策：加载顺序和预读窗口；常驻与可回收的划分；卸载时机（直接回收还是保留映射）。
- 执行：页对齐的权重文件格式；文件页到 NPU IOMMU 的映射；批量预读；共享映射。
- 反馈：冷 / 热加载时间、缺页次数与 IO 大小分布、回收后的再缺页率。

**目标与度量**：冷加载达到 UFS 顺序读理论值的 60–70%；NPU 路径额外拷贝为 0 份；加载期间峰值内存降低约一份权重的大小。基线需要自测。

**风险**：NPU 驱动和 IOMMU 能否映射文件页，取决于 SoC 厂商驱动，需要和厂商确认（这是 KT3 的前置风险）；内存压力下缺页式加载可能抖动，需要和 KT1 协同；厂商私有格式会限制通用方案。

**交付节奏（建议）**：2027-Q1 冷 / 热加载基线，与 SoC 厂商确认 IOMMU 映射可行性；2027-Q2 页对齐格式和大块预读；2027-Q3 NPU 零拷贝映射与权重共享。

## S1 Agent 云转端的性能 / 功耗代价与成本收益评估（含风险评估）

**要解决的问题**：要把部分 Agent 步骤从云下沉到端，但「值不值」没有统一口径。云有 token 成本，端有耗电、内存占用、发热和体验风险，各自不可直接比较。估算显示，单次任务的云成本在 1 美分以内，端侧耗电约占 1.5% 电量。所以下沉的收益主要不在单次成本，而在隐私、离线可用、时延确定性，以及规模化后的云账单；代价在耗电、内存和发热（估算，需平台验证）。

**业界做法与局限**：
- 路由类：Hybrid LLM（ICLR 2024）、RouteLLM（ICLR 2025）、HybridFlow（ICML 2026），不考虑端侧能耗。
- 端云投机解码：实验台是 Jetson，不是手机。
- 仿真器：Vidur、LLMServingSim 2.0、GenZ、LLMCompass，都没有手机 SoC 的 profile。
- 真机评测：BYTE 是面向 GUI Agent 的评测，我们只借鉴它的方法。

**决策模型（核心产出）**：对每类任务计算净收益

`NB = ΔCost + λP·ΔPrivacy − λE·ΔEnergy − λM·ΔMem − λT·ΔLatPenalty − λR·ΔRisk`

再加硬约束：体验红线（TTFT、P95 步延迟、前台掉帧、冷启动退化、温度）、隐私等级、质量下限，任一不满足就不下沉。权重 λ 按「成本优先 / 体验优先 / 隐私优先」三档预设，并做灵敏度扫描，输出决策翻转点，例如云价格涨到多少时下沉才划算。

**风险评估（你要求放在这里的三项）**
1. **真机可观测性与体验指标**：采集手段是 Perfetto 电池计数器 + ODPM（有则用），需要隔离供电避免读数失真。指标集是我们自己定义的，不是行业标准，分五类：
   - 响应类：TTFT、time-to-first-action、任务完成时延 P50/P95；
   - 质量类：任务成功率、工具调用正确率；
   - 资源类：每任务 Wh、温度；
   - 干扰类：叠加场景下前台冷启动增量、掉帧增量、被回收进程数；
   - 经济类：每个成功任务的云成本。
2. **标准负载集**：分三层。模型层用 MLPerf Mobile v6.0 的 LLM 子集；Agent 轨迹层回放参数化的多轮工具 trace（轮数、token、前缀复用、工具延迟）；叠加场景层是 Agent 运行的同时拉起 3–5 个典型应用。**这一层也是 KT1、KT2、KT3 的共同基线。**
3. **仿真校准**：分层进行。算子级用微基准标定有效带宽和峰值算力，PowerInfer-2 实测的 CPU 约 43.9 GB/s、NPU 约 56 GB/s 可作量级参照；系统级用标准负载回归；热和 DVFS 用 10 分钟以上的长时序轨迹。验收标准：算子误差 ≤10%、端到端误差 ≤10%、功耗误差 ≤15%（最后一项没有公开先例，是我们的目标假设）。

**技术难点**

| 难题 | 难在哪 | 怎么破 | 关键突破 |
|---|---|---|---|
| **一、统一能耗记账** | ODPM 只在部分机型上有，整机电流难以拆分；云侧能耗是全栈摊销，不含网络 | 端侧按 prefill、decode、空闲、网络分阶段建模；云侧取公开口径作参照并注明不含网络；网络射频能耗单独建模 | 记账单位从整机下沉到「Agent 步骤 × 阶段」 |
| **二、手机仿真没有校准闭环** | 手机有 DVFS、热降频、带宽共享、UFS 抖动，没有公开的校准方法 | 分层校准，每次平台升级都复跑并给出误差报告 | 真机轨迹持续回灌校准，公布误差带 |
| **三、体验风险难量化** | 端侧推理占用内存，会挤压前台应用 | 把模型常驻内存换算成前台冷启动退化和回收次数，和 KT1、KT2、KT3 联动；体验红线作为硬约束而不是加权项 | 红线硬约束 + 决策翻转点 |

**目标与度量**：仿真 TTFT/TPOT 误差 ≤10%，功耗误差 ≤15%；覆盖 ≥6 类典型任务，输出下沉建议和翻转点；每个配置的评估 ≤10 分钟（对标 LLMServingSim 2.0）。

**交付节奏（建议）**：2027-Q1 标准负载集、指标定义和真机基线（KT1–KT3 的前置）；2027-Q2 仿真平台 v1 与校准报告；2027-Q3 云转端决策模型和翻转点报告。

## S2 单个 Agent 内部的并行化方案导出与仿真验证

**要解决的问题**：单个 Agent 串行执行「生成 → 工具 → 生成」，端侧任务时延等于各步之和。decode 受带宽限制，NPU 在验证阶段有超过 70% 的算力闲置（二手数据，待核实）。云上的证据（LLMCompiler 3.7 倍、PASTE -43.5%、Speculative Actions -20%）不能直接外推到端侧。

**技术难点**

| 难题 | 难在哪 | 怎么破 | 关键突破 |
|---|---|---|---|
| **一、手机上哪些工具能安全并行或投机** | 手机工具大多有副作用（发短信、设闹钟、调起应用），要权限和用户确认 | 给工具声明加语义标签（只读 / 幂等 / 可回滚 / 有副作用 / 需确认），只对前三类开放并行和投机；投机结果在确认前隔离，不落地 | 用工具元数据决定能否并行 |
| **二、共享带宽下收益还在不在** | CPU 和 NPU 并用时带宽约 59.6 GB/s，只比 NPU 单用高约 6%；工具、UI 和其他应用也在抢带宽，合批还会增加 KV | 在仿真平台里建带宽争抢模型，扫描「并行度 × 批大小 × 背景流量」，按收益拐点给并行度设上限，并和 KT2-B 的 KV 配额联动 | 带宽感知的并行度上限 |
| **三、自动导出并行方案** | 依赖关系隐含在对话里，规划出错会造成执行错序 | 从历史轨迹抽取依赖图，枚举候选计划，在仿真平台上做时延 / 能耗 / 内存的帕累托筛选，最后固化成策略模板 | 轨迹 → 依赖图 → 仿真 → 模板的闭环 |

**机制架构**
- 感知 / 建模：轨迹依赖图、工具标签库、带宽 / 功耗 / 热模型（复用 S1）。
- 决策：计划生成、仿真筛选、并行度上限。
- 执行：工具并发、投机隔离与回滚、合批与投机解码、CPU / GPU / NPU 流水。
- 反馈：投机命中率、回滚率、仿真偏差。

**目标与度量**：多工具任务时延降 20–40%；投机命中率 ≥50%（参照 Speculative Actions 最高 55%）；时延降低时能耗增量 ≤+10%。

**交付节奏（建议）**：2027-Q2 工具语义标签与依赖图抽取；2027-Q3 带宽争抢模型与并行度上限；2027-Q4 策略模板上线验证。

## G1 3DGS 全链路热稳态能效

**要解决的问题**：3DGS 在手机上有三类代价。一是渲染：量化版 3DGS 稳态 3 FPS、功耗 5.89W。二是体积：PLY 动辄数百 MB，SPZ 约 25MB。三是生成：多视角重建 255 秒，单图前馈的亚秒级只在服务器 GPU 上达到。手机端「采集 / 生成 → 压缩 / 存储 → 渲染」全链路没有任何公开数据。

**技术难点**

| 难题 | 难在哪 | 怎么破 | 关键突破 |
|---|---|---|---|
| **一、热稳态下的渲染能效** | Mobile-GS 冷启动 127 FPS，稳态降到 74 FPS；持续负载下 GPU 会降频，真正能守住的是稳态 | 按视距和贡献度做 LOD，按帧预算裁剪，把温度预算反馈给高斯数量控制；采用免排序渲染，用神经增强弥补半透明伪影 | 用温度预算而不是固定高斯数驱动渲染 |
| **二、端侧生成的耗时和内存** | 重建要 255 秒、峰值内存接近 3GB，还会和前台应用争 GPU 与内存 | 把重建拆成可抢占的阶段（位姿 → 初始化 → 优化）；单图场景用前馈模型代替优化 | 分阶段可抢占 + 前馈初始化 |
| **三、格式和压缩要能在端侧解码** | glTF 基础扩展不含压缩，SPZ 版本间不兼容，MPEG 标准还没发布 | 跟随 glTF + SPZ 标准；并行解码（SPZ 4 用 6 路 ZSTD 流）；加载时流式上传 GPU，避免整体解压后常驻 | 标准容器 + 并行解码 + 流式上传 |

**机制架构**：感知（采集与位姿、场景复杂度、热和电量）→ 决策（预算控制器、生成路径选择、LOD 档位）→ 执行（可抢占重建、SPZ / glTF 封装、并行加载、免排序 / Tiled 渲染）→ 反馈（稳态帧率、功耗、温度遥测）。

**目标与度量**：持续 15–30 分钟稳态 60 FPS 以上；渲染功耗 <1.5W；房间级场景文件 10–25MB；重建峰值内存不超过 3GB；重建时间先在目标 SoC 上建立基线。

**风险**：标准批准状态待核实；Mobile-GS 的功耗口径待核实；杀手级场景还不明确（iOS Spatial Scenes 是否基于高斯表示，没有公开资料）。

**交付节奏（建议）**：2027-Q1 全链路基线；2027-Q2 温度预算渲染与流式加载；2027-Q4 端侧单图生成原型。

## G2 系统级常驻低功耗 AI 萌宠

**要解决的问题**：手机上没有系统级的常驻 AI 宠物，七家厂商都没有。宠物类体验目前都由 App 提供，受后台限制、回收和功耗约束。陪伴需求是真实的（2026 年上半年浪漫类陪伴 App 内购 1.628 亿美元），但收入集中在头部，留存偏低（AI 类 App 年留存 21.1%）。**立项落点在「只有系统层才做得好的常驻低功耗渲染」；「能提升日活和使用时长」是要用灰度实验验证的假设。**

**技术难点**

| 难题 | 难在哪 | 怎么破 | 关键突破 |
|---|---|---|---|
| **一、常驻渲染的功耗预算** | 用户愿意一直开着的前提是几乎不耗电，而连续动画会持续唤醒 GPU 和显示管线 | 分三级渲染：静止（事件驱动，没有事件就不提交帧）、微动（低帧率 + 预制片段）、互动（满帧 + 模型驱动）；渲染放在系统合成层，随息屏、遮挡、温度自动降级 | 空闲时零帧 |
| **二、动作的混合式生成** | 用大模型实时驱动动作不可持续，纯预制动画又没有个性 | 大模型按需生成动作脚本和状态机参数，由本地状态机执行；嘴型等高频动作用小模型驱动（参考 TaoAvatar） | 低频交给大模型，高频交给小模型和状态机 |
| **三、性格与记忆的端侧持久化和隐私** | 记忆越多越个性化，也越敏感 | 记忆分三层（短期对话、事件摘要、长期偏好），参考 Mem0 的抽取—召回；存储在系统受保护目录，云端只在用户授权时使用 | 只召回相关的少量条目 |

**机制架构**：感知（系统事件、语音、记忆库、渲染负载）→ 决策（行为决策器、渲染分级策略）→ 执行（状态机运行时、合成层常驻渲染、音频驱动）→ 反馈（功耗和帧率监测、用户互动与关闭行为）。

**目标与度量**：静止态额外功耗在测量误差范围内；常驻内存 100–150MB（估算，不含本地大模型）；对前台应用冷启动没有可测劣化。基线测法：同型号两台手机，一台开宠物、一台关闭，亮屏和息屏各测 1 小时电量差。

**风险**：留存假设没有证据；内容安全和未成年人保护（Grok Companions 有前车之鉴）；情感依赖带来的监管和舆论风险；常驻萌宠的内存属于 KT1 治理的负载，需要设预算上限。

**交付节奏（建议）**：2027-Q1 常驻功耗与内存基线；2027-Q2 分级渲染与状态机运行时；2027-Q3 灰度实验验证留存假设。

## G3 神经超分与插帧（系统级为主）

**要解决的问题**：重度手游和光追游戏在持续负载下受功耗和温度限制；120Hz 每帧只有 8.3ms，而 A19 上 MetalFX 插帧实测约 18ms（非官方），持续运行后升到约 30ms。厂商宣称的省电数字（Arm 最多省 50% GPU 负载、Qualcomm 省电最高 40%）都没有独立实测。

**系统级与 SDK 级**：系统级对游戏透明，覆盖面广，但只能拿到最终帧，UI 和 HUD 容易产生鬼影；SDK 级能拿到深度和运动向量，画质上限高，但每个游戏都要集成。**建议以系统级为主战场（我们能掌控），SDK 级跟随 Khronos 和各厂商的演进。**

**技术难点**

| 难题 | 难在哪 | 怎么破 | 关键突破 |
|---|---|---|---|
| **一、在帧预算内完成推理** | 插帧实测 11–30ms，推理和渲染共享 GPU，持续运行后会降频 | 有硬件的平台把网络放进 GPU 内联神经加速器（INT8 / INT16）；没有硬件的平台用更小的模型或半分辨率光流；调度器按帧预算动态启停插帧 | 按帧预算动态启停插帧 |
| **二、系统级方案输入信息不足** | 拿不到深度和运动向量，UI 会被一起插值 | 在合成器一侧估计光流；用 UI 层检测（固定屏幕区域、合成层）做遮罩；SDK 级作为高质量路径补充运动向量 | 系统光流 + UI 遮罩 |
| **三、加速器碎片化** | Apple、Arm、Qualcomm、Samsung 各一套，Vulkan ML 仍是厂商扩展 | 在系统图形栈里做后端抽象层，向上统一提供超分、插帧、降噪接口，向下适配 tensor / data graph 路径 | 统一算子抽象层 |

**机制架构**：感知（帧时间、GPU 频率和温度、游戏与 UI 层识别、硬件能力查询）→ 决策（帧预算调度、系统级或 SDK 级路径选择、模型档位）→ 执行（神经超分、插帧、降噪、后端抽象层）→ 反馈（帧率与抖动、功耗温度、伪影检测）。

**目标与度量**：重度手游 30 分钟、同画质下功耗降 20–40%；插帧 <4ms（参照 NSS 约 4ms）；1% Low 帧率提升；UI 鬼影率下降（指标待定义）。

**风险**：所有省电数字都是厂商声称；Qualcomm Neural Fusion 具体在哪些芯片上、A20 Pro 的 GPU 是否保留神经加速器，均待核实；国内厂商方案没有公开资料；插帧增加的输入延迟没有手机端数据。

**交付节奏（建议）**：2027-Q1 自有平台功耗与插帧耗时基线；2027-Q2 后端抽象层与帧预算调度；2027-Q3 系统级光流 + UI 遮罩方案上线。

## G4 生成式 UI 的流式、安全、原生一致渲染

**要解决的问题**：模型生成界面已经出现在云端对话产品里（Gemini 动态视图、ChatGPT / Claude 的 MCP Apps），但手机系统层还没有统一的渲染方案。界面描述动辄数千 token，不能边生成边渲染的话，用户等待不可接受；iframe 路线需要常驻 WebView，内存和启动代价都大。

**路线选择**：以声明式 JSON + 组件目录为主（对应 A2UI 的设计取向），受限 WebView 兜底（兼容 MCP Apps）。这样既能对接云端 Agent 的两大开放协议，又不用常驻 WebView。

**技术难点**

| 难题 | 难在哪 | 怎么破 | 关键突破 |
|---|---|---|---|
| **一、流式增量渲染不卡顿** | 组件树持续到达，每次都可能触发布局和重绘；首个元素要尽早出现，已显示的内容又不能反复跳动 | 对组件流做增量差分，只更新变化的节点；布局计算移出渲染线程，按帧预算合批提交；约定生成顺序，可见内容优先 | 按帧预算合批的增量提交 |
| **二、沙箱隔离与端侧资源的平衡** | iframe 隔离强但 WebView 重；纯声明式轻，但表达力受限于组件目录 | 默认走声明式；表达力不够时降级到受限 WebView，按需创建、用完回收；权限逐项声明、逐项授权 | 声明式为主、WebView 兜底 |
| **三、生成物和原生体验一致** | 字体、间距、深色模式、无障碍容易和系统不一致 | 用系统设计系统构建组件目录，模型只能引用目录内的组件和设计令牌；校验层拒绝或修复非法节点 | 用设计令牌约束组件目录 |

**机制架构**：感知（组件目录与设备能力、协议校验）→ 决策（渲染路径、帧预算策略、权限判定）→ 执行（流式解析器、增量渲染、组件库、受限 WebView 容器）→ 反馈（交互回传给模型、首帧与掉帧监测）。

**目标与度量**：首个可见元素尽早出现（方向是首 token 到达后一个渲染帧之内上屏）；流式生成 10 秒以上不掉帧；声明式路径的内存增量明显低于 WebView 路径；越权用例 100% 拦截。需要先用两条路径各做一版原型，测完再定稿。

**风险**：A2UI 还在公开预览期，协议会变；Apple 和鸿蒙没有公开协议；按定位，界面只用于信息展示和轻交互，不用于控制其他应用（不做 GUI Agent）。

**交付节奏（建议）**：2027-Q1 两条路径的原型与测量；2027-Q2 组件目录与流式增量渲染；2027-Q3 协议对接与安全校验。

**云端成本**：一个 10 步任务的云成本约 $0.007，按 1 亿日活、每人每天 5 次估算，规模化后约 $12.8 亿/年；每把 10% 的步骤稳定下沉到端侧，约对应 $1.3 亿/年量级的云端支出（估算，取决于任务结构与价格）。S1 输出每类任务的翻转点，避免盲目下沉。

**战略价值**：四家系统级平台都没有公开模型内存治理机制，率先给出「模型内存一等公民」的量化指标，可以占据端侧执行环境的话语权；图形线的三项系统级体验（常驻萌宠、对游戏透明的神经后处理、原生一致的生成式 UI）是 App 无法复制的差异。

2. **人力与预算**：按 12 项关键技术配置，待立项组填写。
3. **外部协作**：与 SoC 厂商建立联合验证，覆盖 SPE 开放与采样开销、NPU 驱动与 IOMMU 文件页映射，2027-Q1 内给出结论。
4. **测量环境与数据**：真机测试设备与隔离供电的功耗测量环境；采购分机型内存分布等付费市场数据（Counterpoint / IDC）。
5. **决策机制**：2027-Q1 末召开决策评审，基于真机基线与两项前置结论，确认各技术的承诺目标与后续投入。

## 附：跨技术的共同前置与风险

| 项 | 内容 | 处理方式 |
|---|---|---|
| **真机基线** | 几乎所有目标都缺手机侧公开基线 | 放进 S1 的风险评估，作为 2027-Q1 的共同前置交付 |
