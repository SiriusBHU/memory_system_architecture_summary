## §0 摘要

1. **Android 17 已把「按进程 memcg 限额」做成平台默认。** Memory Limiter 对 UID≥10000 的应用进程设 `memory.high` 和 `memory.swap.max`，按可见 / 不可见两档、按整机 RAM 查表（16GB 机型：可见 10240MiB、不可见 5120MiB、swap 5120MiB）；超限先节流、压入 zRAM，最后才杀 [A1][A2]。这是 MM-1「会话级 memcg」最强的产业先例。
2. **但限额口径只有「匿名页 + swap」，模型内存可以绕过它。** 官方没有说 dma-buf、GPU 内存是否计入 [A1][A2]。推理运行时把权重和 KV 放进 dma-buf、GPU 或 NPU 缓冲，就同时绕开了限额和 LMKD 的归属。判断：这是 Agent 时代内存记账的最大盲区。
3. **dma-buf 记账的上游路线在 2026 年分叉，没有收敛。** sysfs 统计在 2026-01 提出删除（Android 已迁到 BPF iterator）[A3]；memcg 计费在 2026-05 才出 RFC [A4]，维护者 König 指出「按 PID 计费对中心化分配器不成立」——而共享模型服务恰恰就是中心化分配器；dmem 控制器已合入，但它的前提是独立的设备内存区域，在 UMA 手机上基本不成立 [A5]。
4. **共享模型服务的内存归属，三个平台都没有公开说明。** AICore、Apple Foundation Models 守护进程都查不到官方口径 [A11]。mzCache（MobiCom 2026）指出 OS 的低内存杀手倾向于先杀大的 LLM 进程 [A11]——如果不做归属，共享服务会成为头号被杀对象，杀掉它又会让所有客户端同时失败。
5. **「用户注意力」在工业界只做到「可见 / 前台」。** Android 17 按可见性分档，荣耀回收时跳过前台应用，ChromeOS 按优先级仲裁 [A2][A8][A10]。前台以外的信号（亮屏、用户正在等 Agent 结果）和手机上的 `memory.min/low` 保护契约，都没有找到公开实现。所以「QoS 不跟进程身份走」已经不是差异点，差异点在保护侧和新信号。
6. **有损驱逐在多轮场景下系统性失效。** SCBench 报告 StreamingLLM、SnapKV 在多轮后续问题上接近 0 分 [B6]，KVzip 同向 [B7]。Agent 是典型的多轮负载。这是 MM-4「KV 驱逐经济学」最强的反方证据：回收必须以可恢复为第一约束。
7. **跨租户前缀共享的侧信道是已发表的真实攻击。** PromptPeek（NDSS 2025）通过 TTFT 判断缓存命中，逐 token 重构他人 prompt [B3]；多家云 API 被审计出全局共享缓存 [B4]。判断：端侧「系统提示词 KV」可以跨应用共享，含用户或应用私有内容的前缀必须按信任域分区。
8. **混合 / 线性注意力只解决了一半问题。** KV 体积在缩小（Qwen3.5-35B-A3B 只有 10/40 层是全注意力），但循环状态只能精确匹配、不能部分前缀命中 [B8]。判断：MM-4 的管理对象应从「KV 块」抽象为「会话状态单元」，由模型声明尺寸、可切分性和重算成本。
9. **四种驱逐去向在量级上有清晰的层次，但集合不完备。** 估算：8K 上下文的 4B 稠密模型 KV 约 1.18GB，换出到 UFS 恢复约 0.4–1.2 秒，重算约 8–16 秒，换出快 7–40 倍；上云传 KV 在常见上行带宽下要 45 秒以上，只能「传文本、云端重算」。建议补上「就地降精度」和「直接丢弃」两档，形成有序决策树。
10. **立场结论**：
    - 支持：MM-2；MM-6 的权重分页部分；
    - 方向支持、新颖性需修订：MM-3；
    - 需修订：MM-1（会话做归属标签，补 dma-buf 归属规则）、MM-4（驱逐改回收，对象改为会话状态单元）、MM-5（降优先级并泛化为稀疏权重分层）、MM-7（扩成六档有序决策树）；
    - 证据不足：MM-6 的 LoRA 热插拔部分。

## §3 逐问题分析

### Q1 移动端内存管理现状

**Android：从「杀」转向「限 + 压」。**

- LMKD 仍是低内存终止的主体，Android 11 起由 PSI 触发 [A17]。
- 2026 年的新事实是 Android 17 的 Memory Limiter [A1][A2]：
  - system_server 里的服务与 Activity Manager 联动，按进程可见性切换 `memory.high`，同时用 `memory.swap.max` 封顶 zRAM 占用；
  - 超限的第一反应是节流与回收，只有 swap 耗尽且继续增长、出现分配失败时才终止；
  - OEM 通过 XML 配置按 MemTotal 区间选档；应用可以声明更紧的预算，但不能超过平台限额；开发者运行时没有 API 查询当前限额。
- 判断：平台已经愿意把 memcg 的 `high` 和 `swap.max` 当作每进程配额接口，并与 AMS 生命周期、冻结联动。这对 MM-1 是强支持；不足在于粒度是进程而不是会话，口径不含 dma-buf / GPU。

**MGLRU 仍在争论。** LSFMM+BPF 2026 有三场会议围绕 MGLRU，只达成「拆文件、定评测负载、找共性」的四步计划，没有回应 Android 提出的诉求（代数语义、热冷应用语义、回收上限 hook）[A8][A9]。荣耀在约 7000 万台设备上使用 MGLRU，靠 hook 和 memcg 强制回收绕开语义缺口 [A9]。判断：我方方案不应绑定 MGLRU 页龄，应绑定 memcg 粒度的应用 / 会话语义。

**16KB 页进入强制期。** Play 要求 2027-02-01 起，面向 Android 15+ 的 64 位应用更新必须支持 16KB 页 [A16]。Google 自测启动更快、功耗更低，但平均略多占内存，自带分配器的应用会放大 RSS、恶化 zRAM 压缩率。对 Agent 场景的含义：推理运行时、自带 mmap 的权重布局、KV arena 的对齐假设都要复查。

**iOS Jetsam。** 机制是「每进程静态上限 + 优先级带」，与 Android 17 的「按整机 RAM 与可见性分档」同构。2026 年的新证据只有开发者论坛的实测：12GB iPhone 上单进程上限约 6144MB，WebContent 进程在 2048MB 被杀，且 `increased-memory-limit` 不适用于 WebKit [A25]（D 级）。Apple 没有公开 iOS 26 的 Jetsam 变更。

**HarmonyOS。** 公开面是「应用自愿释放」：`onMemoryLevel` 三档回调、Purgeable Memory C API（API 10 起）[A27][A28]。HarmonyOS NEXT 的页回收、换出机制没有公开资料。判断：鸿蒙的合作式路线与 Android 17 的强制式路线相反，AgentOS 可能需要「合作式 + 强制式」双形态。

**dma-buf 与 GPU 记账的上游状态。**

| 方向 | 状态 | 要点 | 证据 |
|---|---|---|---|
| sysfs 统计 | 2026-01 提出删除 | Android 已迁 BPF iterator；合入版本待核实 | [A3] |
| memcg 计费 | RFC（2026-05） | 计到客户端 cgroup；LSM 钩子授权跨 cgroup 计费；König 指出按 PID 对中心化分配器不成立，作者回复可改传 cgroup fd | [A4][A29] |
| dmem 控制器 | 已合入（6.14 周期，待核实） | `dmem.min/low/max/current`，只有 DRM 驱动接入 | [A5][A30] |
| dmem + CMA 堆 | v2（2026-02） | 按每个后备区域设限 | [A6] |
| dmem 双计费到 memcg | v2（2026-05） | 设备内存同时计入 memcg | [A7] |
| GPU 内存 tracepoint | 已在 Android common 内核 | 依赖厂商驱动上报 | [A32] |

**dmem 在 UMA 手机上的适用性（判断）。** dmem 的前提是一块可枚举、可独占的设备内存区域（独显 VRAM、CMA 区）。手机的 GPU、ISP、NPU 与 CPU 共享 LPDDR，设备缓冲大多来自 system heap 的普通页，没有独立区域可限额。所以在手机上，dmem 只对 CMA 或预留区有意义，system heap 的计量仍要靠 memcg。但「dmem 双计费到 memcg」说明社区在认真处理「区域配额 + memcg 账本」两层并存，这对 MM-2 有利。

**共享模型服务的记账归属（J2）。** 见 §6。

### Q2 KV cache 管理的系统化程度

**块化。** vAttention 保持虚拟地址连续，借 CUDA 虚拟内存 API 把虚拟分配与物理分配分开，解码吞吐最高为 vLLM 的 1.99 倍 [B1]。它和 PagedAttention 的真正分歧是「谁负责映射」：前者把映射交给 OS / 驱动，这最契合 MM-4 的「KV 就是一块按需缺页的匿名内存」。但手机 GPU 驱动是否暴露等价接口没有公开资料；NPU 路径的 KV 缓冲在图编译时定形，动态扩张最难。判断：手机是单用户、少会话，块化消除碎片的价值低于「分块换出」（LLMS、MNN-LLM 的用法）。

**共享与侧信道（J2）。**

- PromptPeek（NDSS 2025）：在 SGLang、vLLM 等多租户引擎上，通过 TTFT 判断缓存命中，逐 token 重构他人 prompt [B3]。
- Early Bird（arXiv 2409.20002）：黑盒测试中多家商业 API 显示暴露；缓解办法是只以不小于 k token 的粒度共享前缀 [B2]。
- 审计研究发现多家 API 存在跨用户全局共享缓存 [B4]。
- CacheSolidarity（2026-03）把防护分为全隔离、时序混淆等几类，主张只在存在可利用泄漏时才隔离 [B5]。

按租户分区能消除信号，同时也消除共享收益，这是显式的「隐私与命中率」权衡。

**压缩与驱逐。** 架构级压缩已经出货：Apple 端侧模型 KV 内存降 37.5%，Gemma 3 用 5:1 的局部 / 全局交错，Qwen3.5-35B-A3B 只有 10/40 层是全注意力 [B33][M3]。这些由模型作者决定，OS 只能适配。驱逐类方法的问题在多轮：SCBench 发现重要的 KV 因查询而异，方法只在第一次查询上表现好 [B6]。判断：Agent 负载（多轮 + 工具结果反复被引用）正好是 SCBench 失效的场景，有损丢弃只适合「已知不会再被引用的片段」，比如已完成工具调用的原始输出。

**卸载。** 云侧（CachedAttention、HCache、Mooncake）都靠 IO 与计算重叠 [B11][B12][B15]。端侧最直接的证据是 KVSwap：介质越慢，预测预载越关键（NVMe 1.8 倍、eMMC 4.1 倍）[B9]；UFS 4.x 介于两者之间，具体数字未知。写入寿命：本文估算单会话每小时换出 1GB、每天 8 小时，三年约 2.9TB，相对数百 TBW 占比很小，只在极端高频场景需要关注（D 级）。

**混合 / 线性注意力对 KV 优先级的冲击（反方）。** 混合模型把 KV 的线性增长换成「固定大小状态 + 少量全注意力层」。两个后果：

1. KV 体积下降，MM-4 的紧迫度降低（支持反方）；
2. 循环状态就地更新，只能精确匹配、不能部分前缀命中；Marconi 用「复用概率 × 节省算力 ÷ 占用」做准入与淘汰，token 命中率最高提升 34.4 倍 [B8]。

判断：反方只成立一半。KV 的体积问题被架构吃掉一部分，但「状态的保存、恢复与淘汰」变得更难，OS 面对的对象从「可切块的张量」变成「不可切分的状态快照」。接口应对状态单元的元数据开放，不要为稠密 GQA 的 KV 布局做过度设计。

### Q3 MoE 内存优化

**命中率的根本问题。** 服务器和大 batch 下，预测式预取有效，因为一个 batch 里多个 token 的专家并集大、复用高。手机上 batch=1，decode 每步只激活 8/256 个专家，路由几乎没有时间局部性，所以容量不足时 LRU 命中率会掉到 0 [B23]。512MiB 到 576MiB 之间命中率从 0% 跳到 38.58%，说明命中率不是平滑函数，而是对工作集边界敏感。判断：缓存策略不能只调参，要先按「层内 top-k 工作集」保证最小驻留。

**出货状态决定优先级。** 已出货的系统级模型走的是 PLE 稀疏，而不是 MoE；Gemma 4 26B A4B 的 Q4_0 权重约 14.4GB，超出多数手机预算；Meta MobileMoE 是总参 1.3–5.3B 的小 MoE，整体常驻即可 [M3]。判断：端侧 MoE 的可行形态是「总参数小的小 MoE」，专家换入需求弱；「大 MoE 流式换入」是极限场景，命中率和热降频都对它不利。EStream 的收益主要在 prefill，decode 阶段的数据缺失 [B22]。

**这说明什么。** MM-5 应下调为「旗舰档可选策略」，并泛化为「稀疏权重分层」，统一覆盖 PLE、专家、神经元簇。

### Q4 权重分页与端侧推理

- **瓶颈在 IOPS，不在带宽。** 4KB 随机读约 0.76–1.08GB/s，512KB 块约 3.5GB/s，相差 3–4 倍 [B18]；UFS 命令队列通常只有 32 项 [B17]。所以「常驻集远小于模型」路线的后续工作集中在改善闪存布局（Neuralink 把共激活神经元相邻存放），而不是提升带宽。
- **激活稀疏对计算友好，对闪存分页不一定友好。** SwiGLU 天然稀疏度低；TEAL 免训练做到 40%–50% 稀疏，但稀疏模式是动态按 token 的，对「按神经元行 / 列读闪存」意味着更碎的访问 [B20]。两者结合没有手机数据。
- **Gemma 3n PLE 是唯一的量产先例。** PLE 的访问是「按 token 查表」，顺序性高、可预测，不同于 MoE 的随机路由 [B21]。判断：这解释了为什么量产的是 PLE 而不是专家换入——**访问模式决定可分页性**。
- **mmap 与 direct IO**：缺页走页缓存，4KB 粒度，预读不一定对齐；direct IO 可以控制块大小和队列深度。手机上两者的对比实测没有找到。
- **LoRA 热插拔（J6 内存侧）**：适配器本身很小，热插拔的内存成本是「适配器常驻 + 切换时的页换入」。若底座权重以 mmap 分页，适配器与底座竞争同一页缓存，切换时可能驱逐底座热页。EdgeLoRA 用适配器缓存 + 预分配内存池，在 Jetson 上吞吐最高 4 倍，但没有切换延迟数据，也没有手机数据 [B26]。判断：适配器页应 pin 住，按「活跃适配器集」限额，与底座记在同一个账下。这一判断缺实测，置信度低。

|---|---|---|---|---|
| Meta TMO / Senpai / oomd | 无硬保护，以 PSI 压力为目标 | 全机群 | `memory.reclaim` 写入 | [A18][A19] A |
| systemd-oomd | 按 `memory.low` 语义选杀 | 用户会话 | 杀 cgroup | [A20][A33] C |

| Android 17 Memory Limiter | 天花板（`high`、`swap.max`），无地板 | 可见 vs 不可见进程 | 节流 → 压 zRAM → 杀 | [A2] A |

**Android 是否按应用建 memcg**：是。LMKD 自 Android 11 起要求 `CONFIG_MEMCG` [A17]；Android 17 对每个应用进程设 `memory.high` 和 `memory.swap.max` [A2]；荣耀用 memcg 强制回收非前台应用的匿名页 [A8]。但**没有任何一家在手机上公开使用 `memory.min/low` 做「前台 / 后台」保护契约**，保护侧的先例只在桌面（uresourced）和 VM 气球（ChromeOS）。

**用户注意力。** 学术工作有 Acclaim（前台感知驱逐）、PMR（并行回收）、mzCache（LLM 进程在后台空闲时被杀的问题）、LLMaaS（把 LLM 上下文内存与应用内存分开管理）[A11][A21][A22][A34]。前台以外的信号——亮屏、用户正等待 Agent 结果、Agent 任务的意图级别——没有找到公开的系统实现或论文。

**这说明什么。** 工业界已经把 memcg 当作每进程配额接口，但只实现了「天花板 + 可见性」，没有「地板 + 注意力」。保护侧是空白，也是最可能的差异化落点。但要承认：Google 选择按整机 RAM 查表，是有意追求简单和确定性。我方的保护契约需要证明，它带来的收益值得引入更难调试的非确定性。

### Q6 NPU 内存抽象

- **Linux accel**：2026 年继续增加驱动（NXP Neutron，用户态仍闭源）[A12]；v7.1 周期出现 amdxdna 的单 BO 内存用量查询、dma-buf 撤销（revoke）机制（二手摘要，待核实）[A13]。判断：单 BO 查询是 NPU 记账「可见」的第一个上游原语，dma-buf revoke 可能是「可回收」的上游原语。
- **手机 NPU 不走 accel**：Qualcomm 走 FastRPC 内存映射 ioctl，计算上下文绑定到 SMMU [A35]；MediaTek 有自有的缓冲分配器 `libneuron_buffer_allocator.so` [A36]，是否接受 dma-buf fd 没有官方文档；Apple ANE 的内存归属没有资料。
- **标准化**：跨厂商 NPU 内存抽象没有收敛迹象。
- **隔离研究**：sNPU（ISCA 2024）扩展 TEE 到 NPU，隔离 scratchpad 与 NoC [A14]；TZ-LLM 在 TrustZone 下分时使用 NPU，世界切换约 32ms [A15]。针对手机 NPU 共享内存的侧信道专项论文没有找到。

**这说明什么。** NPU 内存的三个最小需求——可见（谁占多少）、可归属（计到哪个 cgroup）、可回收（不杀持有者也能收回）——在 Linux 通用栈里只有「可见」的雏形，后两者没有。手机 NPU 驱动又多为闭源，我方能直接改的空间很小。

### Q7 四种驱逐去向的成本模型

**符号**：被回收的会话状态大小 S（= 每 token 字节 b × 上下文长度 L），再次被需要的概率 p，恢复时延 T，能耗 E，质量损失 Q，隐私风险 R。

| 去向 | 时延 | 能耗 | 质量 | 隐私 | 已发表数据 |
|---|---|---|---|---|---|
| 换出（UFS / zram） | T ≈ S / B_read + t_fault | S ×（e_w + e_r） | 无损 | 低 | CachedAttention、HCache（服务器）；KVSwap（NVMe / eMMC） |
| 重算 | T ≈ L / v_prefill | L × e_token | 无损（同权重同精度） | 低 | HCache：隐状态恢复较 token 重算最多快 5.73 倍 |
| 上云 | T ≈ S_wire / B_up + T_cloud + RTT | 射频发送能耗 | 取决于云端模型 | 高 | CacheGen：带宽过低时退回发文本让对端重算 |
| 摘要入库 | T ≈ 摘要长度 / v_decode | 一次 decode | **有损**，无量化数据 | 取决于记忆授权 | 无 |

**数值估算**（估算，C / D 级）：取 4B 稠密 GQA 模型、fp16 KV、L = 8K：

- S ≈ 1.18GB。
- 换出：大块顺序读约 3GB/s 时约 0.4 秒；退化到 4KB 随机读约 1GB/s 时约 1.2 秒。KV 可以按层、按块连续布局，应落在较快一端。
- 重算：假设手机 prefill 500–1000 tokens/s，需 8–16 秒。注意：C1 的调研发现，2026 年的预印本对「NPU 做 prefill 是否比 CPU 快」结论相反，这个假设值的不确定性很大。
- 比值：换出比重算快约 7–40 倍。结论的稳健性来自量级差，而不是具体数字。
- 上云：KV 按 CacheGen 压缩后约 0.27–0.34GB，在 50Mbps 上行下需 45–55 秒；只传 8K token 文本约 30KB，可以忽略。所以上云只能「传文本、云端重算」。
- 摘要入库：8K token 压成 300 token 摘要，按 20–30 tokens/s 的 decode 速度需 10–15 秒，还丢失细节。

**量级层次**：换出（秒内）< 重算（10 秒级）≈ 摘要入库（10 秒级，附带质量损失）< 上云（含网络与隐私成本）。

**「compute or load」不是二选一。** HCache 按计算与 IO 的相对速度混合两者 [B12]；Cake 从序列头开始算、从序列尾开始加载，两路在中间相遇，平均 TTFT 降 2.6 倍 [B14]。手机的差别是 UMA：计算和 IO 共用同一 DRAM 带宽，并行时会互相争用。

**四种去向不完备**，建议：

1. **增加「就地降精度」**（fp16 → int8 → int4）：没有 IO，代价最低，应放在决策树最前面。KIVI 2-bit 峰值内存降 2.6 倍 [B16]；Apple 端侧模型 KV 已默认 8-bit。
2. **增加「直接丢弃」**：只用于已知无用的状态（已结束子任务的中间推理），因为有损驱逐多轮失效 [B6]。
3. **重算分两个子类**：从原始 token 重算、从隐状态恢复（HCache）。
4. **摘要入库不是 KV 的去向，而是形态转换**：输出是文本，下次使用要重新 prefill，实际等于「丢弃 KV + 保存摘要文本」。

**决策规则草案（有序）**：

1. p 低、属于可丢弃类、无敏感性 → **丢弃**（保留元数据）。
2. 质量余量允许 → **就地降精度**。
3. T_swap < T_re，且写寿命、热状态允许 → **换出到 UFS**，写入时按 ≥512KB 块对齐。
4. 换出被禁止，或闪存不可用 → **重算**；只在时间窗足够长或用户在等待时触发。
5. 重算时间超过用户时延 SLO，且数据敏感度标签允许出设备 → **上云，只传文本**。
6. 上下文超过窗口，且换出、重算都保不住细节 → **摘要入库**，写入记忆框架时附来源与质量等级（J1）。

输入里的 p 和时间窗可以借助 Agent 调度器已知的信息（下一步要调用的工具、是否在等用户）。MemDecay 的区域标签 [B28] 是目前最接近的信号来源。

**与 2027 立项的关系。** 立项（2026-11-03）的决定是「zram 只管应用和 Agent 的非模型匿名页，模型内存不换出」。这里的「换出」是把会话状态单元写成 UFS 上的文件，不走 zram，两者不矛盾。但成本模型显示换出比重算快一个数量级，建议在立项材料里把「模型状态落闪存」明确列为模型内存域的回收手段，而不是笼统地写「模型内存不换出」。

### Q8 记账可见性缺口

**可见** = 能观测总量与持有者；**可归属** = 能稳定计到某个应用或会话；**可回收** = 内存压力下不杀持有者也能收回。✓ 有公开依据；△ 部分或有条件成立；✗ 没有；？ 未找到公开资料。

| 内存类型 | Android 可见 | Android 可归属 | Android 可回收 | iOS | HarmonyOS | 控制方 |
|---|---|---|---|---|---|---|

**关键缺口（判断）**：

1. **dma-buf、GPU、NPU 内存在 Android 17 的限额之外。** 这是 Agent / 模型内存最大的记账盲区。
2. **「可回收」缺口比「可见」缺口更深。** 设备缓冲被持有时只能杀持有者。所以统一记账之外，还需要「可撤销 / 可迁移」原语；MM-7 的回收去向要依赖它，而上游尚未提供。
3. **KV 和权重对 OS 没有语义。** 除非运行时用特定 API 声明类型和价值，OS 只能按页龄回收。
4. **iOS 和 HarmonyOS 的大量「？」是资料空白，不是已证无。**

**谁控制、我们能改什么**：

| 层 | 控制方 | AgentOS 能否改 |
|---|---|---|
| 应用匿名 / 文件页、swap | Google（AOSP）/ OEM 内核 | OEM 可改；上游要走 AOSP / GKI |
| dma-buf 堆与导出者 | Google + SoC 厂商 + 上游内核 | OEM 可在 vendor 内核补计费；上游路径长 |
| GPU 驱动内存 | GPU / SoC 厂商 | 受限，依赖 tracepoint 上报 |
| NPU 驱动内存 | 芯片厂商 | 基本不能，依赖厂商开放 |
| KV、权重的语义 | 推理运行时；系统服务化后归 OS | 若 OS 提供推理服务则可改 |
| iOS 全栈 | Apple | 不可 |
| HarmonyOS | 华为 | 仅限华为内部 |

## §4 趋势判断

**正在收敛的方向**

1. 把 memcg 当作每应用 / 每进程的统一配额接口，并与系统服务（AMS、冻结）联动。
2. dma-buf 统计从 sysfs 迁到 BPF。
3. 设备内存配额采用「区域配额（dmem）+ memcg 账本」双层。
4. 由用户态按 cgroup 主动驱动回收（`memory.reclaim`）。
5. 云侧 KV：块化 + 前缀共享 + 分层存储；重算与加载并行混合，而不是二选一。
6. 端侧量产的权重分层走可预测的访问模式（PLE），而不是随机路由。
7. 闪存优化的方向是布局与合并读，因为瓶颈在 IOPS。

**公认的空白点**

1. dma-buf、GPU、NPU 内存的归属与限额：没有已合入的上游方案，也没有 Android 平台声明。
2. 共享模型服务的内存归属：三个平台都没有公开说明。
3. 前台以外的注意力信号；手机上的 `memory.min/low` 保护契约。
4. 手机上闪存读写、射频发送的 J/GB 能耗。
5. KV 摘要入库（J1）的质量损失数据。
6. 手机上前缀缓存侧信道的实测与防护。
7. 大 MoE 在手机上 decode 阶段的命中率与吞吐。
8. LoRA 与底座权重分页共存的页缓存干扰数据。
9. NPU 路径下 KV 的动态扩张与换出。

**仍有分歧的问题**

1. MGLRU 去留，以及是否与传统 LRU 统一。
2. dma-buf 该计给分配者、客户端还是持有者；按 PID 还是按 cgroup fd。
3. 限额只做天花板（Android 17），还是保护 + 天花板组合。
4. 合作式（鸿蒙）还是强制式（Android 17）更适合 Agent 负载。
5. 有损驱逐是否值得：单轮基准收益显著，多轮接近 0 分。
6. 混合 / 线性注意力会不会让 KV 管理过时。
7. 大 MoE 流式换入与小 MoE / PLE，谁是端侧主流。

### 5.2 修订后的立场表述（建议稿）

- **MM-1′** 记账底座以 memcg 为账本：匿名页、文件页、zram 沿用平台口径；dma-buf、GPU、NPU 缓冲通过「请求方标识 + 共享服务代记」计入；「会话」是 memcg 之上的归属标签，不是新的 cgroup 层级。设备缓冲的可归属、可回收依赖上游和厂商，列为风险项。
- **MM-3′** 供给策略在 Android 已有的「可见性分档 + 天花板限额」之上，增加两件事：保护侧契约（`memory.min/low`），以及前台以外的注意力信号（亮屏、用户正在等待的 Agent 任务）。
- **MM-4′** 模型内存域的回收对象是「会话状态单元」（KV 块或循环状态快照），其尺寸、可切分性、重算成本由模型声明。回收以可恢复为第一约束；含私有内容的前缀按沙箱会话的信任域分区共享。
- **MM-5′** 稀疏权重分层：PLE、MoE 专家、神经元簇统一为「可分页的稀疏权重单元」；专家换入是旗舰档可选策略，必须保证每层的最小工作集驻留。
- **MM-7′** 回收决策按六档有序执行：丢弃（仅已知无用）→ 就地降精度 → 换出到闪存 → 重算 → 上云（仅文本）→ 摘要入库。内存管理负责前五档；第六档由内存管理发出回收事件，记忆框架决定是否摘要、如何摘要。

## §6 接缝发现

**J2 共享底座的记账归属与前缀隔离（主责）**

- 现状：三个平台都没有说明系统级模型服务的内存如何计入应用 [A11]。Android 上有两个先例——binder 层的 dma-buf 所有权转移（Mercier 2023）和分配时按客户端计费（Esteve 2026 RFC）——但都不覆盖「服务代多个客户端长期持有并复用」的场景 [A4][A29]。
- 建议的三层归属方案（判断）：
  1. **底座权重记在系统服务名下**：一次性成本，与客户端数量无关。
  2. **会话 KV 记到会话归属标签**，并带请求方标识，让 LMKD 和限额在杀进程前能区分「杀哪个应用才能真正释放内存」。
  3. **跨会话共享的前缀 KV**：要么按引用计数分摊，要么记在服务名下。两种方案的行为不同——记服务，服务成为被杀目标；分摊给请求方，会重复计费——需要用仿真数据比较。
- 共享服务本身要受保护：mzCache 说明不做归属时它会先被杀 [A11]。合理做法是服务进程整体受保护，压力下由服务**内部**按请求方回收各自的会话状态单元。
- 侧信道：系统提示词 KV（内容由 OS 定义、对所有应用相同）可以安全共享；含私有内容的前缀不得跨应用共享 [B2]–[B5]。分区边界与沙箱的会话主体对齐（见 [C2](C2-沙箱框架与执行能力.md) SBX-9′）。手机上计时噪声是否足以掩盖信号，没有数据。

**J1 有损驱逐 → 摘要入库（成本侧主责）**

- 没有找到把驱逐和长期记忆写入做成一条路径的系统研究。AgentKVShift 方向相反——复用检索到的记忆单元的 KV，只刷新 10%–30% 缓存即接近全量重算 [B27]。这为 J1 的「读侧」提供了参考，但不涉及「写侧」的质量损失。
- 成本侧结论：摘要的时延主要是一次 decode（秒级到十秒级），长期占用小，但不可逆；质量损失没有数据。
- 接口建议：内存管理只定义回收事件（「会话状态单元被回收，附原始 token 范围与可重算标志」），是否摘要由记忆框架和 Agent 决定。这与 MEM-2「策略归 Agent」、MEM-3′「只在文本层摘要」一致，见 [C3](C3-记忆框架与记忆能力.md) §6。

**J5 隔离的内存代价（协同，主责沙箱）**

- 沙箱的内存需求：pVM 和会话沙箱的内存要能记入会话归属标签；pVM 气球回收要与 LMKD / PSI 联动；swiotlb 与 dma-buf 的归属要可见。

**J6 适配器热插拔与权重分页（内存侧协同，主责推理）**

- 适配器小，切换成本主要来自页缓存干扰，而不是适配器本身。适配器页 pin 住，与底座同账；适配器版本绑定底座版本，由 [C1](C1-推理框架与推理能力.md) 主责。

**J7 语义索引常驻成本（协同，主责记忆）**

- 嵌入模型（约 200MB 级）纳入模型内存域，可驱逐、按事件加载；索引文件是文件页，记账归属「记忆服务」。
