# R1 Agent 超长序列推理

> 调研日期 2026-11-09。本地已读：`advanced/A16f-端侧KV-Cache管理方案.md`、`insight/N+1/on-device-kv-cache-management/on-device-kv-cache-management-CN.md`、`proposals/2027-agentos-ai-graphics/notes/M3-model-memory.md`（KV 部分）。联网：WebFetch 9 次（4 篇摘要页 + 3 篇论文 PDF 经本地 pdftotext 抽取全文 + Quest/NSA/2509.25155 摘要页）、WebSearch 3 次。
> 等级说明：官方 / 论文同行评审 / 预印本 / 厂商自报 / 二手 / 估算。**摘要页只给定性结论的，数字栏写「待核实」，不补数。**

## 1. 结论摘要

1. **公开资料里没有「手机 8K/16K/32K prefill token/秒」的实测**：最长的手机 NPU prefill 实测只到 1024 token（llm.npu，ASPLOS '25，Snapdragon 8 Gen 3 / 8 Gen 2）；因此参考负载「557–3808 token/秒、23K 约 6 秒」属于仓库自有实测，应单独标为内部数据，不能用公开文献佐证。
2. 公开最好成绩在约 1B–2B 模型：HeteroInfer（SOSP '25）在 InternLM-1.8B、序列 256 下 prefill 1092 token/秒，同条件 llm.npu 为 564 token/秒（论文自测，同行评审）；Llama-8B 序列 256 仅约 248 token/秒。模型从 1.8B 到 8B，prefill 速度下降约 4.4 倍，基本与参数量成反比（估算）。
3. **长上下文 decode 在手机上被 KV 读取拖累，且已逼近 LPDDR 带宽上限**：按参考负载估算，24K 时每 token 读取 约 1GB 权重 + 0.82GiB KV ≈ 1.8GB，KV 占约 45%；32K 约 51%。52 token/秒 × 1.8GB ≈ 95GB/s，超过 LPDDR5X 理论峰值 77GB/s，实际 decode 上限约 30–42 token/秒（估算，按 60–100% 带宽利用率）。
4. KV 选择类方法（Quest、InfLLM v2、NSA）**均无手机端实测**：Quest 为 GPU 上 self-attention 最高 2.23× 加速（ICML 2024）；InfLLM v2 / MiniCPM4 在 Jetson AGX Orin 与 RTX 4090 上 128K 处理约 7× 加速（论文自报，且需改模型）；NSA 需预训练，属于 R4 范畴。**推理侧可直接用的只有 Quest 类免训练选择 + 闪存卸载（KVSwap）**。
5. KVSwap（预印本，MobiSys 2026 录用见二手检索）全量 KV 放盘、内存只留低秩 K 压缩表，在 Jetson Orin AGX 上 32K 下吞吐比 SOTA 卸载基线最高 1.8×（NVMe）/ 4.1×（eMMC）；RULER 平均精度损失 NVMe 约 2.6%（仓库已引），ShadowKV 52.3%、Loki 34.0%、InfiniGen 78.7%。**评测平台不是手机，UFS 未实测**。
6. Agent 上下文里观察结果（工具返回）占大头：JetBrains 的 SWE-agent 初步实验中 observation 约占每轮 token 的 84%（SWE-bench Lite-50，二手检索摘要）；简单的 observation masking 使成本约减半，解决率持平或略升（Qwen3-Coder 480B：53.8%→54.8%）。**这类「裁剪」是比稀疏注意力更确定的收益来源**，但数据来自编码 Agent，非手机 Agent。
7. 端侧 Agent 系统工作有 Agent.xpu（arXiv 2506.24045）：prefill 放 NPU、decode 放 iGPU 的解耦调度，反应式任务延迟降 4.6×（Intel Core Ultra，非手机 SoC，v2 另报至少 91% 延迟下降，两版基线不同）。
8. 缺口：**增量 prefill（工具返回追加后只算新增 token）+ 前缀 KV 持久化在手机端无公开系统**（M3 也如此判断）；这是我们可以占位的方向。

## 3. 对关键技术的建议

### 对应的负载与瓶颈
- **Prefill 侧**：T3 长程任务 23–32K，6 秒 prefill 来自 3808 token/秒的上限；而公开 SOTA（HeteroInfer、llm.npu）在 1–2B 模型也只有 0.5–1.1K token/秒，8B 约 0.25K。**若底座 3B，按公开水平估算 23K prefill 要 20–40 秒，与内部 6 秒有量级差异**，需确认内部数据的模型、精度与是否含前缀复用（待核实）。端侧接口窗口仅 4K/8K，更说明长上下文必须靠增量 prefill 与 KV 复用，而非每次整段重算。
- **Decode 侧**：24K 时每 token 访存 ≈ 1.0GB 权重 + 0.82GiB KV ≈ 1.8GB，KV 占约 45%；32K 约 51%（估算）。52 token/秒所需 95GB/s 超过 LPDDR5X 理论峰值 77GB/s，因此上下文 20K+ 时 decode 速度会从 52 降到约 30–40 token/秒（估算，非实测）。
- **内存侧**：4GB Agent 预算内，32K KV（1.07GiB）加 1.7GB 权重已占约 70%，只能支撑很少并发会话。

### 问题与挑战
1. **公开基线缺失**：没有手机 8K–32K prefill 的公开实测，自家数据没有外部参照，汇报时要说明口径，避免被追问。
2. **NPU 对动态长度不友好**：NPU 图是静态形状，padding 平均 1.91× 开销，在线建图 1000 token 要 2 秒；长序列必须分块（llm.npu 取 chunk 256），分块后注意力需读全部历史 KV，chunk 越靠后越慢，且 Q·K 部分多落在 CPU/GPU（llm.npu 做法，细节待核实）。
3. **KV 选择类方法缺端侧验证且对 Agent 任务存在风险**：Quest/InfLLM v2 在问答类基准上无损，但 Agent 的工具调用要精确引用（路径、参数、ID），丢 token 可能破坏；KVSwap 报告 InfiniGen/ShadowKV/Loki 在 32K RULER 上精度大幅下降，说明稀疏选择对精确检索任务脆弱。
4. **增量 prefill 与 KV 复用无手机端成熟系统**：Agent 每轮只追加工具返回，理想是只算新增 token；但前缀 KV 的跨轮持久化与失效管理没有公开手机端实现（见 R5，归内存管理）。

### 量化目标建议值（建议值，需按内部基准校准）
| 指标 | 建议值 | 依据 |
|---|---|---|
| 工具返回追加（约 1–2K token）后的 TTFT | ≤2 秒（增量 prefill） | 公开 SOTA 约 0.5–1K token/秒（1–2B），2K 增量即 2–4 秒；需靠 NPU+GPU 协同与内部更高吞吐达成 |
| 24K 长上下文 decode | ≥35 token/秒（较全量 KV 提升 20% 以上） | 带宽上限估算约 42 token/秒；KV 选择或量化把每 token KV 读取降一半可回到约 50 |
| 每 token KV 读取量（24K） | 降至 ≤0.4GiB（约 50% 压缩） | KV 8-bit（Apple 2025 做法，M3 [22]）+ 选择性读取 |
| 上下文裁剪后任务成功率回归 | ≤1 个百分点 | masking 在 SWE-bench 上持平或略升 [8]，需在手机 Agent 任务集复验 |
| 长上下文并发会话数（4GB 预算） | ≥3 个 | 1.7GB 权重 + 3 份 8-bit 约 0.55GiB KV 估算（仅为量级） |

### 模块级方案
1. **增量 prefill + 前缀复用**：系统提示、工具描述、历史作为稳定前缀，工具返回追加时只 prefill 新增块；与内存管理（R5）的前缀缓存配合，推理侧负责「只算新增、块对齐」。
2. **NPU 分块 prefill + GPU/NPU 张量级协同**：采用 llm.npu 的固定 chunk 与 HeteroInfer 的 GPU+NPU 协同；decode 阶段 NPU 贡献有限（带宽受限），以 GPU/CPU 或带宽调度为主。
3. **Prefill / decode 解耦调度**：参考 Agent.xpu 的带宽感知分级，前台反应式任务优先、后台主动任务回填；注意其平台为 PC 级 SoC，手机适用性待验证。
4. **Agent 上下文裁剪（推理侧预处理）**：对工具返回做 observation masking（保留调用与结论，遮蔽旧的原始输出），在不改模型的前提下降 prefill 量；比稀疏注意力更确定。
5. **KV 选择与闪存卸载作为长尾手段**：热点块驻 DRAM，冷块放 UFS，用低秩 K 表预测预取（KVSwap 思路）；仅用于超过 DRAM 预算的会话。

### 细节技术点
- **块对齐**：KV 分块（M3 引 LLMS 为 16 token）与 NPU chunk（256）应成整数倍，保证前缀复用与增量 prefill 的粒度一致。
- **精确引用保护**：对工具名、路径、参数等 token 打「不可淘汰」标记，KV 选择与裁剪时保留；这是 Agent 特有而通用稀疏方法没有的约束。
- **量化精度分层**：prefill 阶段 W8A8（llm.npu 对异常通道做 shadow 执行，精度损失 <1%）；KV 8-bit；避免激活量化引入 20% 以上精度损失（HeteroInfer 对 Qualcomm AI 引擎的批评）。
- **带宽感知调度**：HeteroInfer 与游戏并发时 prefill 仅降 0.5%/2.2%，说明 GPU 只做少量份额可兼顾前台；可作为与图形（前台）共存的设计依据。

## 5. 与其他模块的边界

- **归推理（R1）**：分块 prefill、NPU/GPU 调度、decode 阶段的 KV 读取与选择（只用推理期可做的免训练方法）、Agent 上下文裁剪与 observation masking、增量 prefill 的计算侧。
- **归内存管理（R5 与内存模块）**：KV 的分页、冷热分层、闪存换出与预取（KVSwap 的存储侧）、前缀缓存命中率与失效、KV 与专家缓存的 DRAM 预算划分。KVSwap 横跨两侧，建议把「预测哪些 KV 重要」放推理，「怎么放盘与预取」放内存管理。
- **归 R2/R3**：PIM 把长上下文注意力放进存储内计算（AttAcc 类）。
- **归 R4**：改模型结构的稀疏注意力（NSA、InfLLM v2 的训练部分）、混合线性注意力、KV 共享。
