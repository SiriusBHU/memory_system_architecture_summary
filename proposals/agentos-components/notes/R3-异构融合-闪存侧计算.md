# R3 异构融合：闪存侧计算（UFS-PIM、闪存内计算）

> 日期：2026-11-09。范围：面向 LLM 的闪存内 / 存储内计算（in-flash computing，IFC；computational storage drive，CSD）。
> 方法：先读本地 4 份材料，再抓取 Cambricon-LLM、InstInfer、KVNAND、NVLLM（二手摘要）、Berkeley「LLM Inference in a Flash!」、FlashAccel、MoE-SSD 能耗论文；WebSearch 4 次已用完（AiF 原文、厂商动向各 1–2 次，均未命中一手来源）。
> 等级说明：官方 / 论文同行评审 / 预印本 / 厂商自报 / 二手 / 估算。查不到的写「待核实」。

## 1. 结论摘要

1. 闪存内计算的共同做法是把「权重 GEMV」下沉到 NAND die 旁的逻辑，只把几 KB 的结果向量送回 SoC；Cambricon-LLM 报告 7B 36.34 token/s、70B 3.44 token/s，较 FlexGen-SSD 快 22–45 倍（论文，MICRO 2024，INT8，自建仿真/模型，非手机量产硬件）。
2. 与 UFS 4.0 的关系：论文自己算出 INT8 Llama2-70B 走 UFS 4.0（4GB/s）理论上限仅 0.06 token/s，所以收益来自绕开接口带宽，而不是更快的计算（论文）。
3. 所有已读 IFC 方案都需要**定制 NAND die 或 chiplet**（Cambricon-LLM 的 NPU+闪存 chiplet、NVLLM 的 wafer-to-wafer 堆叠 CMOS 逻辑 die，面积开销 2.7%（二手摘要））；没有任何一篇基于现有 UFS 器件。
4. UFS 5.0（JESD220H，2026-02）没有计算存储接口；铠侠 / 三星 2026 年发布均只讲 10.8GB/s 顺序读和能效；本次检索未发现三星、SK 海力士、铠侠、SanDisk 在**移动端**存储内计算上的公开产品信息（负面结果，不等于不存在）。
5. 对 A3B 级 MoE：冷专家若走 DRAM 路径，0% 命中率每 token 约 1.1GB IO，UFS 4.x 约 256ms/token，UFS 5.0 约 100ms/token（估算）；闪存内计算把这部分变成近乎 0 的接口流量，但前提是内部带宽与 4-bit 算子支持（待核实）。
6. 写寿命是 KV 放闪存的硬约束：HiFC 测得 1.98 TiB/day KV 写入，1TB 盘默认 TLC 模式仅 750 TBW（引自 2609.16161，二手）；本团队 24K–32K 上下文 KV 仅 0.8–1.1GiB，**没有必要把 KV 放进闪存计算**。
7. 能耗口径有分歧：KVNAND 的模型给 flash 读 3 pJ/bit、LPDDR5X 7 pJ/bit（估算模型）；但 Kyung 等测得 MoE 专家放 SSD 的每 token 能耗最高比 HBM 基线高约 12 倍，需要闪存读能耗下降约一个数量级才划算（预印本/IEEE CAL）——说明「在闪存里算」只有在不经过接口搬运时才省能。
8. 建议定位：UFS-PIM 对 2027 年产品是**前瞻研究 + 参与标准的议题**，不是可依赖的交付路径；2027 MoE 底座应以「UFS 5.0 + 专家缓存 + 预取」为主路径，闪存内计算作为 2029+ 的可选增强。

## 3. 对关键技术的建议

### 对应的负载与瓶颈
- 基线稠密 3B/4-bit：权重 1.7GB，decode 约 52GB/s LPDDR 读带宽。该负载**不适合**闪存内计算：权重常驻 DRAM，闪存内带宽（Cambricon 级别约数十 GB/s 量级，KVNAND 假设 32GB/s，均为设计假设）也很难覆盖 52GB/s，且 UFS 器件内算力、浮点能力远弱于 NPU。
- MoE 场景（2027 底座）：30B 级 A3B，0% 命中率每 token 约 1.1GB IO；UFS 4.x 4.3GB/s 下约 256ms，UFS 5.0 10.8GB/s 下约 100ms（估算：1.1GB ÷ 带宽）；iPhone 上 576MiB 缓存命中率 38.58% 时未命中仍约 0.68GB/token（估算：1.1GB × 61.4%）。这才是闪存内计算的潜在价值所在。
- 长程任务 KV：24K 约 820MiB、32K 约 1.07GiB，12GB 机型 Agent 侧 4GB 内放得下，不需要把注意力搬进闪存（InstInfer 类方案针对数据中心 GPU 的 TB 级 KV）。

### 问题与挑战
1. **器件形态**：现有结果都假设定制 NAND die/chiplet（Cambricon-LLM、NVLLM、KVNAND 的 hybrid bonding），UFS 是带 FTL 的托管 NAND，无法直接承载；成本方面 KVNAND 估算 SLC 模式计算型 3D NAND 约 $0.52–0.72/GB（估算），远高于量产 UFS 的容量成本（待核实对比数）。
2. **精度与算子支持**：已读方案以 INT8 为主（Cambricon-LLM、NVLLM），而参考负载为 4-bit；4-bit / 混合精度 / MoE 的 top-k 路由门控与激活函数在 flash 逻辑里怎么做，缺公开证据（待核实）；Berkeley 工作显示浮点算子是主要障碍。
3. **可靠性**：raw NAND BER 1e-4 到 >1e-2，需要片内 ECC 或容错数据通路（Cambricon-LLM 用 on-die ECC，NVLLM 用延迟纠错），并增加面积与功耗。
4. **写寿命与前台 IO 干扰**：KV 放闪存会产生 TB 级写入（HiFC 1.98 TiB/day），而手机闪存还要服务应用启动与系统 IO；计算请求占用 plane/channel 时的 QoS 无公开方案。
5. **生态与标准**：UFS 5.0 无计算存储命令集；NVMe 侧有 Computational Storage 规范工作（SNIA/NVMe，来自既有知识，本次未核对，待核实），UFS/JEDEC 动作未见公开信息。

### 量化目标建议值（评估闪存内计算立项门槛，估算）

| 指标 | 建议值 | 依据 |
|---|---|---|
| 冷专家计算的闪存内部有效带宽 | ≥ 20GB/s | 要使 0.68GB/token（38.6% 命中）≤ 35ms，才不拖慢 52 token/s 稠密基线节奏（估算） |
| 接口回传量 | ≤ 每 token 数 MB | 仅回传激活/结果向量，Cambricon-LLM 的 GeMV 输出缩减约 4096 倍（论文） |
| 每 token 闪存路径能耗 | ≤ DRAM 路径（读入再计算）的 50% | 避免重蹈 Kyung 等「SSD offloading 能耗高 12 倍」的结论（预印本）；KVNAND 模型下 flash 3 pJ/bit 对 DRAM 7 pJ/bit |
| KV 写入量 | ≤ 0.1 TiB/day | 约为 HiFC 实测 1.98 TiB/day 的 5%；本团队不建议 KV 入闪存 |
| 前台 IO 干扰 | 应用冷启动 P99 退化 ≤ 5% | 立项门槛，无公开依据，属目标建议 |
| 增量成本 | ≤ 每 256GB 闪存 $5 | 内部目标，无公开依据，待与成本团队核实 |

### 模块级方案
1. **定位为「冷专家/冷权重」卸载，不进 decode 主路径**：热专家（命中的）仍在 NPU+DRAM 计算，未命中专家交给闪存侧计算，把 1.1GB 的未命中 IO 变成激活向量往返。
2. **分两步走**：近期（2027）做 UFS 5.0 + 专家预取，不依赖私有计算；中期（2028–2029）与存储厂商联合做「GEMV offload」自定义命令的原型，目标是 INT4/INT8 GEMV。
3. **参与标准化**：把「只读 GEMV 卸载 + 结果回传」作为最小命令集，向 JEDEC UFS 工作组或厂商预研提出需求；避免通用可编程 CSD（InstInfer 式 FPGA 方案成本不可接受）。
4. **软硬协同模型改造**：配合 R4，选择 INT 化友好、路由可提前预测的 MoE 结构（SmallThinker 式注意力前路由），使闪存内计算可提前下发请求。
5. **仿真先行**：用 KVNAND/NVLLM 式分析模型 + 本团队参考负载，先出盈亏点（见下），再决定是否立项。

### 细节技术点
- **数据布局**：权重按 page 对齐、跨 channel/plane 条带化，使每次 read-compute 请求命中单个 Compute Core（Cambricon-LLM 的 hardware-aware tiling 使速度提升 1.3–1.4x、通道利用率到 76.2%–88.9%，论文）；专家权重一个专家一个连续条带，便于整专家调度。
- **读-算命令与普通读混发**：Cambricon-LLM 在 read-compute 请求的 channel 空泡里穿插普通读请求，可作为与前台 IO 共享通道的参考；UFS 命令队列深度（32）下需要优先级。
- **误码处理**：raw read + 延迟纠错（NVLLM）适合容错的 GEMV，片内 ECC（Cambricon-LLM）更稳；手机需要结合 P/E 磨损选择。
- **写寿命管理**：KV 不入闪；确需持久化时，采用只读字典编码（Berkeley）、pSLC 区（HiFC）与写合并；本方案优先「不写」。
- **盈亏点估算**（假设：未命中专家 4-bit，全部 1.1GB/token；闪存读 3 pJ/bit、DRAM 7 pJ/bit、UFS 链路能耗待核实）：
  - 搬到 DRAM 再算：每 token 闪存读 ≈ 26mJ + 链路（待核实）+ DRAM 写入 ≈ 62mJ + DRAM 读 ≈ 62mJ，合计 > 150mJ（估算，未含链路）。
  - 闪存内算：闪存读 ≈ 26mJ + 逻辑计算（待核实）+ 少量结果传输。
  - 即便计算能耗翻倍，仍有明显优势；但 Kyung 等的数据提醒：用当前 SSD 读能耗，数据中心 MoE 并不划算，需要核对手机 UFS 的真实 pJ/bit。延迟方面：UFS 5.0 约 100ms/token 的 0% 命中情形，在内部带宽 ≥ 20GB/s 时降到约 55ms/token（估算，仅权重 IO）。
  - 命中率越高，闪存内计算的边际收益越小：命中 38.58% 时未命中量只有 0.68GB/token，UFS 5.0 下约 63ms；命中 70% 时约 0.33GB/token，约 31ms。**结论：命中率提升（R5）与闪存内计算是替代关系，先做命中率。**

## 5. 与其他模块的边界

- **归本模块（R3）**：闪存内/存储内计算的器件形态、命令接口、数据布局、写寿命与前台 IO 调度；盈亏点分析。
- **归 R2（LPDDR-PIM、SoC 协同）**：DRAM 侧 PIM 与 NPU/GPU 协同；两类 PIM 的统一编程模型（闪存侧只负责冷权重 GEMV）。
- **归 R5 / 内存管理「MoE 专家命中率」**：专家缓存、预取、命中率提升；本模块只回答「未命中的那部分能否在闪存里算」，两者是替代/互补关系。
- **归内存管理「模型加载 IO 零拷贝」**：UFS 5.0 顺序读带宽、direct IO、mmap；本模块不重复。
- **归 R4**：模型结构配合（INT 化、路由提前预测）。
- **归 R1**：长上下文 KV 的稀疏选择；InstInfer 类「注意力进存储」在手机 24K–32K 场景无必要。
