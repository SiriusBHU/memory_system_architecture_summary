# 负载量化：C1 推理（贴身秘书参考负载）

> 2026-11-07；检索 WebFetch 11 次（含 1 次失败重试）/ WebSearch 3 次；结论：用户的 10 : 1 只在「增量 prefill、且每次调用都冷启动重算系统提示」这一口径下成立（本文估算日汇总 8.9 : 1）；「不复用前缀」口径下公开数据是 54–560 : 1，我们的原型估算为 37–85 : 1；在复用前缀的长会话里，增量 prefill : decode 只有 1.5–7 : 1。两个口径必须分开写，否则 10 : 1 会被任何一边的人驳倒。

读法说明：本文所有「估算」类数字都来自 §3.1 的原型参数表和一个 20 行的小脚本（参数×轮数的求和），不是实测。公开实测集中在云端的编码 / 数据分析 Agent，没有一份手机上的「秘书类」Agent 轨迹，这是本文最大的数据缺口。

## 1 逐原型量化表

参数记号：S = 可共享前缀（系统提示 + 工具定义），U0 = 首轮独有输入（用户指令 + 注入的记忆），N = LLM 调用次数，a = 每轮新增的工具返回 token，d = 每轮 decode token（工具调用 JSON 或最终回复）。

| 原型 | N（LLM 调用数） | 每轮增量 prefill | 累计上下文（首轮 → 末轮） | 每轮 decode | 一次任务的累计输入 : 输出（不复用） | 一次任务的增量 prefill : decode（复用，S 随首轮冷算 / S 已命中） | 依据 |
|---|---|---|---|---|---|---|---|
| T1 即时指令 | 4 | 首轮 2.4K，之后约 0.3K | 2.4K → 3.6K | 约 80 | 11.9K : 0.32K = 37 : 1 | 10.3 : 1 / 4.1 : 1 | N：估算，参照第三方统计 τ-bench 零售 3–6 次、航空 5–9 次工具调用 [R12]；其余：估算（§3.1 参数） |
| T2 跨应用事务 | 10 | 首轮 2.5K，之后约 0.6K | 2.5K → 8.9K | 约 100 | 56.5K : 1.0K = 57 : 1 | 7.9 : 1 / 5.9 : 1 | N：估算，取 τ-bench 航空工具调用数的上沿并加确认步 [R12]；a：估算，外部内容经截断后注入 |
| T3 长程任务 | 25 | 首轮 2.5K，之后约 0.7K | 2.5K → 23K | 约 150 | 317K : 3.75K = 85 : 1 | 5.1 : 1 / 4.6 : 1 | N：估算，落在 2605.26297 的 12–62 轮区间下半部 [R1]，低于 Manus 平均约 50 次工具调用 [R2]；末轮上下文 23K 低于 2605.26297 的 37–80K 均值 [R1]（手机场景工具返回更短，估算） |
| T4 后台分拣 | 2（单次批处理） | 首轮 1.6K，第二轮 0.2K | 1.6K → 1.9K | 约 60 | 3.5K : 0.12K = 29 : 1 | 15.0 : 1 / 6.7 : 1 | 估算；S 取 1K，因分拣任务可用短提示 + 结构化输出 |
| T5 个人记忆问答 | 2（检索 + 作答） | 首轮 2.1K，第二轮约 1.5K（检索注入） | 2.1K → 3.7K | 约 60 | 5.8K : 0.12K = 48 : 1 | 30.0 : 1 / 13.3 : 1 | 估算；检索注入量 1.5K 与 C3 负载文件的注入量应取同一个值（待对齐） |

公式（脚本口径）：第 i 轮上下文 C_i = S + U0 + (i−1)(a+d)；累计输入 = ΣC_i；增量 prefill = S + U0 + (N−1)a，其中 decode 出来的 token 已在 KV 里，不重复 prefill；「S 已命中」则去掉 S。

## 3 关键推导

### 3.1 参数表与估算前提

结论：下列参数是本文所有估算的唯一输入；任何一个换掉，日比值会变，但「累计口径远大于 10 : 1、增量口径在 2–15 : 1 之间」这一区间结论不变。
推导：参数见 §1 表头注；a（工具返回）取 200–1500 token 是依据「手机场景的 API 返回是日历 / 消息 / 订单这类结构化小载荷，比编码 Agent 的文件读取短一个量级」这一判断，没有公开实测可引。2605.26297 里 SWE-bench Pro 的 Agent 工具单次返回 1.7K token、TaskOutput 最大 3.9K [R1]，可作为上界参照。

### 3.2 口径一：不复用前缀时，累计输入 : 输出远大于 10 : 1

结论：公开数据是 54–560 : 1，我们的原型是 37–85 : 1；10 : 1 低估了一到两个数量级。
推导：
- 2605.26297 报告每轮「输入 : 输出」均值 53.9× 到 559.8×，覆盖 5 个基准（ADE-Bench、DABStep、GAIA、SWE-bench Pro、Terminal-Bench 2.0）、Gemma4-31B 与 Qwen3.6-27B、思考 / 非思考两种模式，运行在 2×H100 + vLLM 上 [R1]。注意是编码 / 数据分析，不是手机秘书。
- Manus 自报平均输入 : 输出约 100 : 1，每任务约 50 次工具调用 [R2]（厂商博客，2025-07，口径未说明是否含缓存命中部分）。
- τ²-bench-Verified 社区榜单上 Grok 4.1 Fast Reasoning 的总量为 27.10M 输入 / 0.36M 输出，约 75 : 1；榜单页未给任务数与日期，且标注为 5 次运行平均，用户模拟器的 token 不计 [R6]（二手，只取比值）。
- 我们的原型：T1 37 : 1，T2 57 : 1，T3 85 : 1（§1）。N 越大，累计比越高，因为累计输入随 N 近似平方增长而输出线性增长。
- Anthropic 的「Agent 约为聊天的 4 倍 token、多 Agent 约 15 倍」[R3] 说明的是总 token 量的放大，不是输入输出比，不能直接用来核对 10 : 1。

### 3.3 口径二：复用前缀后，增量 prefill : decode 约 1.5–10 : 1，10 : 1 落在上沿

结论：在命中率 85–99.5% 的长会话里，增量 prefill : decode 公开数据是 1.5–7.3 : 1；我们的原型日汇总是 5.4–8.9 : 1；短任务且每次冷启动重算系统提示时才到 10 : 1 以上。
推导：
- 2605.26297 报告「新增 token : 输出」均值 1.5× 到 7.3×，中位数常低于 1.5×；前缀缓存命中率理论值 87.9–99.3%，实测 84.6–99.5% [R1]。两个数互相印证：54 × (1 − 0.9) ≈ 5.4。
- 同一篇的结论：复用后 decode 占 LLM 时间的 91.0–98.6%、prefill 仅 1.4–9.0%；LLM 推理占总运行时间的 71–98%（这就是设计文档里「71%–98%」的出处，属于 C2 的核实项，来源是云端 H100 上的编码 / 数据分析 Agent，不是手机，更不是沙箱空闲率的直接度量）[R1]。
- 我们的原型里 T1 / T4 / T5 的首轮冷启动 S 占了增量 prefill 的大头，所以单次任务比值高（T5 达 13–30 : 1）；T3 因长会话摊薄，只有 4.6–5.1 : 1。日汇总 8.9 : 1（S 冷算）与 5.4 : 1（S 命中）。
- 判断：用户的 10 : 1 对「短任务、系统提示不缓存」的端侧场景成立，对长程任务偏高，对不复用口径偏低一到两个数量级。汇报时建议改写成：「不复用时约 50–100 : 1，复用后约 2–10 : 1，取决于前缀命中率与任务长度」。

### 3.4 两个口径对端侧的含义不同：算力、KV 驻留、能耗

结论：不复用口径把端侧变成「prefill 算力问题」，复用口径把它变成「KV 驻留问题」；两者的代价不能互相抵消。
推导：
- 算力：按 §2 小表，不复用时日 prefill 约 265–606 s，与 decode（311–541 s）同量级，T3 单次任务 prefill 83–190 s 对 decode 72–125 s（GPU 档 / 保守档）；复用后日 prefill 降到 23–86 s，仅占推理总时间的 7–14%。速度比也解释了为什么 token 比 10 : 1 的时间比只有约 1 : 7：prefill/decode 速度比在 GPU 档约 73 倍（3808 / 52.1），保守档约 56 倍 [R8][R4]。基准用 1024 token prefill，长上下文（T3 末轮 23K）的注意力开销会让实际 prefill 更慢，需实测。
- KV 驻留：复用的前提是 KV 一直在。T3 末轮上下文约 23K，T2 约 9K；会话被切走、被内存压力回收后，复用口径立刻退化为不复用口径（重算 23K 约需 6 s（3808 tok/s）到 14 s（1667 tok/s），估算：23050 / 速度）。2605.26297 在 H100 上观察到并发超过缓存容量时命中率会从约 99% 掉到 17–27%，吞吐最多降 66% [R1]，这是同一机制的云端版本。具体 KV 字节数交 C4。
- 能耗：decode 访存受限、prefill 计算受限。独立测量指出 NPU 适合 prefill、CPU 在访存受限的 decode 上胜过其他后端，框架差距在 NPU 上可达 10 倍；调 CPU 频率可降能耗最多 39.7%，NPU 能耗配置最多降 53.2%（作者估算）[R5]（只取了 abs 页，具体设备与吞吐未核实）。每 token 能耗没有可靠的 2026 旗舰数据：搜索得到 iPhone 14 Pro 的 PhoneLab 测量约 0.16–0.21 mWh/token（折算 0.58–0.76 J/token，模型规模未核实）[R11]（二手）。若取 0.2–0.7 J/token 并以日 decode 16.2K token 估算，仅 decode 为 3.2–11.4 kJ，约占 19.3 Wh（69.5 kJ，电池容量为假设，沿用 M4 笔记）的 4.7%–16%；prefill 与空闲能耗未计，范围宽是因为单 token 能耗本身缺 2026 数据。

### 3.5 端侧可行性：T1、T4、T5 能跑，T2 取决于每步确认，T3 在上下文上越界

结论：按时延，T1 / T4 / T5 可在端侧满足；T2 的 10 步串行勉强，T3 的 23K 上下文超出现有端侧窗口。
推导（GPU 档 / 保守档）：
- 首 token：首轮 S 冷算 2.4–2.5K token 需 0.63–0.66 s / 1.4–1.5 s；S 命中后只需 0.1–0.3 s（0.4K–0.5K 的 U0 / 速度）。Google 自己的 Prefix Caching 文档估算 1000 token 前缀 + 100 token 后缀从 2.11 s 降到 0.5 s（Pixel 9，Google 标注为估算值）[R13]，方向一致。结论：前台首 token ≤1 s 只在前缀命中时稳定成立（保守档下冷算 S 会超 1 s）。
- T1：总 decode 320 token，6 s / 11 s；加增量 prefill，全程约 7–13 s，勉强满足「10 s 内确认」，主要由 decode 决定，投机解码（Gemma 4 MTP 在 GPU 上最高 2.2 倍，厂商自报，转引自 C1 笔记 B3–B5，本轮未重抓）可压缩。
- T2：decode 1000 token，19 s / 33 s，加 prefill 共约 21–38 s，加工具与用户确认后在 30–60 s 内；是否可接受取决于产品，不是算力问题。
- T3：25 轮 × 150 token，纯 decode 72 s / 125 s，prefill（复用）5–12 s，共约 1.3–2.3 分钟模型时间，后台可接受；但末轮上下文 23K 超过 Apple 示例 8192 与 Android Prompt API 约 4000 的窗口 [R13]，必须做压缩 / 外存，或回落云端。这是「复杂任务回落云端」设定下最自然的分界线。
- T4：单次 0.9–2.1 s（含不复用 prefill）+ decode 2.3–4 s，约 3–6 s，端侧后台可行，问题在功耗而非时延。
- T5：同量级，端侧可行；前提是检索注入 1.5K token 不让首 token 超 1 s。
- 注意：基准是厂商自报的 Gemma 4 E2B（S26 Ultra GPU 3808 / 52.1 tok/s，TTFT 0.3 s，1024 prefill + 256 decode，上下文 2048）[R8]，不是 3B 的 AFM 3 Core；Apple 页面本轮未给 AFM 3 的时延吞吐 [R9]。一个旧的 NPU 参照是联发科 Gemma 3n E2B（prefill 超过 1600 tok/s、decode 28 tok/s，4K 上下文，厂商博客）（来自 C1 笔记 A10）。「Is Your NPU Ready for LLMs?」本轮只取到摘要，没有设备级吞吐数字 [R5]。MLPerf Mobile 本轮未检索。

### 3.6 推理能耗与热是并发的真实上限，而不是 token 数

结论：并发 3–4 个会话在 token 总量上不是问题（日 decode 仅 1.6 万 token），问题是峰值时刻的持续功耗与带宽争用。
推导：decode 访存受限，单流 52 tok/s 的权重读带宽约为 52 × 活跃权重字节（4-bit 的 2B 有效参数约 1 GB，估算：2e9 × 0.5 B）≈ 52 GB/s，多个并发流若各自独立 decode 会成倍占用 LPDDR 带宽（M4 笔记引 PowerInfer-2 的并用带宽仅比 NPU 单用高约 6%，二手）。因此「峰值并发 3–4」应按「同一时刻 1–2 个 decode 流 + 若干等待中的会话」来配算力，合批 decode 的收益没有公开可引的倍数。

## 4 对当前端侧机制意味着什么

1. 前缀命中率决定一切。累计与增量口径相差 7–10 倍（62 : 1 对 5.4–8.9 : 1），而现有端侧缓存是应用私有的：AICore Prefix Caching 把加密缓存放在应用私有存储 [R13]，没有跨应用共享系统提示与工具定义的系统级前缀缓存（C1 §3 已核）。秘书类场景里 S 对所有任务相同，应当只算一份，现有机制做不到。
2. 窗口越界。T3 估算末轮上下文约 23K，超过 Android Prompt API 约 4000 token 输入窗口和 Apple 示例 8192 token 的上下文 [R13]；现有端侧 API 没有「长会话 + 外存溢出」的契约，只有丢最旧对（Chrome `session.clone()`，见 C1）。
3. 切走再切回会把复用口径打回不复用口径。T3 的 23K 上下文重算需 6–14 s，远超 §1 假设的恢复 ≤1 s；AICore 目前只允许前台应用推理，后台一律返回 `BACKGROUND_USE_BLOCKED`（C1a 笔记，A）——而 T3 / T4 恰恰要求后台持续推理。这是准入模型与负载模型的直接冲突。
4. 首 token 目标依赖命中。保守档（约 1667 tok/s）下冷算 2.5K 的 S 需约 1.5 s，超过 1 s 目标；只有命中前缀才能稳定达标。
5. 公开数据的口径与手机差距大。支撑「复用后 decode 占 91–98.6% 时间」的是 H100 上 27–31B 模型 [R1]；手机上 prefill / decode 速度比只有约 56–73 倍，且长上下文 prefill 不是常数速度。结论的方向（复用后 decode 主导）可信，百分比不能直接搬到端侧。
6. 能耗没有可靠数字。每 token 能耗缺 2026 旗舰实测，日 decode 能耗只能给 4.7%–16% 电量的宽区间（估算），T4 的功耗预算无法收敛到一个数。
