# 负载量化：C2 沙箱（贴身秘书参考负载）

> 2026-11-07；检索次数（WebFetch 12 / WebSearch 4）；一句话结论：沙箱在存活期内 ≥67% 的时间空闲（等模型或等用户），典型峰值只需 3–4 个并发实例、约 0.16–0.8 GB，内存本身不是瓶颈；真正的硬指标是 T3 的「暂停—换出—恢复」要在约 1 s 内完成，而这一能力在手机上没有量产原语，云端参照（E2B 暂停约 4 s/GiB）也慢一个量级。

**范围与定义。** 本文的「沙箱实例」指 Agent 的执行环境：承载工具编排、解释器和不可信内容处理，并在其边界上执行策略。App Intents / MCP 调用的目标应用仍在它自己的 App 沙箱里运行，不算本文的实例。实例粒度（按会话、按任务、按事件）是本文为参考负载做的设定，不是某个平台的现状。多 Agent 并发与 GUI Agent 按立项决定排除。

**证据口径。** 带 [S*] 的是本次抓取的来源；「估算」标注公式与输入；「待核实」见 §6。除 [S1]–[S9] 外的来源多为二手（博客、聚合页），已标明。

**公开数据能支撑什么。**

- τ-bench：τ-retail 15 个工具中 7 个会改数据库，τ-airline 13 个中 6 个，即按工具清单约 46–47% 是写工具，不是按调用次数算 [S5]。取消、修改、退货、换货和订票、改签、升舱、改乘客信息，都要先列出细节并取得用户明确同意 [S5]。任务上限 30 次 agent 动作，动作含工具调用和用户回复 [S5]。
- AppWorld：9 个应用、457 个 API、750 个任务；评测用状态单测，并检查「附带损害」（意外改动环境）。本次没取到状态改变 API 的占比，见 §6 [S6]。
- AgentDojo：4 个套件共 74 个工具、97 个用户任务、27 个注入任务；Slack 套件攻击成功率 92%，论文归因于攻击者控制了较大比例的工具输出；注入放在工具响应末尾最有效，对 GPT-4o 平均约 70% [S7]。论文未给读 / 写工具拆分，也未标记不可逆动作。表题 70 个工具与正文 74 个不一致，取 74 [S7]。
- Agent-SafetyBench：2000 个测试用例、349 个交互环境、8 类风险、10 种失败模式，16 个 Agent 没有一个安全得分超过 60% [S8]。

### 1.3 「71%–98%」的出处核实

结论：这个区间**不是 Vercel 数据**，来自 Yuan 等的「Agentic AI Workload Characteristics」（arXiv 2605.26297，IISWC 2026；v1 2026-05-25，v2 2026-09-21）[S1]。我们读到的内容：第 V 节 Fig. 7 称 LLM 推理占总运行时间 71–98%，工具占 2–29%；DABStep 最偏 LLM（96–98%），GAIA 工具占比最高（Gemma Thinking 28.7%、Qwen Thinking 24.9%），SWE-bench Pro 与 Terminal Bench 约 17.7% 和 17.6% [S1]。

必须讲清的三点：

1. 它测的是 **LLM 推理占用的时间**，不是「沙箱在等模型」。两者在单 Agent 串行时近似互补，但前者含推理排队。
2. 测试对象是 Gemma / Qwen 配置在五个**编码、数据分析、研究类**基准上的云侧服务，不是手机场景 [S1]。
3. 抓取摘要的 Table III 里出现 Agent（子 Agent）调用的均值时延（GAIA 上数百秒），推测工具份额可能含子 Agent 时间，这是推测；该抓取由小模型摘要，未回读原表（待核实）。

另有一条二手数据：TraceLab（UW，2026-06）称编码 Agent 单次生成约 13 s、单次工具调用约 18 s [S11]。按这两个数算，LLM 份额只有约 42%，与 71–98% 冲突。差异可能来自负载类型（长编译、测试），说明这个比例**强依赖工具类型**。手机上的工具是应用意图与 API 调用，时延远短于编译或测试，所以更接近 71–98% 的上段。设计文档中「Vercel 公开数据」「计费差 6–10 倍」两处已在 [S12][S13] 标为未找到。

## 2 一天的剖面与峰值

### 2.1 每日次数与沙箱事件（全部为估算，输入见表）

| 原型 | 每日次数 | 每次工具调用 | 每日工具调用 | 每日写操作 | 其中不可逆 / 外发 | 新建实例 / 天 | 暂停—恢复 / 天 |
|---|---|---|---|---|---|---|---|
| T1 | 8（5–15） | 3 | 24 | 约 16 | 约 8（每次 1 条外发消息） | 0（复用） | 0 |
| T2 | 1.5（1–3） | 12 | 18 | 约 6 | 约 2–3（支付与确认） | 1.5 | 约 2（等确认，秒级到分钟级） |
| T3 | 1.5（1–2） | 50 | 75 | 约 11 | 约 2 | 1.5 + 子任务 0–3 | 3–6（用户切走 2–4 次 / 任务） |
| T4 | 约 45 批（原始事件 100–200，按 5 分钟窗口合批） | 1.5 | 约 68 | 约 17 | 0 | 45（进程级，毫秒级创建） | 0 |
| T5 | 4 | 2 | 8 | 0 | 0 | 0 | 0 |
| 合计 | — | — | 约 190 | 约 50 | 约 12 | 约 50（其中 microVM / pVM 级 ≤5） | 约 5–8 |

- 日次数来源：估算。D1 笔记里有「常驻 Agent 每天 1–3 个有价值任务」的商业假设可作 T2+T3 的参照 [S14]；T4 的事件量应与 C3 笔记的通知量统一，这里不另立。
- 一天的约 190 次工具调用里，约 12 次是不可逆或外发动作，占约 6%；这就是需要「用户确认、策略把关、dry-run」的那部分。其余 94% 是读取或可回滚写入。

### 2.2 活跃时段

估算：T1、T2、T5 集中在通勤、午间、晚间三个前台窗口；T3 在用户离开设备的间隙推进，用户回来时恢复；T4 全天，夜间合批。这是设定，不是实测。

### 2.3 峰值并发

典型峰值：前台重应用 + 一个 T2 或 T3 + T4 后台。

| 场景 | 并发实例 | 单实例内存 | 总内存 | 占 12GB 机型 3GB 预算 | 占 16GB 机型 5GB 预算 |
|---|---|---|---|---|---|
| 全进程级（主 + 任务 + 子任务 ×2 + T4） | 4 | 40–100MB | 0.16–0.40GB | 5–13% | 3–8% |
| 任务与子任务用 microVM / pVM（主进程级、T4 进程级） | 4（2 个 VM） | VM 150–296MB（共享后 / 不共享） | 0.38–0.79GB | 13–26% | 8–16% |
| 暂停快照存储（磁盘，不占 DRAM） | 3–9 份（保留 24–72 h） | 约 256MB / 份（全量快照约等于 guest 内存） | 0.77–2.3GB | — | — |

- 输入与公式：进程级每会话私有页 40–100MB、VM 每会话 guest 私有页 256MB + 固定开销 40MB、写时复制共享 50% 的假设，均来自 C2 §Q7（本文估算，D 级）。VM 不共享为 40 + 256 = 296MB；写时复制共享 50% 后，Q7 取约 150MB（≈296 ÷ 2）。快照份数 = 每日 3 个暂停实例 × 保留 1–3 天。
- 全量快照大小约等于 guest 内存（Firecracker 官方说明：全量快照写出「全部 guest 内存」；差量快照是稀疏文件，仍为开发者预览）[S3]。
- 峰值上限：参考负载规定最多再跑 1–2 个子任务，所以实例数不超过「主 + 2 + T4 = 4」。多于此就越过了范围。

## 3 关键推导

### 3.1 沙箱在存活期内大部分时间空闲，所以内存是在「睡」而不是在「忙」

结论：T2 约 79% 空闲，T3 运行态约 60–70%，计入暂停期后超过 90%。

推导（估算）。T2 取 12 次工具调用：每轮 LLM 约 3 s（增量 prefill 加约 50 token decode，端侧速度假设，需 C1 校准），每次 App 意图 / API 调用约 1.5 s，用户确认等待约 30 s。

- 模型时间 12 × 3 = 36 s，工具时间 12 × 1.5 = 18 s，用户等待 30 s。
- 活跃占比 = 18 ÷ (36 + 18 + 30) ≈ 21%，空闲约 79%；不含用户等待为 18 ÷ 54 ≈ 33%，空闲约 67%。

对照：云侧 71–98% 的时间花在 LLM 推理 [S1]。手机的 decode 更慢、工具更轻，空闲只会更高。含义：一个 150–300MB 的实例在 2/3 以上时间里占着内存却没在算，这就是需要暂停与换出的依据。但 LLM 单轮等待只有数秒，不值得为它做快照（见 §3.2）。

### 3.2 换出只对「分钟级以上」的间隙划算，触发源有三类

结论：LLM 等待（2–5 s）保持驻留；用户确认等待（10–60 s）可选压缩换出；用户切走（分钟到小时）必须快照落盘。

推导。换出的成本由写出和读回组成，二者之和要小于间隙才不会让用户感知；更严格的条件是恢复必须在用户回来的那一刻之前或之内完成。

- 写出：估算持续写入 1.5 GB/s（假设，无来源，UFS 持续写入受温度与闪存状态影响）。256MB ÷ 1.5 GB/s ≈ 0.17 s；若先压缩，实际更小。
- 读回：见 §3.3。

触发事件与频率（估算，无公开实测）：

| 触发 | 对应原型 | 频率 | 间隙 | 动作 |
|---|---|---|---|---|
| 等待 LLM | T2、T3 | 每次工具调用后 | 2–5 s | 保持驻留 |
| 等待用户确认（支付、发送） | T2 | 约 2 次 / 天 | 10–60 s | 可选：压缩换出 |
| 用户切走再切回 | T3 | 3–6 次 / 天 | 分钟到小时 | 快照落盘，释放 DRAM |
| 内存压力（前台重应用、LMKD 或 Memory Limiter 触发） | 全部 | 无公开数据，敏感性范围 0–10 次 / 天 | 不定 | 先换出，再杀 |
| 任务完成 / 超时 | 全部 | 每任务 1 次 | — | 销毁并清理 |

### 3.3 T3 恢复需要在约 1 s 内完成；云端参照给不出，手机原语缺失

结论：T3 用户切回时看到的是「上次做到哪」，恢复需在约 1 s 内（设计目标，估算）；当前云端现成数字是恢复约 1 s、暂停约 4 s/GiB，量级刚好，但手机上没有量产的会话快照原语。

推导与参照。

- E2B：暂停约 4 秒 / GiB 内存，恢复约 1 秒；默认保存内存与文件系统，暂停期间服务不可达、客户端断开；暂停态无 TTL，不会自动删除；暂停可能因节点仍在处理上一次快照而被 503 拒绝 [S2]。按线性估算，256MB 实例暂停约 1 s（0.25 × 4 s，线性假设）。
- Firecracker：恢复时内存文件以私有映射挂入、按需缺页，写入走写时复制，内存文件在整个恢复后的生命周期内必须保留；官方文档不给时延数字，只说取决于内存大小、vCPU 数与设备数 [S3]。二手数据：vHive（2021）发现快照启动内存占用低，但缺页加上 SSD 局部性差，启动时延高；Catalyzer 报告快照恢复在数十到数百毫秒；某博客在 Cloud Hypervisor 上用 userfaultfd 把 2GB guest 的恢复从约 7 s 降到 100 ms 以内（单机、3 次，不是 Firecracker）[S10]。
- CubeSandbox（腾讯，README 自报，无独立复现）：裸金属单并发创建 <60 ms，50 并发均值 67 ms、P95 90 ms、P99 137 ms；每实例内存开销 <5MB（最大配置 32GB）；快照与回滚「百毫秒粒度」，AutoPause / AutoResume 与跨节点暂停恢复有功能但无时延数字 [S4]。
- 手机侧估算：恢复读入量 = 私有页 × 工作集比例。以 256MB × 30–60% = 77–154MB，UFS 4.1 约 4.3 GB/s（取自本任务要求的基准，顺序读）：顺序读 18–36 ms；缺页是随机小块读，假设有效带宽只有 0.5–1 GB/s，则约 80–310 ms。所以 VM 本体恢复在 0.1–0.4 s 的量级，不是瓶颈；但还要加上设备重连、令牌与会话重建、模型 KV 重建。后者见 C1 / C4。

### 3.4 创建成本：进程级毫秒级，VM 级是数量级差异，但 T4 必须用进程级

结论：T4 一天约 45 次创建，只能走进程级或池化；VM 级创建一天不超过 5 次。

参照：

- Android：zygote fork 在真实 trace 中常为 10–30 ms；另一份开发者实测从收到 intent 到 fork 129 ms，再到 `handleBindApplication` 193 ms，设备不同，不可比 [S9]。`isolatedProcess` 的创建属同一路径，另加 SELinux 域与 seccomp 设置，开销未取得（待核实）。
- AVF Microdroid：Android 14 比 13 启动快约 2 倍、内存约减半 [S8']；绝对启动时延和内存没有公开；C2 记录的 32–42（疑为 MB）来自 AOSP 测试提交，单位未注明，不得当事实用。
- Firecracker：VMM ≤5MiB，启动目标 ≤125 ms（规格目标，非实测，取自 C2 §2）。

推导：T4 若每批用 VM，45 批 × 约 125 ms = 5.6 s/天的创建时间，加上每批 40MB+ 的固定开销，对功耗不友好；进程级创建 10–30 ms 量级，更合理。这仅是量级对比，不是实测。

### 3.5 并发数受限于模型与 KV，而不是沙箱

结论：沙箱占用 0.16–0.8GB，占 3GB 预算的 5–26%，不是内存瓶颈。

推导见 §2.3 的表。真正稀缺的是 12GB 机型上模型权重与 KV 之后剩下的预算；沙箱的预算 3GB / 5GB 本身是 C2 的假设（未经 C4 核对）。如果 C4 的预算更紧，microVM 档（0.38–0.79GB）会先被压缩，退到进程级。

### 3.6 风险动作占比低，但集中在 T1 / T2，策略把关必须在这两类上不增加感知时延

结论：全天约 190 次工具调用中约 12 次不可逆（约 6%），其中约 10 次属于 T1、T2；这些前台、用户在等的任务，策略检查与确认必须在亚秒内。

推导：表 2.1 的不可逆列合计 8 + 2.5 + 2 = 12.5。T4 在设定上为 0，若放开则风险全落在「不可信内容 100% 的原型」上，这是 CaMeL / FIDES 一类信息流控制要解决的场景。官方 Claude Code 数据表明人工确认批准率 93%（厂商口径，2026-03，取自 C2 §2），说明确认弹窗容易被点穿，不能只靠确认。这属于已有结论的引用，不是本次新数据。

## 4 对当前端侧机制意味着什么

仅写事实与推导，不写方案。

1. **没有会话级快照 / 分叉原语。** Android 有 `isolatedProcess` 和 AVF，但没有量产的「暂停整个会话沙箱并换出再换入」原语；iOS 第三方无比 App 沙箱更细的边界（C2 §Q6）。T3 每天 3–6 次暂停恢复、需 1 s 内恢复，只能靠 App 自己保存状态，沙箱内的解释器状态和中间产物会丢。
2. **云端暂停速度不能直接搬。** E2B 暂停约 4 s/GiB、恢复约 1 s [S2]：恢复量级可用，暂停在手机上不能发生在用户可见路径上，必须在切走的后台完成，并与 LMKD 的压力抢 UFS 带宽。
3. **pVM 内存与 LMKD 的耦合没有解决。** AVF 的气球调整曾因 VM 内存不足被回退，改为动态内存调整（C2 §Q6，C 级证据）。T3 的 VM 档（0.38–0.79GB）在内存压力下是被杀还是被换出，无机制回答。
4. **快照存储不是 DRAM 问题，但没有配额与回收机制。** 全量快照约等于 guest 内存 [S3]，每天 3 份、保留 1–3 天约 0.8–2.3GB；这笔存储属于谁的配额、何时清理，没有对应的系统记账（与 C4 的记账缺口相同）。
5. **不可信内容占比高，而隔离粒度落在「会话」而非「调用」。** T2、T3、T4 的读取调用有 70–100% 来自第三方（估算），而 AgentDojo 显示注入落在工具响应末尾时成功率约 70%、Slack 套件 92% [S7]。进程 / VM 隔离只防逃逸，不防「合法权限被滥用」，这需要数据标签与带外策略，现有 OS 机制没有。
6. **后台 T4 的创建频率要求进程级创建 + 池化。** 一天约 45 批、每批 1–5 s，VM 级创建不可行；Android 现有的进程创建路径是毫秒到百毫秒量级，能满足，但没有为「用完即毁、不留痕、受策略约束的事件级沙箱」提供形态。
