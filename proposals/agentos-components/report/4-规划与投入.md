# 第四部分 规划与投入

> 本部分回答以下问题：
> - 为什么现在投入；
> - 我们的差异化在哪里；
> - 2027 年如何安排；
> - 需要哪些投入；
> - 有哪些风险和需要决策的事项。
>
> 人力与预算的数字由团队补充，本文只给出结构，用占位符表示。2026-11-08 起，内存管理按两个模块列示：通用内存管理优化、模型内存管理。

## 4.1 为什么是现在：时间窗口

1.2 节的四张原型对比表显示，四个组件中的空白点正在以不同速度被填补。按速度分为四档：

| 分档 | 空白点 | 对我们的含义 |
|---|---|---|
| 已收敛，不宜正面竞争 | 模型作为系统服务；云端沙箱接口；凭证不进入沙箱 | 沿用业界形态，差异化放在记账和组件之间的接口上 |
| 正在被平台填补 | NPU 加载准入与模型级抢占（Android 17 NPU Manager）；系统模型的稀疏权重分层（Apple AFM 3） | 与平台对齐，不另起一套；差异化放在平台未覆盖的会话粒度与跨后端 |
| 窗口正在关闭 | 个人语义索引的第三方细粒度授权；被驱逐上下文写入记忆的接口 | 先出原型与基准，率先定义问题 |
| 长期空白 | 手机统一内存上的模型内存记账（含代分配归账）；沙箱与内存的契约；手机侧的成本参数 | 长期建设，形成长期竞争优势 |

**判断**：2027 年是「会话级」能力的窗口期。平台已完成「模型级」能力，并在向下延伸。会话级的调度、隔离、记忆治理和内存分层，在任何量产端侧系统中都尚未出现，但云端和学术已证明可行。

## 4.2 差异化论据

1. **我们聚焦「会话」层，平台聚焦「模型」层。**
   - Android 17 NPU Manager 实现了模型级准入与卸载式抢占，AFM 3 实现了系统模型的权重分层。
   - 我们的四个组件都以 Agent 会话为单位，由同一个会话档位统一驱动调度、隔离、记忆和内存，见第三部分 3.1.4 的联动表。
2. **模型内存的记账盲区在 Android 17 中仍未解决。**
   - 限额只统计匿名页与 swap；
   - dma-buf 的 memcg 计费仍停留在 RFC；
   - 共享服务代持的内存没有归属原语。

   先做可观测与代分配归账，是所有回收策略的前提，也能发挥部门在可观测性上的积累，率先占据这一位置。
3. **关键参数只能依靠建模与仿真获得。** 四个组件在同一类数据上都找不到公开实测：
   - 每 token 能耗；
   - 切换与恢复时延；
   - 隔离开销；
   - 目标规模下的检索质量；
   - 换出的写入代价。

   服务器上的结论在手机上会反转：服务器上重算优于换出，手机上换出快 31–215 倍。第二部分的负载模型本身体现了部门能力，下一步用真机轨迹校准。
4. **端侧具备云端无法提供的价值。** 云端常驻 Agent 每用户每月 70–300 美元（估算），记忆不可单条删除，且远离手机上的数据和应用。端侧系统的差异化在于：
   - 低成本；
   - 隐私（标签约束出端）；
   - 可删除的记忆；
   - 与本机应用深度协同且不影响流畅度。
5. **立项已选方向获得新证据支撑。**
   - **稀疏权重分层**：AFM 3 已量产，可直接作为参照，管理对象是请求级工作集。
   - **模型加载 IO**：NPU Manager 将「卸载模型」作为抢占手段，模型重载从偶发变为常态。
   - **匿名页冷热识别与预取**：Agent 调起多个应用是参考负载的常态。

## 4.3 2027 年路线图（建议）

| 阶段 | 推理服务 | 执行沙箱 | 记忆服务 | 通用内存管理优化 | 模型内存管理 | 阶段验收 |
|---|---|---|---|---|---|---|
| **一季度 基线与可观测** | 端侧速度与能耗基线；前缀命中率测量 | 进程级实例创建、冻结开销测量；AVF 可用性摸底 | 自建 3 年规模记忆基准（合成与脱敏） | 统一账本第一阶段：只记账、不限额；冷启动与换入基线测量 | 专家缓存基线与路由轨迹采集 | 参考负载的关键参数全部获得真机值，替换第二部分的估算 |
| **二季度 机制原型** | 会话与作业接口；多级队列；分块 prefill 抢占；系统级前缀缓存 | 会话级进程实例；策略引擎与三维定档；出口代理（含 DNS） | 写入网关与完整性分级；分层存储与混合索引 | 代分配归账；主动回收原型；SPE 预取与 .so 锁优化原型 | KV 块池与停放换出；专家热度模型与在线策略；页对齐权重格式 | 单组件指标达标：首 token、判定时延、检索时延、KV 恢复 |
| **三季度 联动集成** | 会话 KV 停放与恢复接入内存管理；端云路由按标签约束 | 冻结、快照、恢复接入档位事件；标签全链路；凭证经纪 | 授权中心与查询网关；冲突检测与级联删除 | 按档位水线接入回收仲裁；档位事件预加载；冷热换出与意图预取 | 按档位回收仲裁接入；跨层预取与 IO 让步；NPU 零拷贝映射 | 3.1.4 联动表端到端跑通：切回 ≤1 秒、12GB 峰值不终止前台、注入路径全部拦截 |
| **四季度 全天回放与交付** | 合批 decode；功耗预算 | 虚拟机级隔离（按机型分级）；审计与回放 | 用户记忆管理界面；应用贡献接口 | 压力信号联动；全天回放验收 | 闪存写入预算；IO 优先级联调；全天回放验收 | 参考负载全天回放：各组件指标全部验收；形成 2028 年规划 |

**2028 年及以后**：与 2026-11-03 的立项排除项一致，只预留接口，不进入 2027 年交付。
- 多 Agent 共享记忆与跨 Agent 调用链；
- 基于注意力预测的升档；
- 广泛的虚拟机级隔离；
- 投机式端云解码。

## 4.5 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 平台方（Google）自行延伸到会话级 | 差异化收窄 | 与平台对齐接口，优先做平台不会做的部分：统一记账、沙箱与内存契约、手机侧成本参数；能贡献上游的就贡献 |
| 芯片厂商 NPU 驱动不开放抢占与内存上报 | 调度只能做到分块边界；记账存在盲区 | 经 NPU HAL 中介；以 CPU / GPU 承担 decode 作为退路；尽早与芯片厂商对接 |
| 应用生态不接入动作接口与实体贡献 | 沙箱与记忆服务的覆盖面受限 | 从系统应用和头部应用起步；接口对齐 App Intents、AppFunctions 的形态，降低接入成本 |
| 负载参数基于估算 | 目标值偏离 | 一季度用真机轨迹替换；本文所有估算都已标明公式与输入 |
| 闪存寿命 | 换出写入量过大 | 按恢复概率决定是否写出，并设日写入上限 |
| 沙箱自身被攻破 | 安全承诺失效 | 将注入语料与逃逸用例纳入持续集成的对抗性回归；已知 CVE 先例说明沙箱本身也需要测试 |
| 监管 | 系统级个人索引受到隐私与反垄断审视 | 最小披露、可审计、用户可删除；法务提前介入 |

## 4.6 需要决策的事项

1. **会话档位与 11-03 排除项的关系。** 第三部分的会话档位，与 11-03 排除的「按 Agent 语义调整前后台资源策略」存在重叠。
   - **建议**：2027 年只实现由确定性事件触发的两档，即「交互」与「后台」。确定性事件指前台对话、确认弹窗、用户切回等用户可见的事件；基于注意力预测的升档列入 2028 年以后。
   - **理由**：缺少这两档，「前台首 token ≤1 秒」与「后台任务不被终止」无法同时成立。
2. **人力与预算的数字（4.4）。**
3. **团队可直接改动的范围**：沙箱和记忆服务是由本团队自研，还是由本团队定义接口、平台或其他部门实现。这决定 4.4 中「主要外部依赖」一列的分量。本文按自研口径规划。
