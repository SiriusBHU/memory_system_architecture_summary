## 4.1 为什么是现在：时间窗口

1.2 节的四张原型对比表显示，四个组件里的空白点正在以不同的速度被填上。按速度分为四档：

| 档位 | 空白点 | 对我们的含义 |
|---|---|---|
| 已收敛，不宜正面竞争 | 模型作为系统服务；云端沙箱接口；凭证不进沙箱 | 沿用业界形态，差异化放在记账和组件之间的接口上 |
| 正在被平台填上 | NPU 加载准入与模型级抢占（Android 17 NPU Manager）；系统模型的稀疏权重分层（Apple AFM 3） | 与平台对齐，不另起一套；差异化放在平台没有覆盖的会话粒度与跨后端 |
| 快关闭的窗口 | 个人语义索引的第三方细粒度授权；被驱逐上下文写入记忆的接口 | 先出原型与基准，先把问题定义下来 |
| 持久空位 | 手机统一内存上的模型内存记账（含代分配归账）；沙箱与内存的契约；手机侧的成本参数 | 长期建设，作为护城河 |

**判断**：2027 年是「会话级」这一层的窗口期。平台已经做完「模型级」，正往下走；会话级的调度、隔离、记忆治理和内存分层，在任何一个量产端侧系统里都还没有出现，但云端和学术已经证明它们可行。

## 4.2 差异化论据

1. **我们做的是「会话」这一层，平台做的是「模型」这一层。** Android 17 NPU Manager 做到了模型级准入与卸载式抢占，AFM 3 做到了系统模型的权重分层。我们的四个组件都以 Agent 会话为单位，用一个会话档位统一驱动调度、隔离、记忆和内存，见第三部分 3.1.4 的契约表。
2. **模型内存的记账盲区连 Android 17 都没解决。**
   - 限额只计匿名页与 swap；
   - dma-buf 的 memcg 计费停在 RFC；
   - 共享服务代持的内存没有归属原语。

   先做可观测与代分配归账，是所有回收策略的前提，也是部门在可观测性上的积累能先占住的位置。
3. **关键参数只能靠建模与仿真获得。** 四个组件都在同一类数据上找不到公开实测：
   - 每 token 能耗；
   - 切换与恢复时延；
   - 隔离开销；
   - 检索在目标规模上的质量；
   - 换出的写入代价。

   服务器上的结论在手机上会反转：服务器上重算优于换出，手机上换出快 31–215 倍。第二部分的负载模型本身就是部门能力的体现，下一步用真机轨迹校准。
4. **端侧有云端做不到的东西。** 云端常驻 Agent 每用户每月 70–300 美元，记忆不可单条删除，离手机上的数据和 App 很远。端侧系统的差异化在于：
   - 低成本；
   - 隐私（标签约束出端）；
   - 可删除的记忆；
   - 与本机 App 深度叠加而不卡。
5. **立项已选的方向得到新证据支撑。**
   - **稀疏权重分层**：AFM 3 已量产，可以直接作为参照，管理对象是请求级工作集。
   - **模型加载 IO**：NPU Manager 把「卸载模型」作为抢占手段，重载从偶发变成常态。
   - **应用内存智能化**：Agent 调起多个 App 是参考负载的常态。

## 4.3 2027 年路线图（建议）

| 阶段 | 推理服务 | 执行沙箱 | 记忆服务 | 内存管理 | 阶段验收 |
|---|---|---|---|---|---|
| **Q1 基线与可观测** | 端侧速度与能耗基线；前缀命中率测量 | 进程级实例创建、冻结开销测量；AVF 可用性摸底 | 自建 3 年规模记忆基准（合成 + 脱敏） | 统一账本第一阶段：只记账、不限额；KT1 基线测量 | 参考负载的关键参数全部有真机值，替换第二部分的估算 |
| **Q2 机制原型** | 会话 / 作业接口；多级队列；分块 prefill 抢占；系统级前缀缓存 | 会话级进程实例；策略引擎与三维定档；出口代理（含 DNS） | 写入网关与完整性分级；分层存储与混合索引 | 代分配归账；KV 块池与停放换出；KT1-a/b 原型 | 单组件指标达标：首 token、判定时延、检索时延、KV 恢复 |
| **Q3 联动集成** | 会话 KV 停放与恢复接入内存管理；端云路由按标签约束 | 冻结、快照、恢复接入档位事件；标签全链路；凭证经纪 | 授权中心与查询网关；冲突检测与级联删除 | 回收仲裁按档位执行；权重工作集管理；KT1-c、KT3 | 3.1.4 契约表端到端跑通：切回 ≤1 秒、12GB 峰值不杀前台、注入路径全部拦截 |
| **Q4 全天回放与交付** | 合批 decode、功耗预算 | 虚拟机级隔离（机型分级）；审计与回放 | 用户记忆管理界面；应用贡献接口 | 闪存写入预算；压力信号联动 | 参考负载全天回放：四组件指标全部验收；形成 2028 规划 |

**2028 年及以后**（与 2026-11-03 的立项排除项一致，接口预留，不进入 2027 交付）：
- 多 Agent 共享记忆与跨 Agent 调用链；
- 基于注意力预测的升档；
- 广泛的虚拟机级隔离；
- 投机式端云解码。

## 4.5 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 平台方（Google）自己往下做到会话级 | 差异化收窄 | 与平台对齐接口，优先做平台不会做的部分：统一记账、沙箱与内存契约、手机侧成本参数；能贡献上游的就贡献 |
| 芯片厂商 NPU 驱动不开放抢占与内存上报 | 调度只能做到分块边界；记账留下盲区 | 经 NPU HAL 中介；把 decode 挪到 CPU / GPU 作为退路；尽早与芯片厂商对接 |
| 应用生态不接入动作接口与实体贡献 | 沙箱与记忆服务的覆盖面受限 | 从系统应用和头部应用起步；接口对齐 App Intents、AppFunctions 的形态，降低接入成本 |
| 负载参数基于估算 | 目标值偏离 | Q1 用真机轨迹替换；本文所有估算都已标明公式与输入 |
| 闪存寿命 | 换出写入量过大 | 换出按恢复概率决策，并设日写入上限 |
| 沙箱自身被攻破 | 安全承诺失效 | 对抗性回归进 CI：注入语料、逃逸用例；已知 CVE 先例说明沙箱本身也要被测试 |
| 监管 | 系统级个人索引受隐私与反垄断审视 | 最小披露、可审计、用户可删除；法务提前介入 |

## 4.6 需要拍板的事

1. **会话档位与 11-03 排除项的关系。** 第三部分的会话档位，与 11-03 排除的「按 Agent 语义调整前后台资源策略」有重叠。
   - **建议**：2027 年只做由确定性事件触发的两档：「交互」与「后台」。确定性事件指前台对话、确认弹窗、用户切回，这些都是用户可见的事件；基于注意力预测的升档列为 2028 年以后。
   - **理由**：没有这两档，「前台首 token ≤1 秒」与「后台任务不被杀」无法同时成立。
2. **人力与预算的数字（4.4）。**
3. **团队能直接改动的范围**：沙箱和记忆服务是自研，还是定义接口、由平台或其他部门实现。这决定 4.4 中「主要外部依赖」一列的分量。
4. **参考负载的真机数据**：你手上的细粒度数据，可以直接替换第二部分 2.1 与 2.2 的估算参数。
