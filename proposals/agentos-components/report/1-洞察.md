## 概括：Agent 的商业化趋势与端侧运行需求

### 问题一：Agent 的使用是否处于爆发期

**判断：Agent 处于爆发期，市场广阔。** 依据分三层。

**一、用量：大模型的 token 用量一年增长 7–10 倍。**

| 指标 | 时间序列 | 增幅 | 来源 |
|---|---|---|---|
| Google 全产品每月处理的 token（万亿） | 2024-04 约 9.7 → 2025-05 约 480 → 2025-07 约 980 → 2025-10 超 1300 → 2026-05 超 3200 | 25 个月约 330 倍，近一年约 7 倍 | [GT1]，厂商自报，媒体转述 |
| 豆包大模型日均 token 调用量（万亿） | 2024-05 约 0.12 → 2025-06 16.4 → 2025-09 30 → 2026-01 约 60 → 2026-03 120 → 2026-06 180 | 两年超 1500 倍，近一年超 10 倍 | [GT2]，厂商自报，媒体转述；2024-05 一点由媒体按倍数反推 |
| Google 第一方模型 API 的 token 速率（亿/分钟） | 2025-Q3 约 70 → 2026-Q3 近 320 | 同比超 4 倍，环比 +40% | [GT3]，2026-Q3 一点为官方财报致辞 |

**二、产品：2026 年 8–10 月，三款 Agent 产品相继上线或开售。**
三款产品本身均未公开日活、销量或调用量，下表给出同公司的可比指标。

| 产品 | 上线 | 形态 | 同公司指标 |
|---|---|---|---|
| xAI Grok Bot | 2026-08 | 账号级常驻云端电脑；200 美元/月 | Grok 月活 2025-12 约 3500 万 → 2026-03-31 约 1.17 亿，付费订阅约 190 万（SpaceX 上市文件，二手转述）[GT5] |
| OpenAI dot | 2026-09 | 每个 Agent 一台云端电脑；随 ChatGPT Pro 提供 | ChatGPT 周活 2025-02 约 4 亿 → 2025-10 8 亿 → 2026-02 超 9 亿 → 2026-08 10 亿；Codex 周用户 2026-05 底 500 万 → 2026-07 中旬约 800 万（厂商自报，媒体转述）[GT6] |
| 阶跃 STEPX Neo 手机（搭载 Step AOS） | 2026-10 开售（10-13 预订、10-16 首销；Step AOS 于 2026-07 发布） | 整机 Agent 手机，3999 元起；系统级 Agent；端侧小模型加云端大模型 | 阶跃 Step 3.5 Flash 曾居 OpenRouter 周调用量第一（2026-03，媒体）[GT4][M1] |

**三、交易与强度：Agent 开始替用户付款，单个用户的用量成倍上升。**

- 支付宝 AI 付累计 3 亿笔（2026-05-26，官方发布），约九成来自千问（媒体）[GT7]。
- Agent 的 token 消耗约为对话的 4 倍，多 Agent 约 15 倍 [AN1]。

**读这些数字时要注意两点。**

1. **用户数的增速在放缓，用量仍在加速。** ChatGPT 周活 2025-10 至 2026-08 由 8 亿增至 10 亿，约 25%；同期 Google 的 token 用量增长数倍。增量主要来自单个用户用量的上升。我们判断其来源是 Agent 与推理模型，但没有公开数据拆分两者（判断）。
2. **反面信号。**
   - Grok 月活在 2026-03 之后被报道趋平 [GT5]；
   - 支付宝 AI 付高度集中在阿里自家入口 [GT7]；
   - 未见留存与付费转化的一手数据。

### 问题二：端侧 Agent 运行需要什么

Agent 要「想」、要「做」，还要与用户正在使用的应用「共存」。Agent OS 的三个趋势，是把这三件事从应用各自处理，转为由系统统一提供。

| 趋势 | 现状 | 方向 | 业界佐证 | 对应的系统服务 |
|---|---|---|---|---|
| 推理服务化 | 每个应用自带模型 | 系统托管底座模型，按会话分配算力 | Apple Foundation Models 向第三方开放端侧模型；Android AICore 托管 Gemini Nano（见 1.1.3） | 推理服务 |
| 执行沙箱化 | 只有应用级权限 | 系统按会话隔离，按每次调用判定权限：外部 Agent 经 A2A 访问系统，系统 Agent 经 MCP 调用外部工具 | dot、Grok Bot 为每个 Agent 配一台云端电脑；Windows Agent Workspace 为 Agent 设独立账户与会话（见笔记 [C2a](../notes/C2a-sandbox-isolation.md)） | 执行与沙箱 |
| X + Agent 内存协同管理（X 指用户正在使用的应用） | 应用与模型各自管理内存，模型整块常驻 | 前台应用与 Agent 统一记账、协同回收；权重按需从闪存换入 | Apple、Google 以 12GB 内存为端侧模型的准入门槛；AFM 3 权重放在闪存，每个请求换入 1–4B 参数 [A1][A2][G1] | 内存与资源 |

**判断**：端侧 Agent 运行需要这三项能力由系统提供，它们对应本次汇报的三项系统服务。1.1.2 节说明为什么系统服务只需要这三项。

调研过程与完整数据见笔记 [G1-Agent产品增长](../notes/G1-Agent产品增长.md)、[G2-Agent宏观增长曲线](../notes/G2-Agent宏观增长曲线.md)，调研 prompt 见 [research-prompt-商业化趋势](../notes/research-prompt-商业化趋势.md)。

## 1.1 Agent OS 的发展与端侧目标形态

### 1.1.1 业界的三条路线

2025–2026 年，「让 Agent 替用户把事办完」从演示走向产品，形成三条路线。

**路线一：云端常驻 Agent，为每个用户配备一台云端电脑。**

- **代表产品**：
  - OpenAI dot（2026-09 上线）：每个 dot 有自己的云端 Linux 电脑和浏览器 [D1-2]。
  - xAI Grok Bot（2026-08-11 公测）：账号级的持久云 VM，多个 bot 共用 [D1-3]。
  - Meta Muse（2026-09）。
- **优点**：模型能力强，不受端侧资源约束。
- **代价**：
  - **成本**：按 GPU 推理加云 VM 估算，每用户每月 70–300 美元 [D1-1]。dot 只随 100–500 美元档的 ChatGPT Pro 附赠，Grok Bot 单独订阅 200 美元/月 [D1-2][D1-3]，都不是大众价位。
  - **位置**：Agent 离用户的手机、本地数据和正在用的 App 很远。
- **安全上的共识**，正在从「授权一次」转向「环境外的独立审核，加敏感步骤回请用户」：
  - dot 用独立的自动审核检查计划动作，密码与付款永远回到用户 [D1-2]；
  - Meta 用独立的 Sentinel Agent 审查动作 [M1]。
  - 即便如此，dot 在 5 步任务链上的越权率仍有 8.6%，10 步链 19.7%（OpenAI 内部数据，二手转述）[D1-4]。

**路线二：OS 内置的系统级 Agent，端云协同。**

| 平台 | 代表 | 端侧模型 | 应用接入 |
|---|---|---|---|
| Apple | iOS 27 + 新 Siri | 2026-06 的 AFM 3 Core Advanced：20B 稀疏模型，完整权重放在 NAND，每个请求只把 1–4B 激活参数换入内存 [A1] | App Intents |
| Google | Android 17 + Gemini Intelligence | 机型门槛为 12GB 以上内存 [G1] | 一路是声明式的 AppFunctions，私有预览，25 个应用用例；另一路是限定伙伴的屏幕自动化 [D1-5] |
| 华为 | HarmonyOS 7 + 小艺 / HMAF 2.0 | — | 2100 多项系统能力 Skill 化（厂商口径）[H1] |
| 荣耀 | MagicOS 11 | — | 以 MCP 和 A2A 为主，GUI 只作兜底 [R1] |

这条路线的特点是 Agent 就在手机里：靠近用户数据，直接调用本机应用，可离线，云成本由厂商承担。它的约束全部落在端侧资源上。Apple 和 Google 都以 12GB 内存作为准入门槛，iPhone 17 标准版的 8GB 被排除在最强端侧模型之外 [A2][G1]。

**路线三：整机重构的 Agent 手机。**

- **阶跃 STEPX Neo**（2026-07 亮相，16GB，3999 元）：Step AOS 用 MCP 把系统能力做成功能块 [M1]。
- **豆包手机**：靠系统特权做 GUI 自动化，二代于 2026-09 开售。150 余款应用（含微信、支付宝、淘宝、美团）拒绝被 GUI 自动化操作 [B1]。

这条路线概念上吸引力强，但出货规模小。豆包的遭遇说明，绕开应用接口去「模拟点击」，会受到应用生态的限制。

**三条路线收敛出的五个事实**

1. **应用能力函数化已成共识。** App Intents、AppFunctions、Skill、MCP / A2A 都是这一做法，GUI 模拟退为兜底。Agent 因此以「调用函数」的方式代用户执行。执行的安全边界必须由系统划定，而不是由应用各自防守。
2. **内存成为端侧 Agent 的准入门槛。** 两大平台都以内存而不是 NPU 算力作为准入门槛。没有一家公布模型的常驻内存，以及与应用共存时的回收机制。
3. **端侧模型从稠密小模型走向稀疏大模型加闪存分层。** AFM 3 把这件事做成了量产 [A1]。模型内存从此不再是一块固定大小的常驻区，而是要按请求换入换出的工作集。
4. **云端路线证明了 Agent 需要一套完整的计算环境。** 这套环境包括：
   - 推理算力；
   - 隔离的执行环境；
   - 持久的状态和记忆；
   - 专属内存。

   云端靠每人一台 VM 解决，代价是每月几十到几百美元。
5. **长任务的可靠性与可控性仍是瓶颈。** 两个数字可以佐证：
   - dot 的越权率随任务链长度上升，见路线一 [D1-4]；
   - Agent 消耗的 token 约为对话的 4 倍，多 Agent 约 15 倍（Anthropic 一手数据）[AN1]。

   执行要可收回，状态要可恢复，算力和内存要按任务长度规划。

**判断**：云端 Agent 为每个用户配备一台云端电脑；端侧 Agent OS 则需要由手机本机提供同等的计算环境。这套环境中：

- 推理算力和隔离的执行环境，必须由系统提供；
- 持久的状态与记忆，和 Agent 自身的能力绑定，由各个 Agent 自己持有；
- 专属内存在手机上不存在：Agent 要与用户正在用的 App 共享同一块芯片、同一块内存。

因此，端侧 Agent OS 的系统层问题是：在与 App 共享资源的前提下，为 Agent 提供推理和执行两项底层能力。1.1.2 节展开这一划分。

### 1.1.2 抛开业界：端侧 Agent OS 应该做成什么样

**目标形态**：一个常驻的个人 Agent。它在用户授权范围内代为办事：读消息、排日程、跨应用下单、整理资料。同时它满足三条：

- 想得快：前台请求秒级响应，长任务的上下文不丢；
- 做得稳：出现异常时影响限定在授权范围内，能定责、能撤销；
- 不打扰：不影响用户正在使用的 App 的流畅度，不导致其被终止。

**能力蓝图**，从上到下五层，外加一个横切面：

| 层 | 内容 | 由谁提供 |
|---|---|---|
| 交互与感知 | 语音、文本、多模态入口；生成式 UI；屏幕内容、通知与消息事件的采集 | 应用框架 |
| 智能 | 意图理解、规划与编排、工具选择、自我纠错；**记忆**（各 Agent 自有） | Agent 框架（模型 + 运行时） |
| 能力接口 | 应用与系统能力的函数化声明：App Intents、AppFunctions、MCP、A2A、Skill | 应用生态 + 系统 |
| **系统服务（本次投入）** | **推理服务、执行与沙箱、内存与资源** | **OS** |
| 内核与硬件 | CPU / GPU / NPU、LPDDR 与 PIM、UFS、memcg、驱动、TEE | 内核与芯片 |
| 横切面 | 安全与隐私（身份、权限、密钥、审计），可观测与计量 | 安全体系与 OS 贯穿各层 |

**为什么系统服务只需要三项？**

Agent 替用户办事，底层只做两件事：**想**和**做**。

1. **想，对应推理服务。**
   - 一个底座模型、一块 NPU、一块 DRAM，要同时服务多个会话和多个应用。
   - 单个应用或单个 Agent 看不到别人的占用，无法统一分配。模型权重也不可能每个应用带一份。
   - 所以推理必须是系统服务。
2. **做，对应执行与沙箱。**
   - Agent 以用户身份调用应用与工具（MCP），也会被外部 Agent 调用（A2A）。它读入的内容大量来自第三方。
   - 一次调用该不该放行，必须在 Agent 之外由系统判定。由 Agent 自我约束，一旦被注入即告失效。
   - 所以执行与沙箱必须是系统服务。
3. **与应用共存，对应内存与资源。**
   - 手机上的 Agent 不独占设备。它叠加在用户正在使用的应用之上：前台应用在跑，Agent 在想、在调起别的应用。
   - 前台 Agent 与应用之间的内存、IO 与回收顺序，只有系统能协调。
   - 这一项包括两部分：
     - 通用内存管理优化，管 Agent 与应用共存；
     - 推理服务内存管理，管模型的权重、KV 与专家。

**其余能力为什么不放在 OS：**

- **交互、编排**：变化快，差异化在模型和产品层，由应用框架和 Agent 框架承担。
- **记忆**：与 Agent 的能力绑定，由各 Agent 自己持有。
  - System Agent 有自己的记忆，微信、抖音等应用的 Agent 也各有记忆。
  - 别的 Agent 需要读取用户上下文时，由 System Agent 以 MCP 或 A2A 提供读取接口，每次读取由执行沙箱判定权限。
  - 业界的做法与此一致：Siri、Gemini、小艺的记忆都随助手提供（见 1.1.3）。

**三项系统服务各自承担的角色**，用经典 OS 类比：

| 系统服务 | 类比 | 承担的关键角色 | 缺了它会怎样 |
|---|---|---|---|
| 推理服务 | 处理器 | 一个底座模型被全系统共享；长上下文推得动；把 NPU、LPDDR-PIM、UFS-PIM 这些新算力用起来；模型结构与硬件匹配 | 每个应用自带模型，内存成倍占用；长任务推不动，只能上云，成本与隐私都承受不起 |
| 执行与沙箱 | 进程隔离与保护环 | 为每个 Agent 会话划定能做什么；MCP 与 A2A 的每次调用都经系统判定；出口与凭证由系统托管；长任务可暂停、可恢复、可撤销 | 应用方不敢开放接口，Agent 做不了交易；一次提示注入即可越权 |
| 内存与资源 | 虚拟内存 | 让模型内存（权重、KV、专家）可记账、可回收、可分层，与应用内存统一协调 | 模型内存不受回收机制管理，应用被误终止，Agent 任务被中断 |

### 1.1.3 业界在三项系统服务上做得怎么样

每项系统服务按其关键要素分行。● 已具备，◐ 部分具备，○ 缺失或未见公开资料，— 不适用。

| 系统服务 | 要素 | Apple / iOS | Google / Android | 华为 / HarmonyOS | 云端 Agent（dot / Grok Bot） |
|---|---|---|---|---|---|
| 推理服务 | 系统级模型服务 | ● Foundation Models 框架向第三方开放端侧模型 | ● AICore 托管 Gemini Nano；NPU Manager 做模型级准入与卸载式抢占 | ◐ 有端侧大模型，系统服务形态未公开 | ● GPU 集群服务 |
| 推理服务 | 长上下文 | ◐ 端侧模型示例窗口 8192 token [W17] | ○ Prompt API 窗口约 4000 token [W17] | ○ 未公开 | ● 数十万到百万 token |
| 推理服务 | 稀疏模型与闪存分层 | ● AFM 3：20B 稀疏，权重在 NAND，每请求换入 1–4B [A1] | ○ 未公开 | ○ 未公开 | — |
| 推理服务 | PIM 等新型算力 | ○ | ○ | ○ | ◐ 数据中心有 HBM-PIM 原型，未大规模商用 |
| 执行与沙箱 | 应用接入方式 | ● App Intents，Siri 操作第三方应用的唯一途径 | ◐ AppFunctions 私有预览；Computer Control 预览，只开放给预装助手 [G2] | ● HMAF，2100 多项 Skill（厂商口径）[H1] | ◐ 云端浏览器与云电脑 |
| 执行与沙箱 | 按会话、按调用的权限判定 | ○ 只有 App 级权限 | ◐ Computer Control：首次操作需授权，交易时交还用户 [G2] | ◐ 高风险操作要求权限与费用确认；转账支付由系统阻断（媒体）[H2] | ◐ 环境外独立审核，敏感步骤回请用户；仍有越权 [D1-4] |
| 执行与沙箱 | 隔离、快照与恢复 | ◐ App 沙箱，无 Agent 会话边界 | ◐ App 沙箱；AVF 可用，未用于 Agent | ◐ 应用沙箱；「动态沙箱」未见官方文档 | ● 每个 Agent 一台 VM |
| 执行与沙箱 | 出口与凭证托管 | ○ | ○ | ○ | ◐ 密码与付款交回用户 |
| 内存与资源 | 模型内存记账 | ○ 未公开 | ○ Memory Limiter 只计匿名页与 swap，dma-buf / NPU 内存不在其中 | ○ 未公开 | — |
| 内存与资源 | 与应用共存的回收 | ◐ Jetsam 加内存压缩，以 12GB 作为准入门槛 | ◐ LMKD 加 memcg；抢占只能卸载整个模型 | ◐ ESWAP；HyperSpace Memory（厂商口径） | — 资源独占 |
| 内存与资源 | KV 与前缀缓存的系统管理 | ○ 未公开 | ◐ 前缀缓存按应用、按会话保存 | ○ 未公开 | ● 前缀缓存已商用并单独计价 |
| 记忆（Agent 层，参照） | 由谁持有 | Siri 个人上下文，基于系统语义索引 | Gemini 个人上下文 | 小艺记忆 | dot、Grok Bot 各自的记忆 |

**读表**：

- **推理服务**：模型托管已普及。但长上下文、稀疏模型与 PIM 等新型算力，除 Apple 的稀疏模型外，都还没有进入端侧系统服务。这正是本次投入的三项关键技术。PIM 的窗口也在打开：LPDDR6-PIM 标准接近定稿，三星 LPDDR5X-PIM 的首个商用目标是 AI PC，手机尚无厂商公开表态 [PIM]。
- **执行与沙箱**：接入方式在收敛，走向函数接口加系统托管的 GUI。但按会话、按调用的权限判定普遍缺失，各家只能整类禁止或逐次确认。
- **内存与资源**：模型内存在多数平台上不可见、不可记账，是端侧最薄弱的一环。
- **记忆**：各家都随助手提供，印证了「记忆放在 Agent 层，系统只管读取权限」的划分。

详细对比见 1.2 节各方面的原型对比表。

## 1.2 技术趋势

**各方面有一个共同趋势**：安全与资源的边界，正从「App」下移到「Agent 会话」。

云端引擎、桌面工具和学术原型已经证明，会话级的调度、隔离、记忆治理和内存分层是可行的。但端侧量产系统在这些要素上普遍缺失，缺口集中在两类：

- **跨主体**：共享、归账、授权；
- **治理**：数据标签、遗忘、可逆。

这些空白也就是本次投入的窗口。

下面每个方面先用一段话讲演进路线，再给原型对比表。表的每一列是一个技术原型，第一行是原型简介，其余各行是该组件的关键技术要素，格子是该原型在这一要素上的达成情况。图例：● 已具备　◐ 部分具备　○ 缺失或未见公开资料　— 不适用。「未核」表示该格只凭单一来源或常识，未取得一手页面。

**读表**：

1. **已做成：系统级共享底座。** 三大平台都已做到单底座多客户端；Android 与 Apple 还提供会话内的前缀缓存接口。
2. **普遍缺失：**
   - 端侧缓存都落在应用私有存储或单个会话内，没有跨应用的 KV 复用；
   - 适配器全部绑定底座版本，底座一升级，第三方适配器就要重训。
3. **只有云端或论文做成：** 细粒度抢占、KV 持久化与分块换页、多适配器并发与运行时加载。产品侧最强的抢占是 NPU Manager 的模型级卸载。
4. **计量与配额是缺口最大的一行。** 端侧没有公开的每 token 能耗计量，配额以电量命名，只有 Android 有迹可循。

### 1.2.2 沙箱：边界从 App 下移到会话，策略执行从 Agent 内移到 Agent 外

**演进路线**：

| 阶段 | 时间 | 形态 | 代表 |
|---|---|---|---|
| 一 | 移动 OS 至今 | App 级沙箱：UID 隔离、权限、entitlement；为「安装前可审查的代码包」设计 | Android、iOS、HarmonyOS |
| 二 | 2024–2026，云端与桌面 | 会话级执行环境 | 云端按会话起 microVM，池化加快照克隆（E2B；腾讯 Cube 单并发冷启动 <60ms）；桌面用进程沙箱加出口代理（Claude Code、Codex）；NVIDIA OpenShell 把默认拒绝的策略、出口代理、凭证注入和策略证明器打包成运行时；商业 Agent 普遍加了环境外的独立审核 |

- 边界从 App 下移到会话与工具调用；
- 策略执行从 Agent 自律移到 Agent 之外；
- 管控对象从代码扩展到数据。

### 1.2.4 内存管理：模型内存从「固定常驻」变成「按请求换入的工作集」，但 OS 的记账仍停留在匿名页

**演进路线**：

| 阶段 | 时间 | 形态 | 代表 |
|---|---|---|---|
| 一 | — | 为 App 设计的回收 | Android LMKD 按优先级终止进程、iOS Jetsam、zRAM / 内存压缩、MGLRU |
| 二 | 2025–2026 | 配额化 | Android 17 Memory Limiter 把每进程 memcg 限额做成默认，但只计匿名页与 swap；Linux 合入 dmem cgroup（6.14），dma-buf 的 memcg 计费 2026-05 仍是 RFC |
| 三 | 2023 起 | 模型内存的分层管理 | 云端 vLLM 的 PagedAttention 把 KV 分块管理；端侧 Apple AFM 3 把完整权重放在 NAND、按请求换入专家，已量产；Gemma 3n 的 PLE 把逐层嵌入卸到闪存；学术上 LLMS 做 KV 分块压缩换出，PowerInfer-2 在手机上按需从闪存读取神经元 |

**判断**：模型内存已经变成需要分层管理的工作集，但手机上的管理权分散在三方：

- 推理运行时；
- OS；
- 芯片厂商的 NPU 驱动。

模型内存在 OS 看来只是不透明的匿名页或 dma-buf，无法记账、无法按语义回收、无法与 App 内存统一协调。

| 要素 | Android（LMKD + memcg + Android 17 Memory Limiter） | iOS（Jetsam + 内存压缩 + increased-memory-limit） | HarmonyOS / OpenHarmony（ESWAP 等） | Linux 主线（MGLRU、dmem、dma-buf memcg RFC） | Apple AFM 3 运行时 | vLLM PagedAttention（云端参照） | LLMS（学术） | PowerInfer-2（学术） |
|---|---|---|---|---|---|---|---|---|
| **简介** | Google，2026；按进程 memcg 设 high / swap.max，节流优先于杀 | Apple；按优先级带与进程上限杀，另有压缩内存与授权加限 | 华为；应用自愿释放回调、Purgeable；OH 文档有 zswapd 换出 | 社区；MGLRU 回收、dmem 6.14 合入、dma-buf 计费 RFC（2026-05） | Apple，WWDC26（2026-06）；20B 稀疏，全量存 NAND，每请求激活 1–4B | UC Berkeley 等，2023；服务器端 KV 分块与前缀共享引擎 | Yin、Xu、Liu 等，arXiv 2024-03；LLM 作系统服务，分块 KV 压缩换出 | 上交 IPADS，2024-06；手机上神经元簇加 Flash IO 流水 |

每格出处见 [P-C4 原型对比笔记](../notes/P-C4-内存管理原型对比.md)。

**读表**：

1. **已做成的只有「传统匿名页」那一层：** 压缩交换、memcg 配额、MGLRU 类回收。这些对模型内存没有语义。
2. **所有商业 OS 与内核都缺失或只有雏形：**
   - 模型内存的统一记账：dma-buf / GPU / NPU 内存在限额之外；
   - 共享服务的代分配归账；
   - OS 层的 KV 管理。
3. **KV 的分块、压缩、换出只在云端引擎与学术原型里做成。** LLMS 自报上下文切换时延最多降两个数量级。
4. **权重分层已有两个端侧量产先例：** AFM 3 的请求级专家驻留，Gemma 3n 的 PLE。两者都避开了逐 token 的随机读取，因为手机闪存的小块随机读带宽是瓶颈。
