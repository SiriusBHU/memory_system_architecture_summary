# 第一部分 洞察

> 本部分回答两个问题：业界的 Agent OS 走到了哪一步；抛开业界，一个端侧 Agent OS 应该做成什么样，为什么推理、沙箱、记忆、内存管理是其中必不可少的四个系统组件。
> 1.2 节给出四个组件各自的技术趋势与原型对比表。

---

## 1.1 Agent OS 的发展与端侧目标形态

### 1.1.1 业界的三条路线

2025–2026 年，「让 Agent 替用户把事办完」从演示走向产品，形成三条路线。

**路线一：云端常驻 Agent，为每个用户配备一台云端电脑。**

- **代表产品**：
  - OpenAI dot（2026-09 上线）：每个 dot 有自己的云端 Linux 电脑和浏览器 [D1-2]。
  - xAI Grok Bot（2026-08-11 公测）：账号级的持久云 VM，多个 bot 共用 [D1-3]。
  - Meta Muse（2026-09）。
- **优点**：模型能力强，不受端侧资源约束。
- **代价**：
  - **成本**：按 GPU 推理加云 VM 估算，每用户每月 70–300 美元 [D1-1]。dot 只随 100–500 美元档的 ChatGPT Pro 附赠，Grok Bot 单独订阅 200 美元/月 [D1-2][D1-3]，都不是大众价位。
  - **位置**：Agent 离用户的手机、本地数据和正在用的 App 很远。
- **安全上的共识**，正在从「授权一次」转向「环境外的独立审核，加敏感步骤回请用户」：
  - dot 用独立的自动审核检查计划动作，密码与付款永远回到用户 [D1-2]；
  - Meta 用独立的 Sentinel Agent 审查动作 [M1]。
  - 即便如此，dot 在 5 步任务链上的越权率仍有 8.6%，10 步链 19.7%（OpenAI 内部数据，二手转述）[D1-4]。

**路线二：OS 内置的系统级 Agent，端云协同。**

| 平台 | 代表 | 端侧模型 | 应用接入 |
|---|---|---|---|
| Apple | iOS 27 + 新 Siri | 2026-06 的 AFM 3 Core Advanced：20B 稀疏模型，完整权重放在 NAND，每个请求只把 1–4B 激活参数换入内存 [A1] | App Intents |
| Google | Android 17 + Gemini Intelligence | 机型门槛为 12GB 以上内存 [G1] | 一路是声明式的 AppFunctions，私有预览，25 个应用用例；另一路是限定伙伴的屏幕自动化 [D1-5] |
| 华为 | HarmonyOS 7 + 小艺 / HMAF 2.0 | — | 2100 多项系统能力 Skill 化（厂商口径）[H1] |
| 荣耀 | MagicOS 11 | — | 以 MCP 和 A2A 为主，GUI 只作兜底 [R1] |

这条路线的特点是 Agent 就在手机里：靠近用户数据，直接调用本机应用，可离线，云成本由厂商承担。它的约束全部落在端侧资源上。Apple 和 Google 都以 12GB 内存作为准入门槛，iPhone 17 标准版的 8GB 被排除在最强端侧模型之外 [A2][G1]。

**路线三：整机重构的 Agent 手机。**

- **阶跃 STEPX Neo**（2026-07 亮相，16GB，3999 元）：Step AOS 用 MCP 把系统能力做成功能块 [M1]。
- **豆包手机**：靠系统特权做 GUI 自动化，二代于 2026-09 开售。150 余款应用（含微信、支付宝、淘宝、美团）拒绝被 GUI 自动化操作 [B1]。

这条路线概念上吸引力强，但出货规模小。豆包的遭遇说明，绕开应用接口去「模拟点击」，会受到应用生态的限制。

**三条路线收敛出的五个事实**

1. **应用能力函数化已成共识。** App Intents、AppFunctions、Skill、MCP / A2A 都是这一做法，GUI 模拟退为兜底。Agent 因此以「调用函数」的方式代用户执行。执行的安全边界必须由系统划定，而不是由应用各自防守。
2. **内存成为端侧 Agent 的准入门槛。** 两大平台都以内存而不是 NPU 算力作为准入门槛。没有一家公布模型的常驻内存，以及与应用共存时的回收机制。
3. **端侧模型从稠密小模型走向稀疏大模型加闪存分层。** AFM 3 把这件事做成了量产 [A1]。模型内存从此不再是一块固定大小的常驻区，而是要按请求换入换出的工作集。
4. **云端路线证明了 Agent 需要一套完整的计算环境。** 这套环境包括：
   - 推理算力；
   - 隔离的执行环境；
   - 持久的状态和记忆；
   - 专属内存。

   云端靠每人一台 VM 解决，代价是每月几十到几百美元。
5. **长任务的可靠性与可控性仍是瓶颈。** 两个数字可以佐证：
   - dot 的越权率随任务链长度上升，见路线一 [D1-4]；
   - Agent 消耗的 token 约为对话的 4 倍，多 Agent 约 15 倍（Anthropic 一手数据）[AN1]。

   执行要可收回，状态要可恢复，算力和内存要按任务长度规划。

**判断**：云端 Agent 为每个用户配备一台云端电脑；端侧 Agent OS 则需要由手机本机提供同等的计算环境。这套环境的四个部件，与经典 OS 的四项核心职能一一对应：

- 推理算力的分配，对应调度；
- 隔离的执行环境，对应进程隔离；
- 持久的状态与记忆，对应文件系统；
- 专属内存，对应虚拟内存。

在手机上，这四件事都要在「与用户正在用的 App 共享同一块芯片、同一块内存」的前提下完成。这就是 Agent OS 的系统层问题。

### 1.1.2 抛开业界：端侧 Agent OS 应该做成什么样

**目标形态**：一个常驻的个人 Agent。它在用户授权范围内代为办事：读消息、排日程、跨应用下单、整理资料。同时它满足三条：

- 出错可控，出现异常时影响限定在授权范围内；
- 随使用逐步了解用户，记忆内容用户可查看、可删除；
- 不影响用户正在使用的 App 的流畅度，不导致其被终止。

**能力蓝图**，从上到下六层，外加一个横切面：

| 层 | 内容 | 由谁提供 |
|---|---|---|
| 交互 | 语音、文本、多模态入口；生成式 UI 呈现结果 | 应用框架 |
| 智能 | 意图理解、规划与编排、工具选择、自我纠错 | Agent 框架（模型 + 运行时） |
| 能力接口 | 应用能力与系统能力的函数化声明：App Intents、AppFunctions、MCP、Skill | 应用生态 + 系统 |
| **系统服务（本次投入）** | **推理服务、执行沙箱、记忆服务、内存管理** | **OS** |
| 内核与硬件 | CPU / GPU / NPU 调度、memcg、驱动、存储、TEE | 内核与芯片 |
| 横切面 | 安全与隐私（权限、数据标签、审计），可观测与计量 | OS 贯穿各层 |

**为什么是这四个组件，而不是交互或编排？** 判据是三条，满足任意一条就必须由 OS 提供，应用和 Agent 框架做不到：

1. **跨主体共享的资源。** 一个底座模型、一块 NPU、一块 DRAM，要被多个会话和多个 App 共享。
   - 单个 App 无法获知其他主体的占用情况，因而无法统一分配与回收。
   - 推理服务和内存管理属于这一类。
2. **需要特权策略执行的信任边界。** Agent 以用户身份行事，读入的内容来自不可信的第三方。
   - 隔离、出口控制、凭证托管必须在 Agent 之外由系统执行：由 Agent 自我约束，一旦被注入即告失效。
   - 执行沙箱属于这一类。
3. **跨应用、跨时间的全局状态。** 用户的个人上下文分散在各个 App 中。
   - 统一的索引、授权和遗忘，只有系统能做。
   - 记忆服务属于这一类。

交互与编排变化快、差异化在模型和产品层，适合由应用框架和 Agent 框架承担，不在本次投入范围内。

**四个组件各自承担的角色**，用经典 OS 类比：

| 组件 | 类比 | 承担的关键角色 | 缺了它会怎样 |
|---|---|---|---|
| 推理服务 | 调度器 | 一个底座模型被全系统共享；按会话分配 NPU / GPU / CPU 算力；前台优先、可抢占；复用前缀与 KV | 每个 App 自带模型，内存成倍占用；前台请求被后台任务阻塞 |
| 执行沙箱 | 进程隔离与保护环 | 为每个 Agent 会话划定能做什么；隔离执行；出口与凭证由系统托管；高风险动作可预演、可回收 | Agent 继承用户的全部权限，一次提示注入即可导致整机失去防护 |
| 记忆服务 | 文件系统 | 跨 App、跨会话的个人上下文：统一写入、检索、授权、遗忘；带来源标签，防投毒 | 每个 Agent 各记各的，用户无法查看和删除；被注入的内容长期留存 |
| 内存管理 | 虚拟内存 | 让模型内存（权重、KV、适配器）可记账、可回收、可分层，与 App 内存统一协调 | 模型内存不受 LMKD / memcg 管理，App 被误终止，Agent 任务被中断 |

### 1.1.3 业界在这四个方面做得怎么样（简述）

| 方面 | Apple | Google / Android | 华为 / HarmonyOS | 云端 Agent（dot / Grok Bot） |
|---|---|---|---|---|
| 推理服务 | 系统级：Foundation Models 框架向第三方开放端侧模型；AFM 3 稀疏权重按请求换入 | 系统级：AICore 统一托管 Gemini Nano；Android 17 NPU Manager 做模型加载准入与卸载式抢占 | 有端侧大模型，系统服务形态未公开 | GPU 集群服务，成熟 |
| 执行沙箱 | App 沙箱成熟；Agent 经 App Intents 调用、由 Siri 编排；没有按 Agent 会话划定的执行边界 | App 沙箱成熟；AppFunctions 尚在预览；同样没有会话级边界 | 应用沙箱加意图框架；「动态沙箱」未见官方文档 | 每个 Agent 一台 VM（dot），或多 bot 共用一台（Grok）；带外审核 |
| 记忆服务 | 端侧语义索引与个人上下文，第三方读取受限 | 个人上下文随 Gemini 提供，系统级开放程度有限 | 小艺记忆，资料少 | 有记忆，但单条不可查看或删除（dot）或保留策略不公开（Grok） |
| 内存管理 | Jetsam 加内存压缩；以 12GB 内存作为准入门槛 | LMKD 加 memcg；Android 17 Memory Limiter 只计匿名页与 swap，模型的 dma-buf / NPU 内存不在其中 | ESWAP 等机制，Agent 场景资料少 | 不适用：资源独占 |

**读表**：

- 推理服务是四个方面里业界走得最远的一个：Apple 与 Google 都已经把模型做成系统服务。但它们做到的是「模型级」的托管与抢占，还没有做到「会话级」的调度。
- 执行沙箱和记忆服务，端侧都还停留在「App 级」的旧边界上，没有为 Agent 会话建立新的边界。
- 内存管理是端侧最薄弱的一环：模型内存在多数平台上不可见、不可记账。

详细对比见 1.2 节各组件的原型对比表。

## 1.2 四组件的技术趋势

**四个组件有一个共同趋势**：安全与资源的边界，正从「App」下移到「Agent 会话」。

云端引擎、桌面工具和学术原型已经证明，会话级的调度、隔离、记忆治理和内存分层是可行的。但端侧量产系统在这些要素上普遍缺失，缺口集中在两类：

- **跨主体**：共享、归账、授权；
- **治理**：数据标签、遗忘、可逆。

这些空白也就是本次投入的窗口。

下面每个组件先用一段话讲演进路线，再给原型对比表。表的每一列是一个技术原型，第一行是原型简介，其余各行是该组件的关键技术要素，格子是该原型在这一要素上的达成情况。图例：● 已具备　◐ 部分具备　○ 缺失或未见公开资料　— 不适用。「未核」表示该格只凭单一来源或常识，未取得一手页面。

### 1.2.1 推理：从「托管一个模型」到「调度多个会话」

**演进路线**：

| 阶段 | 时间 | 形态 | 代表 |
|---|---|---|---|
| 一 | 2023–2024 | 应用自带模型：每个 App 打包一份权重和推理引擎 | — |
| 二 | 2024–2026 | 系统托管共享模型：一个底座通过适配器服务多个应用 | Android AICore 托管 Gemini Nano；Apple 2025 年向第三方开放 Foundation Models 框架；Windows 预装 Phi Silica |
| 三 | 2026 起 | 模型服务开始有调度语义 | 产品：Android 17 NPU Manager 引入模型加载准入、三档优先级和「要求客户端卸载模型」式的抢占。学术：LLMS 把 KV 做成跨调用持久、分块换页的系统服务；Agent.xpu 在 NPU 与 iGPU 之间做算子级抢占，面向 Agent 的前台与后台混合负载 |

**判断**：模型服务正在沿着 OS 调度器的方向演进，关注点从「谁能用」转向四个问题：谁先用、用多少、能否被打断、被打断后状态能否保留。产品做到了第二阶段，并在第三阶段迈出了模型级的一步；会话级的调度、跨应用的 KV 复用、适配器与底座版本解耦、计量与配额，仍是空白。

| 要素 | Android AICore + NPU Manager | Apple Foundation Models（含 AFM 3） | Windows ML / Copilot+ 运行时 | HarmonyOS 端侧大模型服务 | vLLM / SGLang（云端参照） | 学术：LLMS | 学术：Agent.xpu |
|---|---|---|---|---|---|---|---|
| **简介** | Google；AICore 持有 Gemini Nano，Android 17 增系统服务 NPU Manager；量产 | Apple；系统模型是 LanguageModel 协议的一种实现，WWDC26 加入 AFM 3 稀疏模型 | Microsoft；Windows ML 共享运行时加 EP，Phi Silica 预装于 NPU；PC 形态 | 华为；小艺加意图框架，NNRt 为 NPU 北向接口；会议口径多 | 开源云端推理引擎；连续批处理、PagedAttention、前缀缓存 | 北大；把 LLM 作为移动系统服务，KV 分块压缩与换入换出；2024，原型 | 北大；NPU 与 iGPU 协同加细粒度抢占，面向 Agent 负载；2025，原型 |
| **1 系统级共享模型服务** | ● 单底座多应用共享 | ● 系统模型可被 App 共用，且可换第三方实现 | ● Phi Silica 系统预装，需 LAF 解锁 | ◐ 小艺作底座，第三方 API 与配额无文档（媒体） | ● 一个服务进程服务多客户端 （未核） | ● 提出 LLM 即系统服务 | ○ 只做调度，不涉及服务形态 |
| **2 多会话调度与优先级** | ◐ 前台限制加配额，并发返回 BUSY 不排队；NPU 三档优先级 | ◐ 调度策略未披露 | ○ 未见公开调度语义 （未核） | ○ NNRt 并发取决于驱动，仅同步推理 | ● 连续批处理、优先级调度 （未核） | ◐ 以上下文切换为目标，调度细节页面未载 | ● 区分 reactive 与 proactive 任务 |
| **3 抢占粒度** | ◐ 模型级：要求客户端卸载，任务可 PAUSED | ○ 未披露 | ○ 未见 （未核） | ○ 未见 | ◐ 请求级抢占（换出或重算） （未核） | ○ 不做算力抢占，只管上下文切换 | ● 算子 / 内核级细粒度抢占，reactive 延迟降至少 91%（自报） |
| **4 异构算力路由** | ◐ NPU 内有准入；CPU/GPU/NPU 不统一，官方 GPU 路径为主 | ◐ Core AI 在 ANE 与 GPU 间特化 | ◐ EP 按设备选 CPU/GPU/NPU，非阶段级 | ◐ NNRt 对接 NPU，无统一路由 | — GPU 集群 | ○ 未涉及 | ● NPU 与 iGPU 协同，按负载划分 |
| **5 前缀与 KV 复用、持久化** | ◐ 显式 Prefix Caching，存应用私有存储，不跨应用 | ◐ cached token 计数；系统提示 KV 是否复用未核 | ○ 未见 （未核） | ○ 未见 （待核） | ● 前缀缓存（RadixAttention 等）、跨请求共享 （未核） | ● KV 跨调用持久，分块管理 | ○ 摘要未见 （未核） |
| **6 多适配器驻留与热切换** | ◐ Google 自训功能 LoRA，不开放第三方 | ◐ 第三方适配器约 160MB，绑定单一底座版本 | ◐ 第三方 LoRA，换底座须重训 | ○ 未见 （待核） | ● 多 LoRA 并发，运行时加载 / 卸载接口，官方警告仅限可信环境 | ○ 未涉及 | ○ 未涉及 （未核） |
| **7 端云路由与隐私控制** | ◐ Private AI Compute 用于重任务，细则未披露 | ◐ 统一 API 含端侧、PCC、第三方；PCC 有证明与透明日志 | ○ 未见系统级端云路由 （未核） | ◐ 媒体称 OHTTP 匿名，无官方文档 | — 纯云 | ○ 未涉及 | ○ 未涉及 |
| **8 计量与配额** | ◐ 电量配额，短长两窗口；NPU 归账字段 | ◐ usage 含 cached token；无配额文档 | ○ 未见 （未核） | ○ 未见 （待核） | ◐ token 级统计与限速，多租户配额依部署 （未核） | ○ 不涉及 | ○ 不涉及 |

每格出处见 [P-C1 原型对比笔记](../notes/P-C1-推理原型对比.md)。

**读表**：

1. **已做成：系统级共享底座。** 三大平台都已做到单底座多客户端；Android 与 Apple 还提供会话内的前缀缓存接口。
2. **普遍缺失：**
   - 端侧缓存都落在应用私有存储或单个会话内，没有跨应用的 KV 复用；
   - 适配器全部绑定底座版本，底座一升级，第三方适配器就要重训。
3. **只有云端或论文做成：** 细粒度抢占、KV 持久化与分块换页、多适配器并发与运行时加载。产品侧最强的抢占是 NPU Manager 的模型级卸载。
4. **计量与配额是缺口最大的一行。** 端侧没有公开的每 token 能耗计量，配额以电量命名，只有 Android 有迹可循。

### 1.2.2 沙箱：边界从 App 下移到会话，策略执行从 Agent 内移到 Agent 外

**演进路线**：

| 阶段 | 时间 | 形态 | 代表 |
|---|---|---|---|
| 一 | 移动 OS 至今 | App 级沙箱：UID 隔离、权限、entitlement；为「安装前可审查的代码包」设计 | Android、iOS、HarmonyOS |

### 1.2.4 内存管理：模型内存从「固定常驻」变成「按请求换入的工作集」，但 OS 的记账仍停留在匿名页

**演进路线**：

| 阶段 | 时间 | 形态 | 代表 |
|---|---|---|---|
| 一 | — | 为 App 设计的回收 | Android LMKD 按优先级终止进程、iOS Jetsam、zRAM / 内存压缩、MGLRU |
| 二 | 2025–2026 | 配额化 | Android 17 Memory Limiter 把每进程 memcg 限额做成默认，但只计匿名页与 swap；Linux 合入 dmem cgroup（6.14），dma-buf 的 memcg 计费 2026-05 仍是 RFC |
| 三 | 2023 起 | 模型内存的分层管理 | 云端 vLLM 的 PagedAttention 把 KV 分块管理；端侧 Apple AFM 3 把完整权重放在 NAND、按请求换入专家，已量产；Gemma 3n 的 PLE 把逐层嵌入卸到闪存；学术上 LLMS 做 KV 分块压缩换出，PowerInfer-2 在手机上按需从闪存读取神经元 |

**判断**：模型内存已经变成需要分层管理的工作集，但手机上的管理权分散在三方：

- 推理运行时；
- OS；
- 芯片厂商的 NPU 驱动。

模型内存在 OS 看来只是不透明的匿名页或 dma-buf，无法记账、无法按语义回收、无法与 App 内存统一协调。

**读表**：

1. **已做成的只有「传统匿名页」那一层：** 压缩交换、memcg 配额、MGLRU 类回收。这些对模型内存没有语义。
2. **所有商业 OS 与内核都缺失或只有雏形：**
   - 模型内存的统一记账：dma-buf / GPU / NPU 内存在限额之外；
   - 共享服务的代分配归账；
   - OS 层的 KV 管理。
3. **KV 的分块、压缩、换出只在云端引擎与学术原型里做成。** LLMS 自报上下文切换时延最多降两个数量级。
4. **权重分层已有两个端侧量产先例：** AFM 3 的请求级专家驻留，Gemma 3n 的 PLE。两者都避开了逐 token 的随机读取，因为手机闪存的小块随机读带宽是瓶颈。
