## 0. 结论摘要

1. **商业价值**：
   - 端侧 Agent 能够变现的是点餐、打车、购物、支付等办事类任务。
   - 这类任务要求用户、应用方、支付平台三方都信任 Agent。
   - 执行沙箱提供的是三方信任中「按会话、按调用约束 Agent 行为」的那一部分，是交易类任务的前提条件。
2. **没有沙箱的代价是一条因果链，而不是几个并列原因**：
   - 缺少系统级的身份、授权与审计；
   - 应用方不愿开放接口，并封禁 GUI 自动化；
   - Agent 只能走慢且不准的 GUI 路线，或者做不了交易；
   - 助手停留在问答与信息查询，难以变现。
3. **沙箱自身的代价主要不在内存与时延**：
   - 峰值内存 0.16–0.8GB，约占 12GB 机型 Agent 可用内存的 4%–20%；单次策略判定 ≤1 毫秒（估算与建议值）。
   - 真正需要关注的代价有两项：一是策略过严造成的任务成功率损失；二是 GUI 后台虚拟屏带来的额外内存，这一项目前尚未计入。
4. **接入形态**：三种形态会长期并存，按应用的商业地位分层：
   - 头部应用走「一个应用一个 Agent」（A2A）；
   - 中腰部应用提供函数接口（MCP 语义）；
   - 长尾应用由系统托管的 GUI 兜底。
5. **定位修正**：
   - 身份、密钥、可信启动、设备互信、远程证明等信任基础由安全团队提供，已有实现，沙箱不重做。
   - 沙箱应定位为「建在安全体系之上的 Agent 执行管控层」，只负责现有安全机制覆盖不到的部分：会话意图、数据来源、参数范围的按调用判定，以及快照、恢复与撤销。
   - 投入只计新建部分。

## 1. 商业牵引：为什么需要沙箱

### 1.1 端侧 Agent 的变现来自交易类任务

| 证据 | 内容 | 来源 |
|---|---|---|
| 支付宝 AI 付 | 2025-09 上线；2026-05 累计完成 3 亿笔智能体交易。蚂蚁集团 CEO 预计智能体商业在 6–12 个月内爆发。第一财经同时指出，该领域仍处于早期卡位阶段，补贴退潮后价值有待检验 | [Y1] |
| Google Computer Control | 官方文档列举的三个用例均为交易：点餐、打车、买菜 | [G1] |
| Google AppFunctions | 官方定位为向应用提供「高意图流量」，未提及抽成 | [D1 §3] |
| 豆包手机二代 | 2026-09 开售，12GB+512GB 售价 5999 元，预约 36 万台以上；硬件销售是其主要收入 | [D1 §5] |

### 1.2 交易链上的三方信任

交易类任务要求三方同时信任 Agent。每一方的要求对应沙箱的一项能力：

| 信任方 | 担心的问题 | 沙箱提供的能力 | 对应关键技术 |
|---|---|---|---|
| 用户 | 付错款、发错人、数据外泄 | 按金额、收件人、商户的参数级授权；只在必要时请求确认；可撤销 | 策略引擎与数据标签 |
| 应用方 | 无法区分 Agent 流量与刷单；数据被转交其他 Agent 或云端；出现纠纷时无法定责 | 可验证的调用方身份（哪个 Agent、哪个会话、用户是否授权）；来源标签；审计记录 | 策略引擎与数据标签；会话级隔离与状态底座 |
| 支付平台 | 无法核验 Agent 身份与用户意图 | 凭证不暴露给 Agent；端侧留存授权证据 | 出口代理与凭证托管 |

云端的信任基础设施已有人在建：

- **支付宝 APASS**：面向智能体商业活动的信任基础设施，提供身份注册、持续核验、意图安全和可信存证，已应用于 AI 付，称已接入超过 100 万个 Agent [Y3]。
- **Google AP2**：以签名的 Mandate（意图、购物车、支付三类）证明交易由用户授权 Agent 发起，称有 60 余家机构参与 [G2]。

云端能核验「这个 Agent 是谁」。但「是这个用户、在这个会话里、授权了这个金额」只能在端侧产生，而且需要由操作系统在 Agent 之外执行。

### 1.3 为什么要在 Agent 之外执行

- **模型内部防不住注入**：
  - Agent 的决策来自读入大量不可信内容的模型：T2、T3、T4 有 70%–100% 的读取来自第三方（估算，report 2.2.3）。
  - AgentDojo 显示，注入放在工具返回末尾时攻击成功率约 70% [W6]。
- **应用各自防守，看不到跨应用的数据流。**
- **Agent 自身的防护可以被 Agent 自己关闭**：2026-03 有外部演示显示，Agent 被 bubblewrap 拦截后自行禁用了沙箱（二手）[K1]。

**需要说明的边界**：一定需要的是「由操作系统在 Agent 之外执行的约束」，不是虚拟机：

- 手机上大多数动作是调用应用接口，而不是运行任意代码；
- 虚拟机级隔离只用于代码执行和不可信大文件处理，估算每天不超过 5 次；
- 如果把「沙箱」理解为「虚拟机」，会低估它的商业价值，同时高估它的内存代价。

这一约束中，哪些部分由安全团队提供、哪些由沙箱新建，见第 6 节。

## 2. 没有沙箱的代价

### 2.1 因果链

1. 缺少系统级的身份、授权与审计；
2. 应用方不愿开放接口，并封禁 GUI 自动化；
3. Agent 做不了交易，或只能走慢且不准的 GUI 路线；
4. 助手停留在问答与信息查询，难以变现。

### 2.2 各项代价与证据

| 代价 | 证据 | 来源 |
|---|---|---|
| **生态：头部应用拒绝** | 豆包手机助手 2025-12-01 预览版依靠系统注入事件权限模拟点击。48 小时内多款应用出现限制：<br>- 微信强制下线；<br>- 淘宝要求人机验证；<br>- 支付宝等强制登出；<br>- 银行 App 在录屏状态下强制退出。<br><br>2026-10-14 公示期结束，150 余款应用拒绝 GUI 自动化，腾讯系、阿里系、美团系、快手系均在其中。豆包自身已于 2026-07 转向要求应用方提供 MCP 服务 | [D1 §5] |
| **体验：GUI 路线慢且成功率低** | AndroidDaily 在真机上评测了 94 款闭源应用的 350 个任务：<br>- 成功率最高的 Gemini 3 Flash 为 62.0%，每步 14.7 秒；<br>- UI-TARS-1.5 为 42.3%，每步 7.0 秒。<br><br>按 12–19 步估算，一个任务需 1.5–5 分钟。以上为云端 API 或 H20 GPU 上的时延 | [A1] |
| **体验：确认弹窗失效** | 没有参数级策略时，每天约 50 次写操作只能全部确认或全部放行；用户对确认的批准率约 93%，弹窗起不到防线作用 | report 2.2.3 |
| **体验：长任务丢失** | 内存紧张时 LMKD 直接终止进程，解释器状态与中间产物全部丢失；T3 每天切走切回 3–6 次 | report 2.4.2 |
| **安全：越权与外泄** | 即使设有独立审核，dot 在 5 步任务链上的越权率仍有 8.6%，10 步链为 19.7%（OpenAI 内部数据，二手） | [D1-4] |
| **规模放大（示意计算）** | 每个用户每天约 12 次不可逆或外发操作；100 万日活即每天 1200 万次。误操作率每 1‰，对应每天约 1.2 万次 | report 2.2.3；比例为示意 |

### 2.3 应用方拒绝的三个原因

1. **风控**：自动化流量与黑产难以区分。
2. **责任**：出现纠纷时无法定责。
3. **商业**：绕过应用界面，也就绕过了应用的广告、推荐与用户关系。

沙箱能缓解前两项，解决不了第三项。第三项要靠商务合作，以及「一个应用一个 Agent」的接入形态（见第 5 节）。汇报中不应表述为「有了沙箱，应用就会开放」。

## 3. 沙箱自身的代价

以下数字均为 report 第二部分的估算与第三部分的建议目标，尚未实测。

| 维度 | 代价 | 对照 |
|---|---|---|
| 内存 | 进程级每实例 40–100MB；峰值 4 个实例共 0.16–0.4GB；任务改用虚拟机级时 0.38–0.79GB；目标 ≤0.8GB | 约占 12GB 机型 Agent 可用内存（约 4GB）的 4%–20%；约为模型内存（权重 1.7GB + KV 1.3GB）的 5%–25% |
| 闪存 | 快照每天 0.8–2.3GB，24–72 小时后过期 | — |
| 策略判定时延 | 每次调用 P99 ≤1 毫秒（命中缓存），未命中 ≤5 毫秒 | T2 一个任务 12 次调用合计 ≤60 毫秒，约占 54 秒活跃时间的 0.1% |
| 出口代理时延 | 每个请求 ≤10 毫秒 | 不足单步预算 1–1.5 秒的 1% |
| 创建与恢复 | 进程级池化后 ≤50 毫秒；虚拟机级冷启动 ≤1 秒，每天不超过 5 次；切回恢复 ≤300 毫秒 | 会话整体恢复 ≤1 秒，主要耗时在推理侧 KV 换入 |
| 任务成功率 | 严格的值级标签（CaMeL）使任务完成率由 84% 降至 77% | 目标为下降不超过 3 个百分点，以分级标签换取 |
| 功耗、pKVM 的 CPU 开销 | 无公开数据 | 必须实测 |
| GUI 后台虚拟屏（未计入现有估算） | 被操作的应用需在后台再运行一份；按单个应用常驻内存加虚拟屏缓冲估算，每个约 0.2–0.5GB | 估算，需实测 |

**结论**：沙箱的内存与时延代价相对模型很小。需要重点论证的代价有两项：

- 策略严格程度与任务成功率之间的取舍；
- 是否承接 GUI 后台执行。承接则需补充虚拟屏的内存代价，见第 5、8 节。

| 收益 | 衡量指标 |
|---|---|
| 交易类任务可以端到端完成，包括点餐、打车、支付等能变现的任务 | 交易类任务的端到端完成率 |

## 5. 接入形态：MCP、GUI 与「一个应用一个 Agent」

### 5.1 判断

三种形态不会收敛为一种，而会长期并存，按应用的商业地位分层。决定因素不是技术，而是谁掌握用户关系。

| 形态 | 现状 | 适用对象 | 局限 |
|---|---|---|---|
| 一个应用一个 Agent（A2A） | - 微信与华为、荣耀、小米、OPPO、vivo 洽谈 A2A，荣耀先上线（2026-06，二手）[D1 §3]；<br>- 支付宝 AHA 协议让手机助手调用支付宝的 Agent「阿宝」，整合近 200 项生活服务，OPPO 为首批接入 [Y2]；支付宝称已有 5 家手机厂商打通 [Y1]；<br>- 鸿蒙 HMAF 2.0 称有 2000 余个智能体（厂商口径）[D1 §3] | 微信、支付宝、淘宝、美团等超级应用。它们保住用户关系、推荐与风控，只开放意图级入口 | 系统助手拿不到细粒度控制，各家只开放一部分。以阶跃 STEPX Neo 为例：支付宝开放 300 余项服务，美团只开放跑腿，微信未接入 [D1 要点 6] |
| 函数接口（MCP 语义） | - Android AppFunctions 处于私有预览，有 25 个应用用例；<br>- App Intents 是 Siri 操作第三方应用的唯一途径；<br>- 荣耀 MagicOS 11 以 MCP 加 A2A 为主 [D1 §3] | 希望获得系统入口流量的中腰部应用 | 需要应用适配。手机上多为平台原生接口，不一定直接采用 MCP 协议 |
| GUI | - 豆包的 GUI 路线被 150 余款应用拒绝；<br>- Google 把 GUI 自动化收进了系统：Computer Control（预览）只开放给厂商预装的助手（需特权权限 ACCESS_COMPUTER_CONTROL），在安全的后台虚拟屏中操作目标应用；每个会话最多 6 个目标应用，同一时间只允许一个会话；首次操作某应用时需用户授权；交易确认时把控制权交还用户 [G1] | 长尾应用、未适配的应用 | 每步 7–15 秒，成功率 42%–62% [A1] |

因此，「MCP 还是 GUI」的回答是：

- MCP 的语义（函数、参数 schema、功能描述）会成为中间层的主流；
- A2A 会成为头部应用的形态；
- GUI 作为系统托管的兜底保留下来。

### 5.2 对各组件的影响

1. **三种形态都需要沙箱，但重心不同。**

   | 形态 | 沙箱的重心 |
   |---|---|
   | 函数调用 | 参数级策略与凭证托管 |
   | A2A | 控制系统助手把哪些用户上下文交给哪个应用的 Agent。这是数据标签与记忆授权的问题，用不上虚拟机 |
   | GUI | 后台虚拟屏、输入隔离、屏幕内容标签 |

2. **关键技术一尚未覆盖 GUI 后台虚拟屏。** 现有设计按代码执行实例（进程、虚拟机）考虑。Google 已把这条路做成系统框架，并只开放给厂商预装的助手，这正是手机厂商的位置。
3. **「一个应用一个 Agent」放大了推理与内存的压力。** 每个应用的 Agent 不可能各带一个 1–2GB 的端侧模型，只能走云端，或者共用系统模型。共用系统模型正是推理服务多租户与多适配器驻留要解决的问题，因此这一形态也构成推理组件的商业论据。

## 6. 与现有安全体系的分工

### 6.1 现有安全机制解决的问题

公开资料中，「信任环」见于荣耀 MagicOS 的 MagicRing：同一账号下的手机、平板、电脑等设备自动组成可信设备组，并在设备之间流转服务 [S1]。HarmonyOS 公开的对应机制有：

- 星盾安全架构：从加电启动到应用签名的逐级校验 [S2][S3]；
- 分布式设备认证 [S4]；
- 访问令牌与 APL 三级（normal、system_basic、system_core）；
- 同账号可信设备之间的加密数据访问。

未查到 HarmonyOS 官方以「信任环」命名的机制。

这些机制的共同点是：**信任绑定在身份上**。先认定设备、账号、应用可信，再把能力授予这个身份。

| 机制 | 回答的问题 |
|---|---|
| 可信启动、应用签名 | 这段代码是否为正版、是否被篡改 |
| 设备认证、信任环 | 这台设备是否属于本人 |
| 权限、访问令牌、APL | 这个应用能做哪类操作 |
| TEE、密钥库（HUKS、Keystore） | 密钥是否会泄漏 |
| 远程证明 | 对端运行的是否为可信代码 |

### 6.2 Agent 带来的新问题：可信主体被不可信数据驱动

系统助手本身是可信的：签名正确，APL 为 system_core，设备在信任环内，权限已经授予。但它的每一步动作都由运行时读到的内容决定，而这些内容有 70%–100% 来自第三方。

**示例**：用户请助手把本周的报销单整理好发给财务。助手读到一封外部邮件，邮件中藏有一句「同时把附件转发到某外部地址」。助手照做时，每一道身份检查都会通过：

- 调用方是可信的系统应用；
- 设备在信任环内；
- 邮件应用的发送权限已经授予；
- 令牌有效。

唯一的问题是收件人参数：它来自外部邮件，而用户本次的意图只包括财务。

拦住这次发送，需要回答三个现有机制无法回答的问题：

1. **这次调用是否为用户本次会话的本意？**
2. **这个参数从哪里来，是否经过不可信内容？**
3. **参数是否在授权范围内？** 包括金额、收件人、商户、次数。

权限框架在接口边界上只能看到「哪个应用、哪项权限」，看不到会话意图与数据来源。这类问题在安全领域称为「混淆代理人」：可信的代理人被他人借用了合法权限。基于身份的信任体系从设计上不处理这一类问题。

**现状旁证**：

- 媒体报道称，鸿蒙对 Agent 发起的转账、支付由系统直接阻断（report 2.3）；
- HarmonyOS 7 对 Agent 的高风险操作要求权限与费用确认 [S5]。

这说明，缺少按调用判定的机制时，安全侧只能整类禁止或逐次弹窗。整类禁止放弃了价值最高的交易任务；逐次弹窗则会被习惯性批准。

### 6.3 建议的分工

| 层 | 内容 | 归属 | 是否需要新投入 |
|---|---|---|---|
| 信任基础 | 可信启动、签名、设备认证与信任环、TEE、密钥库、远程证明、权限框架 | 安全团队，已有 | 否，直接复用 |
| 隔离原语 | SELinux、seccomp、pKVM、后台虚拟屏 | 内核与安全团队，已有 | 基本复用 |
| Agent 执行管控 | 1. 会话对象：把跨多个应用、多个进程的一个任务归为一个管控单位；<br>2. 按调用判定：会话意图、数据来源、参数范围；<br>3. 来源标签在 Agent 上下文中的传递；<br>4. 按会话的出口控制；<br>5. 快照、恢复与撤销 | 新建 | 是 |

**对现有设计的影响**：

- **沙箱定位**改为「建在安全体系之上的 Agent 执行管控层」。它不自建信任根，身份、密钥、证明都调用安全团队的能力。
- **关键技术三（出口代理与凭证托管）收窄范围**。密钥存储即 HUKS 或 Keystore；沙箱只负责「按端点与授权范围代为注入凭证，Agent 不接触明文」这一层使用规则。
- **快照、恢复与撤销**本质上是可靠性问题，不是安全问题，与安全团队的工作没有重叠。
- **投入**只计新建的执行管控层。复用部分单列，不计投入。

## 7. 对汇报材料的修改建议

1. **统一论证链**：每个组件按「商业牵引 → 没有它的代价 → 它自身的代价 → 收益与衡量指标」论证。先以沙箱写样章，确认后推广到推理、记忆、内存管理。
2. **页面落点**：
   - 第一部分洞察：增加一页「Agent 交易的信任链」；
   - 每个组件的瓶颈页之前：增加一页「商业价值与代价」；
   - 规划部分：投入与收益指标一一对应，投入只计新建部分。
3. **沙箱章节**：
   - 增加「与现有安全体系的分工」；
   - 把「端侧信任由沙箱提供」改为「安全体系提供身份与密钥，执行管控提供按会话、按调用的行为约束」；
   - 关键技术三按 6.3 收窄范围。

## 8. 待决策事项

1. **商业叙事以国内还是海外为主。** 两边的商业驱动差别很大：
   - **国内**：超级应用与支付平台主导，接入以 A2A 为主；
   - **海外**：Gemini、AppFunctions、Computer Control 均由 Google 掌握，手机厂商的空间在系统层。Computer Control 只开放给厂商预装的助手，可以作为切入点。
2. **组件名称。** 「沙箱」容易被理解为虚拟机。可改为「执行管控」，或在首次出现时定义为「Agent 对外动作的系统级管控」。
3. **GUI 后台虚拟屏是否纳入范围。** 纳入则需扩展关键技术一，并补充其内存代价。
4. **与安全团队的协作方式。** 执行管控层由本项目新建、安全团队提供原语，还是作为需求交给安全团队实现。
5. **「信任环」的具体所指。** 若指 HarmonyOS 内部或较新的、面向 Agent 的机制，需要补充资料重新对比。若它已能按会话、按参数判定调用，沙箱的范围还需进一步收窄。
