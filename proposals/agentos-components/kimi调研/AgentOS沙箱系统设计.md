# AgentOS 沙箱系统设计：从基础组件到关键技术

**文档状态**：设计草案（v0.1）
**面向读者**：软件工程师、系统架构师
**日期**：2026-11-06

---

## 1. 背景与动机

端侧 Agent 的落地瓶颈不是模型能力，而是操作系统基础设施。当前第三方 Agent 在移动设备上的实现路径（无障碍服务 + 截屏理解）存在结构性缺陷：Agent 继承用户的全部环境权限，信任是二元的——要么不用，要么交出一切；一次 prompt injection 等于整机沦陷；实现路径随系统与应用版本更新不断失效。

本文件讨论 AgentOS 的基础设施拆解，并聚焦其中**沙箱子系统**的功能定义、构建难点与关键技术。核心论点：沙箱不是限制 Agent 的机制，而是让 Agent 被允许自主行动的前提；它将"审查"（人工、不可扩展）替换为"结构性保证"（自动、可扩展），是 Agent 应用生态成立的基础条件。

## 2. AgentOS 基础组件拆解

### 2.1 设计原则

整个 AgentOS 的组件划分遵循三条原则：

1. **机制与策略分离**。每一层都要回答：哪些是 OS 必须提供的机制（mechanism），哪些是 Agent 保留的策略（policy）。例如记忆框架中，OS 提供存储与索引机制，Agent 决定记什么、何时检索。
2. **两个问题的剃刀**。判断某能力是否应进入 OS：（a）单个 Agent 或厂商能否自行实现？能，则不进入；（b）是否需要跨 Agent 仲裁或跨厂商信任？需要，则必须由 OS 兜底。
3. **状态生命周期独立性**。判断一个新机制能否并入既有子系统：若其状态的生命周期独立于宿主层，则独立成层；否则复用。

### 2.2 核心四层

AgentOS 的基础能力收敛为四个核心子系统，与经典 OS 子系统存在精确映射：

| 子系统 | 经典 OS 对应 | OS 提供的机制 | Agent 保留的策略 |
|---|---|---|---|
| 推理框架 | 计算抽象与调度器 | NPU HAL、模型加载/分页/LoRA 热插拔、多租户推理调度与 QoS、token 计量 | prompt、解码策略、模型选择 |
| 沙箱框架 | 进程模型与保护环 | 能力调用契约、代码执行隔离、来源分级与污点追踪、凭证隔离 | 工具选择、任务编排 |
| 记忆框架 | 文件系统 | 向量/图谱索引、ACL、跨 Agent 共享区、持久化与一致性 | 记什么、忘什么、何时检索 |
| 内存管理 | 虚拟内存 | 权重与 KV cache 分页换出、内存压力信号、上下文预算 API | 上下文内容选择、压缩与摘要策略 |

内存管理子系统管理的三种资源值得单独说明：**模型权重驻留**（GB 级，必须可分页）；**KV cache**（PagedAttention 本质上是 KV cache 的虚拟内存，OS 化之后即多 Agent 共享 KV 的调度）；**上下文窗口**（模型的"地址空间"，长期记忆相当于磁盘，检索相当于缺页换入）。

### 2.3 辅助子系统

除核心四层外，以下子系统满足剃刀条件、必须存在于 OS 层：

- **命名与发现 / IPC**：能力注册中心与 Agent 间通信，并入沙箱框架作为接口契约层。
- **事件总线**：Agent 主动性（proactivity）的前提是被事件唤醒而非轮询。传输层复用现有 IPC（Binder/XPC），语义层是新的：可回放的持久日志、类型化 topic 与注册中心、能耗感知投递、权限化订阅（topic 级 ACL 与字段级脱敏）、背压与配额。定位：从 signal → message → durable log 的第三级阶梯。
- **记账与可观测**：token 是新的 CPU 时间，需要 cgroups 式配额核算与审计。
- **身份与委托（薄残差）**：身份管理归应用自管，OS 只保留两块——硬件锚定的信任根（Attestation：回答"这东西是真的吗"，不回答"它是谁"），以及跨应用委托链上的不升级规则（confused deputy 防护）。
- **能耗管理**：分级唤醒链（sensor hub → 微型模型 → 大模型 → 云端），任务级能耗预算。
- **监督界面层**：权限确认、任务进度、急停、操作回放、undo 入口必须由系统拥有——被授权的 Agent 不能自己渲染自己的授权弹窗。
- **版本与行为兼容**：底座模型升级会静默改变所有 Agent 行为（"概率 ABI"问题），需要模型版本化、随 OTA 的行为回归套件、灰度与回滚。
- **任务运行时**：任务语义（分解、ReAct 循环）归 Agent；但 checkpoint/restore、生命周期事件、多 Agent 资源仲裁的机制必须归 OS——否则移动端后台限制与多 Agent 共存都不成立。

## 3. 沙箱的功能定义

### 3.1 定义

沙箱子系统是 Agent 所有对外动作的**唯一通道**：无论动作来自模型输出、事件回调还是 IPC，都必须、且只需经过沙箱。其结构收敛为三层：

1. **第零层：隔离边界**。进程隔离、seccomp、VM/TEE 等禁锢机制。该层基本是现有 OS 能力，沙箱子系统**配置**它而非新建它，但必须在架构中显式存在——接口面与权限管理都依附于"边界真实存在"这一前提。
2. **块一：统一接口面（结构层）**。定义"能做什么"的形态：能力契约、命名发现、来源标签、装配投影。
3. **块二：权限管理（决策层）**。判定"这次能不能做"：分档分层体系、信任根、三时机执行、跨链规则。

### 3.2 身份模型

"身份"由四种生命周期不同的 artifact 构成，是架构争论的焦点，最终分工如下：

| Artifact | 生命周期 | 归属 |
|---|---|---|
| 主体身份（发布者证书、二进制/模型哈希） | 永久 | 应用自管，OS 仅提供 Attestation 原语验证 |
| 代表关系（Agent ↔ 用户绑定） | 长期 | 应用自管 |
| 委托令牌（scope、限额、有效期） | 中期 | 应用自管语义，OS 在调用时验证 |
| 接口面 | 随沙箱实例生灭 | OS 按令牌投影生成 |

关键设计关系：**身份是源，沙箱的权限面是身份的投影**。强制执行发生在沙箱内，但授权判定（用户同意、策略协商、scope 签发）发生在沙箱外。分档分层体系由 OS 拥有（语义、同意 UX、装配逻辑）；应用的角色↔档位映射以 manifest 形式**声明**，由系统执行——"应用自管"指声明权，不是应用内部自行判断。

### 3.3 接口面设计

接口面是沙箱中唯一的纯原创设计工作——它定义了"Agent 能做的事"这门语言本身。

**分层接口体系**，解决通用性与可治理性的矛盾：

- **L0 逃生舱：raw 代码执行**。沙箱内可执行任意代码，但代码的所有效果（出网、写盘、调应用）必须经接口面流出。可执行任意代码 ≠ 可产生任意效果。L0 保证完备性。
- **L1 结构化动作接口**：常用任务的结构化路径，提供 dry-run、undo、审计、精确授权。设计目标是覆盖约 80% 任务，**L0 逃生率**作为接口体系健康度的核心在线指标。

**接口的单位是"动作"而非 syscall**：`file.read`、`http.fetch`、`app.invoke`、`message.send`、`payment.charge`——Agent 可规划的最小语义单位，自带结构化输入输出与效果描述。

**接口规格七要素**：

1. input/output schema（结构化、可校验）；
2. 效果描述（自然语言 + 结构化，供 dry-run 与确认 UI 使用）；
3. dry-run 实现（`dry_run=true` 返回效果预览，Agent 规划与用户确认共用）；
4. 可逆性声明与 undo token；
5. 幂等键（重试安全）；
6. 异步语义（长动作返回任务句柄，完成事件走事件总线回调）；
7. 结构化拒绝（denial 返回"为什么被拒、如何申请更大 scope"，构成"请示通道"）。

外加**注册表**：运行时可查询当前沙箱的接口清单与约束，供 Agent 规划器作为能力清单使用。

### 3.4 权限管理

**权限是参数化约束，不是布尔值。** 每个接口定义自己的权限参数空间：

| 接口 | 权限参数示例 |
|---|---|
| `http.fetch` | 域名白名单、速率、流量上限、是否允许带凭证 |
| `file.*` | 路径集合、读写分离、配额 |
| `payment.charge` | 单笔上限、总额度、商户范围、次数 |
| `message.send` | 收件人范围、条数、内容来源限制 |

**三维风险模型定档**：每个接口按外部性（效果是否越出沙箱）、可逆性（能否 undo）、敏感度（触碰的数据分类）打分定档；档位决定同意形式（默认放行 / 会话级授权 / 每次确认）。**数据分类标签随数据流过接口**：`http.fetch` 产出"不可信内容"标签，`message.send` 接受不可信内容时自动升档确认——这是防注入在接口层的落点。

**三时机执行**：装配时（按委托令牌与映射投影接口面）、调用时（每次调用判定——撤销、额度递减、跨链判定都发生在运行时）、销毁时（清算）。运行时判定是主战场；LSM 的先例即 hook 打在每次系统调用上，而非仅在 exec 时检查一次。

**跨链不升级规则**：委托链上每跳有效权限不超过链上最小值，由系统强制——它同时约束两个互不信任的应用，应用无法自行保证。

**凭证经纪人**：凭证存于沙箱外 vault，出口代理按（目标端点 × 令牌 scope）注入，Agent 不见真凭证；响应侧脱敏防回泄。

### 3.5 沙箱提供的核心能力

1. **有界的爆炸半径**：最坏情况等于该档位的接口面，而非整台设备——保险与定价的前提；
2. **可验证的声明**："我的 Agent 做不了 X"从承诺变为机制，信任基础从人品换成结构；
3. **可归责**：所有动作经过单一通道，可记录、可回放、可定责；
4. **可组合**：其他应用敢于向 Agent 暴露能力，因为强制执行是结构性的。

对生态的意义：移动应用经济的爆发依赖"安装应用成为低风险行为"（商店审核 + 沙箱压低风险保费）；Agent 以机器速度自主行动，人工审核无法扩展，只有结构性禁锢可以。对开发者，责任上限可界定才可投保、可投资。

### 3.6 与指令遵从的关系

指令遵从可分解为四个成分：理解精度、规划精度、边界遵从、抗干扰。沙箱**不提升精度，提升可保证性**：对理解与规划无能为力；对边界与抗干扰，将概率问题（模型是否愿意）改写为确定性问题（环境是否允许）。统计上说：不动分布的均值，压缩方差、抬高下限——最坏情况从"整机沦陷"变为"任务失败"。

四条间接提升精度的路径：训练态的干净奖励信号（边界由环境强制的 RL 环境中，违规动作物理不存在）；可度量性使遵从首次成为可优化指标；请示通道将边界模糊地带的"猜"换成"问"；拒绝信号作为观测支持在线纠偏。

## 4. 业界现状与差距分析

### 4.1 移动平台的原生沙箱

三家移动 OS 均有成熟的应用级沙箱，但共同假设是：**沙箱主体为"已安装的应用"，绑定发生在安装期，权限面静态**。

- **Android**：安装时为每个应用分配唯一 UID、隔离进程空间，Android 5 起以 SELinux 强制访问控制实施沙箱，Android 10 引入分区存储。后续出现 SDK Runtime（将第三方广告 SDK 关入应用内独立隔离环境），是"应用之内再分主体"的先例。端侧另有 AVF（Android Virtualization Framework）提供受保护 VM。
- **iOS**：自 2008 年 SDK 起，每个应用一个 UUID 容器目录，进程层以 TrustedBSD MAC（Seatbelt 内核扩展）强制隔离；entitlement 为加密绑定的声明，由 Apple 在分发时校验；密钥与生物特征存于独立 ARM 核 Secure Enclave。
- **HarmonyOS NEXT**：星盾安全架构，获 CCRC EAL5+ 认证；Access Token 权限框架将应用分为三级 APL（normal / system_basic / system_core），按等级开放权限范围——已是量产系统中的"分档分层"；从"管权限"转向"管数据"：禁用通话记录、短信、已安装应用列表等 9 类权限，图库访问走系统 Picker 按张授权——是"语义数据门户"的雏形；其"基于动态沙箱的数据权限管控"（为数据分享场景动态安装带权限定义的沙箱、在接收方延伸控制）是现存最接近"动态生成、任务级沙箱"的机制。

### 4.2 云端 Agent 沙箱

- **E2B**：Firecracker microVM per session，Apache 2.0，生态集成最全（自称 10 万+ 团队、94 家 Fortune 100），其 API 形状已成事实标准。
- **Daytona**：sub-90ms 冷启动；2026 年 6 月起转闭源，10 月完成 6000 万美元 B 轮。
- **Modal**：gVisor 与 VM 双运行时，GPU 场景。
- **Vercel / Cloudflare**：active-CPU 计费派。
- **Cube（腾讯云开源，2026 年 5 月）**：RustVMM + KVM microVM，独立内核冷启动 <60ms、单实例内存 <5MB、单机 2000+ 实例；快照/克隆/回滚、AutoPause/AutoResume；兼容 E2B API；支撑腾讯元宝与 MiniMax 的 Agentic RL 训练（分钟级调度数十万实例）。**注意：Cube 是腾讯云的产品，并非 NVIDIA 的。**
- **NVIDIA OpenShell（2026 年 3 月 GTC 发布，Apache 2.0）**：策略治理层的代表。Landlock LSM + seccomp-BPF 带外执法；声明式 YAML 编译为 OPA/Rego；文件/网络/进程/**推理**四策略域（Privacy Router 按策略路由推理请求）；凭证经纪人；策略变更在生效前经形式化验证（policy prover 证明变更新增放开了什么）；policy advisor 支持 Agent 提议窄范围新策略、默认挂起人工审批。NVIDIA 的战略动机：Agent 能做什么与企业允许其做什么之间的鸿沟是 agentic AI 采用的最大瓶颈，开源信任层以拉动算力销售；Sentry 执法层下沉至 BlueField-4 硬件。
- **Anthropic Claude Code**（2025 年 10 月）：本地开发 Agent 引入文件系统与网络双重隔离的沙箱执行，是"编程类 Agent 默认沙箱化"的标志性动作。
- **Kubernetes 社区 agent-sandbox 项目**：以 CRD 管理隔离的、有状态的 Agent 环境，支持 gVisor / Kata，代表云原生生态对 Agent 运行时原语的标准化尝试。
- **Google Agent Sandbox（基于 gVisor）** 与 **AWS Strands Box**（2026 年 10 月）：平台厂商将 Agent 执行环境产品化的动作。

### 4.3 威胁模型的反转

传统沙箱防的是"可审查的恶意代码"——代码确定、审查在安装前。Agent 沙箱防的是"审查时刻还不存在的代码"——LLM 现场生成。由此产生第一设计原则：**假设 Agent 已经沦陷，执法层必须在 Agent 够不到的地方**。另一个反直觉教训：2026 年 9 月两次最著名的 Agent"逃逸"（OpenAI 与 Gemini）均非打破隔离层，而是网络出口配置错误（DNS 可出网、互联网访问未关）。新手易将预算花在隔离强度上，真实风险在出口治理。

### 4.4 差距与空白

移动平台沙箱回答"这个**应用**能否读通讯录"，无法回答"**这个动作**是否在用户委托的 scope 内"。Agent 沙箱相对现状的三个转变：

1. **主体从应用变为任务/会话**：运行时随时 spawn、用完即毁；
2. **绑定从安装期变为创建期**：接口面由委托令牌投影，而非 manifest 声明一次管终身；
3. **权限面从静态变为逐次调用判定**：额度递减、中途撤销、跨链不升级。

当前空白点：**端侧 Agent 会话级沙箱、NPU/GPU 隔离、指令级授权投影、策略形式化验证的平民化**。

### 4.5 学界视角：沙箱思想的学术谱系

- **能力安全（Capability-based Security）**：object-capability 模型（Miller 等）与 seL4 的 capability 机制确立了"权限随引用传递、默认无权限"的范式——本设计的分档分层、令牌投影、跨链不升级规则，均可视为该范式在 Agent 语义层的实例化。Confused deputy 问题（Norm Hardy，1988）正是跨链不升级规则要防御的经典攻击原型。
- **LLM Agent 安全**：CaMeL（Google DeepMind，2025）首次将 capability 机制系统化应用于 LLM Agent——能力令牌、策略约束与信息流追踪，从学术上验证了"来源分级 + 参数化权限"路线的可行性；AgentDojo（NeurIPS 2024）建立了 Agent 注入攻防基准；InjecAgent、AgentPoison 等工作建立了注入攻击的测量方法。
- **从业者共识**："致命三要素"（私密数据访问 + 不可信内容输入 + 对外通信能力，三者同现即构成高危组合）与本设计按"外部性"维度定档的思路一致。
- **隔离技术谱系**：Firecracker（NSDI 2020）以极简 device model 证明 microVM 可兼得硬件级隔离与毫秒级启动；gVisor 的用户态内核路线以部分兼容性换取更小的可信基；Wasm 研究提供了语言级隔离的另一极。
- **逃逸基准自动化**：SEB（Sandbox Escape Benchmarks）用 Agent 合成逃逸载荷进行防御基准测试，提示"红队自动化"正在成为沙箱工程的标准实践。

## 5. 构建难点与技术挑战

**C1. 隔离底座选型——隔离强度、启动速度、单机密度三者不可兼得。** 谱系：容器（共享内核，逃逸面最大）→ gVisor（用户态内核拦截 syscall，存在兼容性缺口）→ microVM（Firecracker：约 125ms 启动、约 5MB 额外内存，当前不可信代码的默认答案）→ 全 VM；Wasm isolate 更快（亚 10ms、亚 2MB）但生态窄。端侧特有约束：无随意可用的 KVM（Android AVF 能力受限）、功耗与热约束、**NPU/GPU 隔离为行业空白**（Firecracker 设计上不支持 GPU 直通）。

**C2. 带外执法——假设 Agent 已沦陷。** 策略判定若跑在沙箱内，被攻破的 Agent 可直接改写之。所有执法点必须带外。

**C3. 策略系统的不可能三角。** 表达力 × 可验证性 × 运行时开销。策略太粗无价值、太细判不动；运行时逐次判定不能成为热路径瓶颈；策略热更新与进行中会话的一致性语义需要定义。

**C4. 状态与生命周期——成本结构的生死线。** Agent 负载 71%–98% 的时间在等待模型响应（Vercel 公开数据），快照/暂停/恢复不是优化而是命脉；计费模式（wall-clock vs active-CPU）实际成本差 6–10 倍。

**C5. 可观测、审计与合规。** "出事能定责"是售卖前提；SOC 2 Type II / HIPAA 已是企业准入门票。

**C6. 对抗性回归。** 逃逸与注入测试必须进 CI 而非一次性测试；新动向是用 Agent 自身合成逃逸载荷做基准（SEB 方法论）。

**C7. 生态与开发者体验。** E2B API 形状已是事实标准；采用率的真正决定因素是开发者体验（本地调试、策略 dry-run、镜像模板）。

**C8.（端侧特有）系统资源与同意链路集成。** 与系统权限框架对接、系统拥有的同意 UX、OS 生命周期联动、NPU 访问中介化。

## 6. 关键技术（与挑战对应）

### 对应 C1：隔离底座

- **microVM（首选）**：Firecracker 或 Cloud Hypervisor；配套内核裁剪（精简 device model）、模板镜像 + 快照恢复替代冷启动、预热池。
- **用户态内核（备选）**：gVisor，必须先跑 syscall 兼容性测试套件——部分冷门 syscall 会中断，运行时依赖清单需先验证。
- **K8s 集成路径**：Kata Containers，或 Google 系 agent-sandbox 项目（管理隔离的有状态 Agent 环境）。
- **内存去重**：KSM、userfaultfd 懒加载——单机密度从几百提升至 2000+ 的关键。
- 决策依据：威胁模型决定隔离级别；**不要自研 VMM**（腾讯 Cube 可复用其 Serverless 存量，属特例）。

### 对应 C2：带外执法

- **内核级强制**：Landlock LSM（文件系统）、seccomp-BPF（syscall 白名单）、eBPF（网络与观测）。
- **策略引擎带外**：OPA 运行于沙箱外 daemon，沙箱内只留 enforcement proxy，不留 policy decision。
- **出口代理（最高优先级）**：L7 proxy 部署于 net namespace 之外；默认拒绝 + 域名/方法级白名单；**DNS 强制劫持**（直接对冲 2026 年逃逸教训）。
- **凭证经纪人**：凭证存外部 vault，出口代理按（端点 × 令牌 scope）注入 header；响应侧脱敏。
- 业界参照：OpenShell 带外架构；E2B（出口代理注入）、Daytona（占位符替换 + 响应脱敏）、Vercel（防火墙层经纪人）、Cloudflare（凭证留 Worker）。

### 对应 C3：策略系统

- **策略语言**：声明式 YAML 编译至 Rego/OPA；或选 Cedar（AWS 授权语言，自带形式化分析工具链，做策略 diff 证明更顺手）。
- **默认拒绝** + 四域建模（fs / net / proc / inference；端侧加 sensor、UI）。
- **热路径优化**：决策缓存（策略版本 + 输入哈希）、高频路径本地判定、审计异步落盘。
- **版本钉住语义**：会话创建时绑定策略版本，热更新仅影响新会话。
- **策略即代码**：git 管理 + CI review + 签名；变更产出"新增放开项"报告挂人工审批。
- 业界参照：OpenShell 的 YAML→Rego 编译与变更前形式化验证。

### 对应 C4：状态与生命周期

- **文件系统快照**：overlayfs / ZFS snapshot（CoW）。
- **内存快照与恢复**：Firecracker snapshot（内存 + 设备态）；userfaultfd 懒恢复将 resume 压至亚秒；CRIU 仅作进程级补充。
- **AutoPause/Resume**：空闲检测（网络静默 + CPU 阈值）触发暂停，请求到达触发唤醒；目标 standby 恢复 <25ms（Blaxel 已达成）。
- **分叉克隆**：一份快照拉起 N 个实例——RL 训练与并行探索的基础。
- **密度与计费**：cgroup 内存回收 + balloon；active-CPU 计量（cgroup cpuacct 采样）。
- 业界参照：Cube 的快照/克隆/回滚与 AutoPause；Morph 的"暂停后分叉为平行轨迹"。

### 对应 C5：可观测与审计

- **结构化决策日志**：每次 allow/deny 记录（sandbox_id、policy_version、target、binary、decision）五元组。
- **不可抵赖**：append-only 存储 + 日志哈希链签名。
- **全链路追踪**：OpenTelemetry 贯穿 agent loop → tool call → policy decision。
- **遵从度指标**：越界尝试率、denial 分类统计——使"指令遵从"可测量。
- **合规件**：SOC 2 / HIPAA 的日志保留与访问控制要求在设计期埋入，事后补齐成本高。

### 对应 C6：对抗性回归

- **逃逸测试自动化**：已知 CVE payload 库 + Agent 合成逃逸载荷（SEB：数千自适应合成载荷）。
- **注入语料回归**：维护 prompt injection 攻击语料库，验证"被注入时有效动作集不变"。
- **fuzzing**：syzkaller 针对自研 VMM / 用户态内核。
- **红队常态化**：策略引擎或底座升级触发全套回归；上线后设逃逸赏金。

### 对应 C7：生态与开发者体验

- **API 兼容**：直接兼容 E2B API 形状（Cube 即采用此策略），不自创标准。
- **SDK 五语言**（Python/TS/Go/Java/Rust）+ 本地模式（Docker 后端）供离线调试。
- **MCP 网关**：工具以 MCP server 形态注入沙箱。
- **策略 dry-run 模拟器**：回放历史 trace 显示新策略"会拦截什么"——缺此功能则策略系统无人敢用。
- **镜像模板生态**：预置浏览器、代码解释器等模板。

### 对应 C8：端侧集成

- **承载**：Android AVF 的 pVM 或 TEE（Trusty）；NPU 隔离需 HAL 层中介代理推理请求，顺带实现端侧版 privacy router。
- **权限对接**：分档映射至系统权限框架（Android runtime permission / 鸿蒙 APL）。
- **同意链路**：系统弹窗 → 令牌签发 → 沙箱装配。
- **OS 生命周期联动**：onTrimMemory / Doze 信号触发 AutoPause，而非被系统直接杀死。

## 7. 与负载建模、系统仿真的结合（立项视角）

本部门的两个技术方向与沙箱构成天然闭环：**负载建模是仿真的输入，仿真是负载建模的验证器**。与业界玩家的关系是错位竞争——E2B 建执行、OpenShell 建规则、Cube 建密度，而"负载科学"与"仿真验证"目前是空白。

### 7.1 负载建模 → 接口清单与分档定档

**挑战 A1：Agent 负载的表示。** Agent 负载是概率的、语义的、长尾的、随模型升级漂移的，传统 SPEC/TPC 式建模假设（操作集合确定、分布平稳）不成立。
关键技术：动作 taxonomy + 参数化约束空间（建模单位为"动作类型 × scope 参数"）；结构化 action trace 采集规范（OpenTelemetry 语义扩展 + 差分隐私/联邦采集）；动作转移图/Markov 模型与 Zipf 长尾拟合；合成负载（Agent 自生成任务补冷启动，需真实性校验防自我强化）。

**挑战 A2：覆盖率的可计算定义。** "接口清单覆盖 80% 任务"必须是可证伪命题。
关键技术：动作空间上的概率质量覆盖度（覆盖的动作簇概率质量，非种类数）；L0 逃生率在线指标 + 离线缺口报告；未覆盖动作自动聚类 → 新接口提案的数据驱动演化（与编译器 PGO 同构的"profile 指导设计"流程）。

**挑战 A3：分档定档的定量化。**
关键技术：频率 × 风险双目标优化——在"期望摩擦成本 ≤ 体验预算、期望风险 ≤ 风险预算"约束下求最优档位分配（与缓存层次设计同问题结构）；风险评分数据化（三维模型 + 真实事故库与红队结果）；档位敏感性分析（依赖仿真）；负载漂移监测与档位表定期再校准管道（"概率 ABI 回归"在负载侧的对应物）。

### 7.2 系统仿真 → 云上仿真与云下真实匹配

**挑战 B1：环境保真。**
关键技术：Android 模拟器镜像裁剪 + ARM 服务器原生运行（避免 x86 转译失真）；iOS 为诚实约束（闭源，仅小规模真机农场 + API 级 mock，覆盖声明需写明边界）；应用环境快照化（预装应用矩阵、账号态注入、数据 fixture）；保真度度量（同一 trace 在仿真与真机的动作成功率/时延分布 diff、UI 元素命中率）；小规模真机群作为 ground truth 持续校准。
业界参照：Firebase Test Lab 等设备农场、Corellium（ARM 虚拟化）。

**挑战 B2：负载保真——两个方向的耦合点。**
关键技术：负载模型驱动负载生成器（A 的输出是 B 的输入）；真实 trace 脱敏后回放（参照 Oracle RAT 的 workload replay、TRex 的流量生成）；分布对齐的持续监控（trace 分布的 KL / Wasserstein 距离）。

**挑战 B3：规模与成本。**
关键技术：沙箱生命周期技术复用（一份环境快照 fork 千个仿真实例，快照/分叉/休眠同时服务生产与仿真）；场景矩阵自动 sweep（应用版本 × 档位表 × 负载模型版本）；时间加速（以录制的模型响应做 time-accelerated replay）。
业界参照：自动驾驶仿真体系（Waymo 的 scenario library + replay + fork）。

### 7.3 闭环：仿真结果回流设计

- **策略/档位 A/B**：真实会话状态 fork 进仿真，对比不同档位表的 denial 率、任务成功率、越界率；
- **遵从度 benchmark**：仿真中跑注入攻击语料集，产出沙箱安全评分（SEB 的端侧治理版）；
- **上线门禁**：新接口、新档位表须过仿真回归 + 真机抽检方可发布——仿真即"概率 ABI 回归套件"的载体。

**立项风险提示**（需主动写入）：负载冷启动（公开任务集 + 合成 + 小规模真实采集，初期模型置信度低）；iOS 环境保真存在硬上限。

## 8. 落地路线

| 阶段 | 内容 | 理由 |
|---|---|---|
| P0 | 威胁模型文档 → 隔离底座选型（C1）→ 出口代理 + 凭证经纪人（C2） | 2026 年逃逸教训证明真实风险在出口治理 |
| P1 | 策略系统 v1（默认拒绝 + 四域）（C3）→ 生命周期原语（C4） | 成本结构跑通才有商业模型 |
| P2 | 审计与度量（C5）→ 对抗回归（C6） | 企业准入门票 |
| P3 | 生态与开发者体验（C7）→ 端侧集成（C8） | 决定规模化 |

预算分配原则：隔离底座是"借来的"（成熟开源），差异化与易错点都在出口治理、策略层与生命周期层。

## 9. 开放问题

1. **NPU/GPU 隔离**：端侧 NPU 共享内存的隔离无现成方案，是端侧沙箱的最大技术空白；
2. **Scope 语言的表达力上限**："允许订 500 元以内机票一次"类委托的可表达范围，决定整个授权体系的上限；
3. **指令级授权投影**：业界当前粒度为"一个 Agent 一份策略"，"一条指令一份投影"尚无实现；
4. **iOS 仿真保真**：闭源约束下的替代验证方案；
5. **拒绝信息设计**：denial 携带多少上下文才能既支持 Agent 纠偏、又不引入撞墙重试死循环或信息泄漏。
