## §0 摘要

1. **云侧隔离底座已收敛，差异化在生命周期。** 底座分两大类：microVM（E2B、Blaxel、腾讯云 Cube、Docker Sandboxes、AWS AgentCore、Azure Hyper-V）和 gVisor（Modal、GKE Agent Sandbox、Anthropic claude.ai）[A5][A13][A14][A17]。冷启动数字几乎全靠池化和快照取得：Cube 平均 60ms 以内，Blaxel 待机恢复 25ms 以内，Morph 分支 250ms 以内，都是厂商自述 [A7][A8][A9]。
2. **手机上缺的不是隔离类型，而是「会话生命周期层」。** 可借的硬隔离只有 AVF / pKVM，且机型覆盖没有官方清单；SDK Runtime 随 Privacy Sandbox 在 2025-10 退役 [A20]。系统级的「按会话出口代理」和「会话快照 / 分叉」在三家移动 OS 上都没有量产原语。判断：我方要做的是把隔离、出口策略、凭证注入、快照包成一个会话对象。
3. **约一半公开事件全程使用 Agent 的合法权限，权限衰减挡不住。** 在 13 个事件中，EchoLeak、GitHub MCP、Supabase MCP、Comet、Replit 都属于这一类；能阻断它们的只有信息流（污染）标签、会话属性约束和出口治理 [B22][B42][B44][B45]。Anthropic 披露的事件里，沙箱本身没破，数据经白名单域名外泄 [A16]。
4. **有效防护都在确定性执行层，模型层不可靠。** CaMeL 可证明安全地完成 77% 的任务（无防护 84%）[B5]；FIDES 启用策略检查时挡住 AgentDojo 全部注入 [B6]；Progent 把攻击成功率从 39.9% 降到 1.0% [B7]。反过来，12 个已发表的模型层防护被自适应攻击绕过，多数成功率超过 90% [B9]；Anthropic 自家的 auto mode 分类器漏报 17% [B10]。
5. **七要素里，dry-run 和 undo 是业界真空。** schema、异步、结构化拒绝已有标准件；效果描述只有 MCP 的「提示性」注解，规范要求客户端视为不可信 [B3]；dry-run 和 undo 在 MCP、AppFunctions 中都没有标准位置 [B3][B4]。这既是我方的差异化点，也是生态成本最高的两项。
6. **MCP 在一年内两次结构性修订。** 2026-07-28 版改为无状态、去掉 SSE 断点续传、把 Tasks 移出核心、弃用 Roots / Sampling / Logging 和动态客户端注册 [B1]。去掉续传后，断流的请求要以新 ID 重发，带副作用的动作可能被重复执行。判断：七要素的「幂等」不能依赖应用自觉，需要系统层的幂等键。
7. **Agent 身份正在被收进平台层，这挑战 SBX-9。** Microsoft Entra Agent ID 把 Agent 做成一等身份 [B14]；Windows Agent Workspace 给 Agent 独立账户 [A3][B15]；Android AppFunctions 用平台权限 `EXECUTE_APP_FUNCTIONS` 放行调用方 [B4]；鸿蒙 Skill 上架与华为账号绑定 [B16]。
8. **凭证经纪人已是云沙箱的默认形态，支持 SBX-8。** Vercel、Deno、Daytona、Docker、Claude Code on the web、OpenShell、Cloudflare 都是「沙箱内无明文、出口注入」[A1][B11][B12][B17]。缺口有三：响应脱敏没有公开方案、非 HTTP 协议覆盖不全、合法凭证仍可能被滥用。
9. **确认弹窗在高批准率下接近无效。** Claude Code 用户手动确认中 93% 是批准 [B10]；沙箱化后权限提示减少 84%（内部口径）[B17]。判断：监督界面的出路是「边界内不打扰、越界才升级、事后可审可接管」。
10. **立场结论**：
    - 支持：SBX-2、SBX-6、SBX-8；
    - 支持但需补充：SBX-1（改措辞，允许自建生命周期层）、SBX-4（补策略来源信任）、SBX-7（补污染标签）；
    - 部分支持：SBX-3（dry-run、undo 改为可声明能力）；
    - 需修订：SBX-5（加会话污染状态维度）、SBX-9（拆成系统签发的会话主体 + 归应用的用户身份）。

## §3 逐问题分析

### Q1 云侧 Agent 执行沙箱格局

**三类底座。**

| 类别 | 厂商 | 特点 |
|---|---|---|
| microVM | E2B、Blaxel、腾讯云 Cube、Docker Sandboxes、AWS AgentCore、Azure dynamic sessions | 每会话独立内核；会话结束清理内存 |
| gVisor | Modal、GKE Agent Sandbox、Anthropic claude.ai | 开销小且固定；I/O 密集型负载慢 |
| 容器 / isolate | Cloudflare（Sandbox 容器 + Dynamic Workers isolate）、Daytona（官方称默认容器） | 启动最快；隔离强度最弱，Cloudflare 自加第二层沙箱 |

来源：[A5]–[A9][A13][A14][A18][A28]。另有两种不绑定单一底座的形态：kubernetes-sigs/agent-sandbox 只提供 CRD 和预热池，隔离委托给 RuntimeClass [A17]；NVIDIA OpenShell 的计算驱动可选 Docker、Podman、Kubernetes 或 microVM，在 Linux 上叠加 Landlock、seccomp 和沙箱内代理 [A1][A2]。

**生命周期原语是主战场。**

- **快照 / 分叉**：Cube 的 CubeCoW（XFS reflink 实现 O(1) 克隆）、Morph 的 Infinibranch、Cloudflare 文件系统快照、Modal 内存与文件系统快照 [A8][A9][A6][A24]。
- **休眠 / 待机**：Blaxel 待机可无限期，但待机态不持久；E2B 暂停期间保留内存和文件系统，且不计费 [A7][A11]。
- **预热池**：Azure 会话池、agent-sandbox WarmPool、Cube 资源池 [A14][A17][A8]。

共同结论：裸 VM 引导仍是百毫秒量级，毫秒级的数字全靠池化和快照取得 [A8]。计费模型都在走向「空闲不付费」，这反过来要求平台提供廉价的挂起和恢复。

**分歧。**

- 隔离强度没有唯一答案：Anthropic 对 claude.ai 用 gVisor，对本地 Cowork 用整机 VM，对 Claude Code 用 OS 级进程沙箱，三种强度对应三种威胁模型 [A16]。
- 内存快照有版本脆弱性：Modal 承认内存快照对 NVIDIA 驱动和运行时版本敏感 [A24]。
- 冷启动和恢复数字几乎都是厂商自述，没有独立复现。

**这说明什么。** 云侧证明了「会话级隔离 + 池化 + 快照」可以量产，而且每一项收益都依赖写时复制和页共享。手机上能借的是这些**原语**（预热池对应预先 fork 的 zygote 式沙箱，快照对应 pVM 快照），不是产品本身。

### Q2 策略与授权

**策略层收敛到「工具调用前置评估」。** AWS AgentCore Policy 在 2026-03-03 GA：把自然语言生成为 Cedar 策略，挂在 Gateway 上逐请求评估 [B19]。OpenShell 用 YAML：文件系统和进程段在创建时锁定，网络和推理段可以对运行中的沙箱热加载，未命中任何策略块的连接被阻断并记录 [B27]。

**Cedar 与 OPA / Rego。** 本轮只核实到 Cedar 一侧：它用 Lean 建模，逻辑编码可靠且完备，能精确回答「重构后授权集合是否变化」[B28]。判断：选型的关键变量不是表达力，而是「能否对机器生成的策略做静态分析」。当策略由 LLM 生成时（AgentCore、Progent、Conseca 都是这条路），可分析性就是刚需。v1 提到的「OpenShell policy prover」在公开文档中没有找到，不应写进设计依据。

**deny-by-default 出口。**

- Claude Code：文件系统限定在工作目录；网络只能经 Unix 域套接字连到沙箱外代理，按域名放行。Anthropic 强调两种隔离缺一不可——没有网络隔离，被攻陷的 Agent 能外泄 SSH 密钥；没有文件隔离，它能逃出沙箱再联网 [B17]。
- 但代理本身是攻击面：CVE-2025-66479 中「封锁全部出站」被当成「全部放行」；CVE-2026-25725 中，沙箱内代码可以创建 `.claude/settings.json` 并植入钩子，重启后以宿主权限运行 [B29]。教训：策略文件和配置文件必须在沙箱的写保护范围内。

**信息流控制是 SBX-7 的理论基础。**

| 方法 | 强制点 | 代价 | 证据 |
|---|---|---|---|
| CaMeL | 解释器跟踪数据来源与能力 | 效用 77% 对 84% | [B5] |
| FIDES | 规划器对带标签变量做策略检查 | 要为每个工具定义标签传播 | [B6] |
| Progent | 工具调用代理层的参数约束 | 策略质量依赖生成器 | [B7] |
| Conseca | 确定性评估器 | 策略正确性靠可审的理由字段 | [B30] |
| Chrome Critic + Origin Sets | 独立批评模型 + 源集合门控 | 产品化的「弱化版」 | [B8] |

分歧：CaMeL、FIDES 假设「控制流可以和不可信数据分离」，对读完数据才能决定下一步的任务，效用会下降。Chrome 明说 Critic「部分受 CaMeL 启发」，但选择了弱化版——判断：通用网页任务没法预先写出计划。

**参数化权限的先例。** Progent 的策略可以约束参数取值 [B7]；MCP 授权规范允许服务器按请求参数动态决定所需 scope [B31]；MCP 2026-07-28 新增 `x-mcp-header`，把指定参数镜像到 HTTP 头，让网关能按参数做策略 [B3]。反面教训：Claude Code 进入 auto mode 时会丢弃宽泛的 shell 和解释器规则，因为静态的「命令前缀白名单」容易被滥用成任意执行 [B10]。

**这说明什么。** 执行层的确定性策略有扎实的 L1 证据和 Chrome 的 L3 落地，SBX-4、SBX-6、SBX-7 方向正确。未解决的问题是「策略由谁写、谁审」——当策略本身由模型生成时，它也是一个需要信任评级的输入。

### Q3 凭证经纪人与身份

| 实现 | 注入位置 | 沙箱看到什么 | 弱点 | 证据 |
|---|---|---|---|---|
| Vercel Sandbox | 防火墙转换块，给匹配域名的 HTTPS 请求加头 | 无凭证 | 只覆盖头部 | [B11] |
| Deno / Daytona | 访问批准主机时把占位符换成真值 | 占位符 | 非 HTTP 协议无法替换 | [B12] |
| Fly Tokenizer | 无状态代理持私钥，客户端发加密的密钥头 | 只有密文 | 可用密文可被重放到允许的域 | [B12] |
| Claude Code on the web | git 代理校验作用域凭证与操作，再附加真实令牌 | 作用域凭证 | 作用域内仍可滥用 | [B17] |
| Anthropic Cowork | 凭证留在宿主钥匙串，VM 只拿每会话受限令牌 | 会话令牌 | — | [A16] |
| OpenShell | supervisor 注入，沙箱只持网关公钥 | 无凭证 | — | [A1] |

**响应脱敏**——服务把凭证回显到响应或错误信息里的情况——没有任何厂商公开方案。

**事故复盘带来的两条补充。**

- Nx s1ngularity：恶意 npm 包调用本机的 AI CLI（带 `--yolo` 等参数）递归搜索敏感文件，约 2349 个密钥被盗 [B13]。结论：「Agent 不持有明文」必须扩展为「Agent 所在环境里不存在明文」。
- Amazon Q 扩展（CVE-2025-8217）：入口是构建环境里权限过大的 GitHub 令牌，不是提示注入技术本身 [B32]。

**身份的走向。**

- MCP authorization：HTTP 传输上用 OAuth 2.1，令牌必须绑定受众，服务器不得接受或转发其他令牌 [B31]。但 stdio 传输明确不用这套规范。判断：对手机上本地调用的 AppFunctions，它没有约束力，端侧缺等价物。
- Entra Agent ID：blueprint 是创建 agent identity 的模板；agent identity 不持有自己的密钥；停用 blueprint 即阻止其全部 agent identity 认证 [B14]。
- Windows：Agent Workspace 中所有动作归属于独立于用户的 agent identity；所有 Agent 与连接器的通信经 MCP 代理，由代理执行同意、治理、审计 [B15][B34]。
- 鸿蒙：Skill 上架与华为账号认证绑定；转账、支付等环节由系统阻断自动流程，用户手动完成 [B16]。

**端侧形态。** 判断：在手机上，凭证经纪人最自然的形态是「系统服务持有密钥并代为签名或请求」（Keystore / Secure Enclave / HUKS 都是「可用不可导出」），而不是云侧的 HTTPS 中间人代理。存量 HTTPS 流量仍需要某种出口代理，这是云侧方案迁移到手机的主要障碍。

### Q4 接口面

**MCP 2026-07-28 的结构性变化**（相对 2025-11-25）[B1]：

1. 去掉协议级会话，取消 `initialize` 握手，改为无状态；有状态的服务器用显式句柄作为普通工具参数，且每次调用都要校验授权。
2. 去掉 SSE 断点续传：断流后请求丢失，客户端以新 ID 重发。
3. Tasks 从核心移出，成为官方扩展（轮询 + `tasks/update`）。
4. 新增 Multi Round-Trip Requests：服务器返回 `input_required`，客户端带输入重试。
5. 弃用 Roots、Sampling、Logging 和动态客户端注册；新增 12 个月的最短弃用窗口。

**七要素打分**（● 标准内明确支持；◐ 部分或仅为提示；○ 未找到；— 未核实）：

| 要素 | MCP 2026-07-28 | AppFunctions | App Intents | 鸿蒙 HMAF | Windows ODR | computer use |
|---|---|---|---|---|---|---|
| schema | ● | ● XML schema | ●（待核实） | — | ● 沿用 MCP | ○ |
| 效果描述 | ◐ 四个不可信提示 | ◐ KDoc + 应用元数据 | — | — | ◐ 声明最小能力 | ○ |
| dry-run | ○ | ○ | — | — | ○ | ○ |
| undo | ○ | ○ | — | — | ○ | ○ |
| 幂等 | ◐ idempotentHint | ○ | — | — | ◐ | ○ |
| 异步 | ◐ Tasks 扩展 + MRTR | ◐ `suspend`，无任务句柄 | — | — | ◐ | ○ |
| 结构化拒绝 | ● 含 403 `insufficient_scope` 质询 | ◐ 预定义异常 | — | — | ◐ | ○ |

依据：[B1][B3][B4][B35]。

**平台原生接口的结构与 SBX-2 同构。** Google 在 2026-02 公布：Gemini 用 AppFunctions 支撑日历、笔记、任务集成；对没有专门集成的应用，用 UI 自动化框架兜底 [B36]。「结构化函数 + UI 自动化兜底」正是 L1 + L0 的结构。鸿蒙 HMAF 2.0 提供 Agent、Skill、MCP、意图框架四种接入方式 [B16]。iOS App Intents 在 WWDC 2026 的变化只有二手报道，不作设计依据 [B37]。

**computer use 的定位。** 它没有 schema、dry-run、undo，不适合做 L1，只能做 L0 兜底并配外层门控。Chrome 的做法是：敏感站点、登录、购买、支付、发消息要求用户确认，并提供工作日志与接管 [B8]。

**命名与发现。** MCP 只保证工具名在单个服务器内唯一，聚合多服务器时可能冲突 [B3]；MCP Registry 从 2025-09 起处于预览，无数据持久性保证 [B38]；AppFunctions 由系统索引 XML schema [B4]。事件触发方面，AppFunctions 和鸿蒙没有找到公开接口描述。

**这说明什么。** 接口面已收敛到「函数式工具 + schema + 提示性注解 + 轮询式异步」。协议仍在快速变动，七要素不应直接绑定某个 MCP 版本的字段，内部要有一层稳定的抽象。

### Q5 Agent 安全

**基准与攻防。**

- AgentDojo：97 个任务、629 个安全测试用例 [B21]。
- 自适应攻击：Nasr、Carlini 等人用梯度、强化学习、搜索和人工红队绕过 12 个已发表防护。论文的方法学论点是：用静态攻击集评估防护几乎没有意义 [B9]。
- SandboxEscapeBench（即 v1 所说的 SEB）：评估前沿 LLM 能否逃出 Docker / OCI 容器，ICML 2026 收录 [B40]。判断：容器级边界对前沿模型不可靠，高风险会话应借更强的边界（VM / pKVM）。但 Claude Code 自己的 CVE 说明，实际绕过更常发生在代理和配置层，而不是内核逃逸。

**Meta Agents Rule of Two**（2025-10-31）[B18]：

- 三个属性：[A] 处理不可信输入、[B] 访问敏感系统或私有数据、[C] 改变状态或对外通信。
- 在能可靠检测提示注入之前，一个会话最多同时具备其中两个；三者都需要时，开新会话、清空上下文，或由人批准。
- Simon Willison 指出原图把「不可信输入 + 状态变更」标成「安全」不对，Meta 随后改为「lower risk」[B19b]。

**事件复盘**：13 个事件的逐一检验见 §7.4。结论是两类各占一半：

- 合法权限被劫持型（EchoLeak、GitHub MCP、Supabase MCP、Comet、Replit）：只有信息流标签、Rule of Two 和出口治理能挡；
- 供应链或实现缺陷型（Amazon Q、Nx、postmark-mcp、mcp-remote、OpenClaw、Claude Code CVE）：需要装配期校验和更强的隔离。

GTG-1002（Claude Code 被恶意使用于网络间谍活动）不在沙箱的防范范围内——用户本人就是攻击者。

**风险框架。** OWASP Top 10 for Agentic Applications 2026 于 2025-12-09 发布，ASI01 为目标劫持、ASI02 为工具滥用、ASI03 为身份与权限滥用 [B41]；完整条目、NIST AI 600-1、Google SAIF 本轮未核实。

### Q6 端侧会话级沙箱

| 能力 | Android | iOS | HarmonyOS | 桌面先例 |
|---|---|---|---|---|
| 进程级隔离可借 | 有：isolatedProcess、SELinux、seccomp | 有：App 沙箱、Extension | 有（细节待核实） | Seatbelt、bubblewrap、Landlock |
| VM 级隔离可借 | 有但机型受限：AVF / pKVM | 无第三方入口 | 未找到公开资料 | Cowork（平台 hypervisor） |
| 会话级身份 | 多用户、Private Space 可近似 | 无 | 待核实 | Windows Agent 账户 |
| 会话快照 / 分叉 | 无量产原语 | 无 | 未找到 | 云侧有 |
| 按会话出口代理 | 无系统级 | 无 | 未找到 | Claude Code、Cowork |
| 语义层把关 | 无 | 无 | 转账支付系统阻断 | Chrome Critic |

来源：[A3][A4][A16][A20]–[A22][A26][B16]。

**要点。**

- **Android**：pKVM 是 AVF 的标准 hypervisor，只限 ARM64；没有官方机型清单，联发科机型走 GenieZone（社区资料，待核实）[A22]。AVF 的气球调整曾因 VM 内存不足被回退，改为动态内存调整（C）——说明 pVM 内存与 LMKD、应用生命周期的耦合还没解决。SDK Runtime 已退役，不应作为借用对象 [A20]。
- **iOS**：Memory Integrity Enforcement 随 iOS 26 下发，覆盖内核和 70 余个用户态进程 [A26]，但它防的是内存破坏，不是会话隔离。判断：iOS 上的会话级沙箱只能由 Apple 自己作为系统服务来做，第三方借不到比 App 沙箱更细的边界。
- **HarmonyOS**：HDC 2026 上小艺暴露 2100 余项系统能力，并能通过 GUI 控制操作没有开放 API 的应用 [A29][B16]。v1 提到的「动态沙箱」没有找到公开资料。动作面已经很大，隔离方案却没有公开技术文档。
- **Windows Agent Workspace** 明确不是 VM，而是独立账户 + 独立会话；开启后 Agent 可以读写下载、桌面、图片等已知文件夹 [A3]。这说明「借来的边界」不一定是虚拟化，也可以是账户。

**这说明什么。** 手机上不缺某一种隔离，缺的是把隔离、出口策略、凭证注入、快照包成**会话生命周期**的那一层。桌面上 Windows（账户 + 会话）和 Anthropic（整机 VM）已各自走出一条路，手机上还没人做。

### Q7 隔离的代价（J5）

| 隔离单元 | 单会话内存 | 启动延迟 | 证据 |
|---|---|---|---|
| 进程沙箱 | 额外开销近零，主要是进程自身 RSS | 毫秒级 | 机制推断，D |
| V8 isolate | 数 MB | 数 ms | [A5] B / C |
| gVisor | 开销小且固定（官方未给数值） | — | [A27] A（定性） |
| Firecracker | VMM ≤5MiB + guest 内存 | ≤125ms；快照恢复更快 | [A10] A（目标值） |
| Microdroid（pVM） | 量级 32–42（疑为 MB）+ pvmfw + swiotlb | 绝对值未取得 | [A21][A22] C |

**关键认识：microVM 的单实例成本主要由 guest 里装了什么决定，而不是 VMM。** 降低代价的杠杆是「共享只读基底 + 快照分叉」。Firecracker 的快照内存文件私有映射、按需缺页、写入走写时复制 [A10]；但**分叉后实际页共享率没有任何公开实测**。

**手机承载估算**（D 级，全部为假设）：

- 假设：12GB 机型给 Agent 会话沙箱的预算 3GB，16GB 机型 5GB；进程级沙箱每会话私有页 40–100MB；microVM 每会话 guest 私有页 256MB + 固定开销 40MB；分叉后 50% 的页保持共享。
- 进程级：3GB ÷ 100MB ≈ 30，按 40MB 可到 75，量级为**数十个**。
- microVM 不共享：3GB ÷ 296MB ≈ 10；16GB 机型约 17。
- microVM 带写时复制共享：每会话私有约 150MB，3GB ÷ 150MB ≈ 20；16GB 机型约 33。

判断：「同时活跃」的会话数更多受端侧模型和 KV 占用限制，而不是沙箱本身。microVM 适合少量高风险会话（个位数到十余个），其余走进程级。这个估算没有建模 swiotlb、气球行为和 LMKD 压力下的可回收性，需要用仿真先占位、再用真机验证。

## §4 趋势判断

**正在收敛的方向**

1. 云侧默认：会话级 microVM 或 gVisor + 预热池 / 快照。
2. 出口默认拒绝 + 凭证在出口注入。
3. 工具调用前置评估（AgentCore Policy、Progent、Conseca、MCP scope 质询）。
4. 用「会话属性组合」描述风险（Rule of Two）。
5. 结构化接口 + UI 自动化兜底（AppFunctions + Gemini UI 自动化，MCP + computer use）。
6. Agent 主体上收平台（Entra Agent ID、Windows Agent Workspace、AppFunctions 调用方权限）。

**公认的空白点**

1. 端侧 OS 层的信息流标签与出口策略强制——没有找到公开实现。
2. dry-run 与 undo 的标准化。
3. 会话快照 / 分叉在手机上的量产原语，以及分叉后的页共享率实测。
4. 响应脱敏、合法凭证被误用的防护。
5. 工具注解的可信度——注解不可信，但没有签名或认证机制。
6. 端侧会话级沙箱的内存、启动、功耗实测。

**仍有分歧的问题**

1. 隔离强度取 VM、gVisor 还是 OS 级（Anthropic 三种并用）。
2. 确定性解释器（CaMeL）还是批评模型（Chrome Critic）。
3. 策略由人写、LLM 生成还是按任务动态生成。
4. 分类器自动批准是否可接受（Anthropic 已上线，漏报 17%）。
5. Agent 身份归平台、IdP 还是应用。
6. MCP 与平台原生接口（AppFunctions、App Intents、HMAF）长期融合还是并存。

| SBX-7 跨链不升级 | **支持，补信息流** | CaMeL、FIDES、Progent 的理论基础 [B5]–[B7]；MCP 禁止令牌透传 [B31] | EchoLeak、GitHub MCP 攻击链全程没有任何权限提升 [B22][B42] | 权限衰减之外，增加「污染传递」规则：链上数据的完整性标签单调不升；并扩展到时间维度——低完整性会话写入的记忆，读出时仍为低完整性（与 C3 MEM-1′ 对齐） | 中高 |
| SBX-8 凭证经纪人 | **支持** | 云沙箱默认形态 [A1][B11][B12][B17] | 经纪人不防合法凭证被滥用；Nx 事件说明环境里不能有明文 [B13] | 经纪人绑定目的地与会话（Cowork 的每会话受限令牌）；增加使用审计与限额；端侧采用「系统服务持钥并代为请求」的形态；要求会话环境内不存在明文 | 高 |
| SBX-9 身份归应用 | **需修订** | 反方：Entra Agent ID [B14]、Windows Agent 账户 [B15]、AppFunctions 平台权限 [B4]、鸿蒙 Skill 账号绑定 [B16] | 支持：MCP 授权把用户身份留给资源方与 IdP [B31] | 拆成两层：**会话级 Agent 主体**（包名 + 签名 + 会话号）由系统签发、可审计、可撤销；**用户对第三方服务的身份**仍归应用 | 中 |

### 5.2 修订后的立场表述（建议稿）

- **SBX-1′** 沙箱不自建隔离边界的类型，借用平台已有的进程级、VM 级、账户级边界，按风险档选用；但自建会话生命周期层（预热池、快照、分叉、挂起恢复），并负责把隔离、出口策略、凭证注入打包成一个会话对象。
- **SBX-3′** L1 动作的必选要素是 schema、结构化拒绝、异步任务句柄、幂等键、效果声明；效果声明由系统按实际观测校正。dry-run 与 undo（补偿动作）是可声明能力，未声明的动作一律按不可逆定档。
- **SBX-5′** 风险档位 = f（动作的可逆性、影响范围、数据敏感度；会话污染状态；调用方可信度）。同一会话同时满足「已接触不可信输入、访问敏感数据、产生外部副作用」时，强制升档或拆分会话。
- **SBX-6′** 策略在装配、调用、挂起 / 恢复、销毁四个时机执行。
- **SBX-7′** 跨链不升级包含两条单调规则：权限只减不增，数据完整性标签只降不升；这两条规则跨会话延伸到记忆。
- **SBX-9′** 系统签发并管理会话级 Agent 主体，作为审计与撤销的单位；用户对第三方服务的账号身份仍由应用管理。

## §6 接缝发现

**J5 隔离的内存代价（主责）**

- 隔离单元的内存 = 固定开销（VMM、pvmfw、swiotlb，几十 MB 量级）+ guest 私有页（取决于运行时与镜像）。杠杆在共享只读基底和快照分叉。
- 给内存管理（C4）的接口需求：
  - pVM 和会话沙箱的内存记入会话级 memcg（与 C4 的「会话作为归属标签」对齐）；
  - pVM 气球回收要与 LMKD / PSI 联动（AVF 气球回退事件说明这还没解决）；
  - swiotlb 与 dma-buf 的归属要可见。
- 与 J2 的交集：会话共享底座模型时，隔离单元不能直接映射 KV 页，要经 dma-buf 受控共享。这对 pVM 是额外约束，没有找到现成方案。

**J3 工具调用 / 结构化输出 ↔ 接口面（安全侧协同，主责推理）**

- 注入防护的位置：证据倾向执行层。自适应攻击系统性绕过模型层防护 [B9]；CaMeL、FIDES、Progent 的强制点都在解释器、规划器或工具调用代理 [B5]–[B7]。
- 分工：MCP 规范明确，`structuredContent` 是服务器产出的结果数据，和 LLM 的「结构化输出」（约束生成）无关 [B3]。所以约束解码（推理侧）保证参数合乎 schema，沙箱用 schema 做入口校验与策略评估，二者不能互相替代。
- 线索：MCP 要求工具列表确定性排序，以利于 LLM 提示缓存命中 [B1]——接口面的稳定性与推理侧前缀缓存直接相关。

**J4 记忆的写入授权与投毒（协同，主责记忆）**

- 沙箱向记忆框架提供三样东西：会话级 Agent 主体（SBX-9′）、会话污染状态（SBX-5′）、数据来源域。记忆条目继承这些标签。
- 「跨链不升级」延伸到时间维度后，记忆框架成为污染标签跨会话持久化的唯一位置。详见 [C3 记忆框架](C3-记忆框架与记忆能力.md) §6。

### 7.2 七要素逐条评审

| 要素 | 业界先例 | 支持度 | 实现难点 | 修订建议 |

### 7.3 三维定档评审

**假设**：三维为可逆性、影响范围、数据敏感度。

| 对照对象 | 其维度 | 与三维的关系 | 缺口 |
|---|---|---|---|
| Meta Rule of Two [B18] | 不可信输入、敏感数据访问、状态变更 / 对外通信 | 数据敏感度 ≈ 敏感数据访问；可逆性和影响范围 ≈ 状态变更的强度 | 缺「会话是否已接触不可信输入」——这是会话的动态状态，不是动作属性 |
| MCP 工具注解 [B35] | 只读、破坏性、幂等、开放世界 | 只读 / 破坏性 ≈ 可逆性；开放世界 ≈ 外部可见性 | 注解不可信；缺数据敏感度 |
| OWASP ASI [B41] | 目标劫持、工具滥用、身份与权限滥用等 | 威胁分类，不是定档维度 | 「身份与权限滥用」说明调用方身份应进入定档 |
| Chrome 敏感动作清单 [B8] | 敏感站点、登录、购买、支付、发消息 | 清单式，对应资金与外部可见性 | 实践中资金单列 |

**结论（判断）**：三维作为「动作的静态属性」基本够用，但缺两个量：

1. **会话污染状态**：决定同一个动作在不同会话里是否升档。可以先简化为二值——「本会话是否读取过外部不可信内容」，后续再升级为 FIDES 式的标签。
2. **调用方可信度**：包括调用方身份、策略来源级别。

定档函数建议改为「动作静态三维 × 会话污染状态 × 调用方可信度」，并把「同一会话同时出现污染、敏感数据访问和外部副作用」设为硬性升档条件。资金是否单列，由设计文档决定；Chrome 的实践支持单列。
